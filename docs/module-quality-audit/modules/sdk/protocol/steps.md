## Step 1 Scope and public surface

The `sdk` unit is the runtime half of the programmatic SDK. `packages/ax-code/src/sdk/programmatic.ts:1` is a one-line barrel into `programmatic-impl.ts`; the implementation re-exports the SDK error classes at `packages/ax-code/src/sdk/programmatic-impl.ts:44-53` and directly exports `formatToolArgumentsForPrompt` at `:96` plus `createAgent` at `:922`. The corresponding public contract lives in `packages/sdk/js/src/programmatic/types.ts:113-180,182-240,260-289`, while `packages/sdk/js/src/programmatic/agent.ts:7-29` dynamically loads `ax-code/sdk/programmatic`. I treated those contract and loader files as required related evidence rather than reviewing the two candidate files in isolation.

## Step 2 Trust boundaries and sensitive data

The main sensitive boundary is authentication. Creation can persist an explicit API key (`programmatic-impl.ts:966-974`) and auto-detects four environment variables (`:196-219`). The persistence sink encrypts API-key fields (`packages/ax-code/src/auth/index.ts:287-292`) and writes the auth file with mode `0600` (`auth/index.ts:411-426`), so keys are not inserted into prompts or logs by this unit. In-process requests receive a process-random runtime header at `programmatic-impl.ts:550-561`; comparison is length-checked and timing-safe in `packages/ax-code/src/server/runtime-auth.ts:5-26`. Permission events are scoped to `sessionID` and default to rejection when no hook is installed (`programmatic-impl.ts:630-637,745-752`). A weaker boundary exists in `Agent.tool`: serialized caller input is interpolated into an LLM instruction (`:1126-1145`) instead of invoking the registered tool executor directly, making the method probabilistic and allowing argument text to influence the instruction despite the public description “Execute a tool directly” at `packages/sdk/js/src/programmatic/types.ts:282-283`.

## Step 3 Session-isolation correctness

The event subscription is directory-wide, but two event types are not narrowed to the active session. In `collectResult`, assistant `message.updated` events overwrite `agent`, model, and `messageID` without checking `info.sessionID` (`programmatic-impl.ts:588-596`), although the generated message type carries that field (`packages/sdk/js/src/v2/gen/types.gen.ts:230-250`). The same omission exists in streaming at `programmatic-impl.ts:668-676`. More seriously, every `session.error` terminates the collector or stream at `:624-628` and `:738-743`, even though the event schema supplies an optional `properties.sessionID` (`types.gen.ts:1621-1634`). By contrast, parts, permissions, and idle status are explicitly filtered at `programmatic-impl.ts:598-600,630-632,640-645`. Concurrent `agent.run`, `agent.stream`, and persistent sessions are permitted and tracked in a set (`:926-948`), so an unrelated run in the same directory can corrupt metadata or fail another run. This is a High correctness finding.

## Step 4 Streaming, cancellation, and lifecycle

Normal completion caches the result and resolves the completion promise (`programmatic-impl.ts:253-294`). Cancellation is less robust: `cancel()` only queues `generator.return()` (`:344-359`), while the session-abort callback is deferred until the generator reaches its `finally` block (`:285-292`). If a consumer already has a pending `next()` waiting for an SSE event, async-generator `return()` waits behind that read, so cancellation may not promptly abort the session that would unblock the read. The advertised `RunOptions.timeout` (`packages/sdk/js/src/programmatic/types.ts:169-180`) is enforced for `run` (`programmatic-impl.ts:823-832,1038-1053`) but is never consulted by either stream path (`:835-869,1057-1117`). Also, a saved `SessionHandle` checks disposal only in `fork` and `abort` (`:877-892`); `run`, `stream`, and `messages` can reach the torn-down client after `agent.dispose()` (`:1180-1187`) rather than consistently throwing `DisposedError`.

## Step 5 Retry behavior and performance

Each run subscribes before prompting, which avoids missing early events (`programmatic-impl.ts:790-805`), and timeout wrappers clear their timers on both fulfillment and rejection (`:147-180`). Retries create a fresh event subscription and re-prompt the same session (`:370-424,790-820`) with bounded exponential delays up to eight seconds. The retry predicate accepts only 429, 500, 502, 503, and 504 (`:384-400`), while the public `ProviderError.isRetryable` reports every status at or above 500 as retryable (`packages/sdk/js/src/programmatic/types.ts:21-33`); callers can therefore see a different policy from the built-in runner. Tool and permission hooks are awaited inside the event-consumption loop (`programmatic-impl.ts:606-619,714-734,745-752`), intentionally preserving order but allowing a slow user hook to delay SSE consumption. Per-run state is bounded; the principal scaling cost is one full event subscription per concurrent attempt.

## Step 6 API and design consistency

The loader/runtime split is coherent: the published package owns types and error identity, while the runtime owns bootstrap and in-process server plumbing (`packages/sdk/js/src/programmatic/agent.ts:1-29`; `programmatic-impl.ts:11-42,550-561`). The bootstrap callback remains alive until disposal so `Instance.provide` does not tear resources down early (`programmatic-impl.ts:950-999`; `packages/ax-code/src/cli/bootstrap.ts:4-16`). Two public options are nevertheless disconnected from implementation: `AgentOptions.system` and `AgentOptions.signal` are declared at `packages/sdk/js/src/programmatic/types.ts:120-135`, but neither is read from `opts`; prompt input even supports `system` in the generated client contract (`packages/sdk/js/src/v2/gen/types.gen.ts:11405-11431`). Custom tool registration is ordered before client creation (`programmatic-impl.ts:976-995`), but failed registrations are only warned and creation still succeeds, so callers cannot know from the return value that a requested tool is unavailable.

## Step 7 Hygiene and test quality

The candidate files contain no TODO/FIXME markers and follow the repository’s ESM/no-semicolon conventions. Best-effort suppression is concentrated around abort cleanup (`programmatic-impl.ts:808-814,867-869,938-940,1025-1050,1065-1069`); the non-serializable custom-tool result path deliberately substitutes a marker at `:530-534`. The focused runtime test file has two behavioral serialization tests (`packages/ax-code/test/sdk/programmatic.test.ts:6-29`), but its remaining seven tests inspect source substrings (`:31-138`) rather than executing agents, event filtering, timeouts, or disposal. `packages/sdk/js/test/stream-handle.test.ts:72-103` exercises cancellation only through `createMockAgent`, not the real `createStreamHandle` in this unit. Missing regressions include concurrent session-error/message events, cancellation during a blocked read, stream timeout, use-after-dispose on a session handle, propagation of `system`, and prompt failure in `Agent.tool`.

## Step 8 Findings and severity disposition

No Critical item was found, and no finding files exist under `docs/module-quality-audit/modules/sdk/findings/`. Findings from this pass are: **High — cross-session event contamination**, at `programmatic-impl.ts:588-596,624-628,668-676,738-743`; filter events whose supplied session ID differs from the collector’s session. **Medium — cancellation/stream timeout contract**, at `:285-292,344-359,835-869`; trigger idempotent abort immediately from `cancel()` and apply `RunOptions.timeout` to streams. **Medium — ignored public configuration**, because `system` and agent-level `signal` are declared at `types.ts:120-135` but never applied. **Medium — “direct” tool execution is LLM-mediated**, at `programmatic-impl.ts:1126-1157`. **Low — tool-error detail is discarded**: generated error state contains `error` (`types.gen.ts:428-440`), while `getToolOutput` returns an empty string for every non-completed state (`programmatic-impl.ts:114-116`), so hooks and `ToolCallInfo` lose the diagnostic. None meets the Critical re-verification threshold, so `protocol/reverify.md` is not created.
