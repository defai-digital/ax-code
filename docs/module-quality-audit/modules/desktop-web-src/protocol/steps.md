# Review Protocol — desktop-web-src

## Step 1 Scope and Entry Map

I read all 15 requested sources under `desktop/packages/web/src` for the `desktop-web-src` unit: the eight `api/*.ts` adapter modules, their three co-located `.test.ts` files, `api/index.ts`, and the two React entry points `main.tsx` and `mini-chat-main.tsx`, plus `MODULE-AUDIT.md` (the `findings/` directory is empty). The composition root is `desktop/packages/web/src/api/index.ts:12`, where `createWebAPIs` assembles eight sub-API factories (`terminal`, `git`, `files`, `settings`, `permissions`, `notifications`, `github`, `tools`) into a single `RuntimeAPIs` object. Endpoint paths are not defined here — `desktop/packages/web/src/api/constants.ts:1` re-exports them from `@openchamber/ui/api/endpoints` so each route string lives exactly once, and `constants.ts:6-30` only re-groups them into a web-specific shape. The two entry points both assign the composed APIs to `window.__AX_CODE_DESKTOP_RUNTIME_APIS__` (`desktop/packages/web/src/main.tsx:13`, `desktop/packages/web/src/mini-chat-main.tsx:12`) and then dynamically import the UI renderer.

## Step 2 Assets, Boundaries, and Failure Modes

The adapter holds no long-lived secrets itself; the protected assets are the GitHub device-flow payloads, settings JSON, and filesystem operations proxied to the local authenticated server. The filesystem boundary is consistently expressed through an opt-in `allowOutsideWorkspace` flag forwarded on `createDirectory`, `statFile`, `readFile`, `writeFile`, and `downloadFile` (`desktop/packages/web/src/api/files.ts:111`, `:134`, `:162`, `:192`, `:274`) — the client never silently adds it, so workspace containment stays a server-enforced contract. `desktop/packages/web/src/api/permissions.ts:4-14` is an explicit trust-the-input stub: `requestDirectoryAccess` echoes `request.path` back with `success: true` and `startAccessingDirectory`/`stopAccessingDirectory` discard their argument (`permissions.ts:8`, `:12`). That is correct for a web runtime with no native directory picker, but it means the web permission surface grants no real capability — every actual FS mutation still goes through the authenticated `files` endpoints. Failure handling is uniform: each fetch checks `response.ok`, attempts to read a JSON `error` field, and falls back to `statusText` (`files.ts:60-63`, `desktop/packages/web/src/api/github.ts:35-37`, `desktop/packages/web/src/api/settings.ts:21-23`), with `jsonOrNull` (`github.ts:24-26`) centralizing null-safe parsing for the GitHub module.

## Step 3 Correctness and State Transitions

`normalizePath` (`desktop/packages/web/src/api/files.ts:13`) is applied to both inputs and response fields, and `toDirectoryListResult` (`files.ts:29-45`) filters entries missing `name`/`path` and coerces `isDirectory` to a real boolean, so malformed server payloads cannot crash the list view. `downloadFile` (`files.ts:268-284`) constructs a `download=true` query URL and uses an anchor click; `desktop/packages/web/src/api/files.test.ts:30-47` pins the exact encoded URL `/api/fs/raw?path=%2Ftmp%2Fapproved%2Fimage.png&download=true&allowOutsideWorkspace=true`. The main correctness smell is in `github.ts`, which builds query strings three different ways in one file: `new URLSearchParams({...})` at `github.ts:114-119`, manual `directory=${encodeURIComponent(directory)}&page=${...}` concatenation at `github.ts:185`, `:202`, `:221`, and `:273`, and `new URL(API_ENDPOINTS.github.pullsContext, window.location.origin)` plus `searchParams.set` at `github.ts:244-256`, `:292-298`, and `:315-321`. Each path currently encodes its arguments so there is no live bug, but the variety is a latent correctness hazard — a future param added to one of the manual-concat sites could easily miss encoding. `desktop/packages/web/src/api/settings.ts:48-55` returns `{ restarted: true }` unconditionally after any 2xx on the reload endpoint, so an async server-side restart that later fails has already been reported as success to the UI.

## Step 4 Security Review

The adapter does not touch tokens directly: GitHub credentials live server-side and are addressed indirectly through the `authStatus`/`authStart`/`authComplete`/`authDisconnect`/`authActivate` endpoints (`desktop/packages/web/src/api/github.ts:29-94`). `authComplete` sends only the short-lived `deviceCode` in a JSON body (`github.ts:56-61`), matching the OAuth device-flow pattern. There is no `eval`, `innerHTML`, or dynamic property construction; `downloadFile` builds its anchor `href` from `buildQueryUrl` with URL-encoded params (`files.ts:277-280`), so there is no injection vector. The `allowOutsideWorkspace` opt-in is forwarded only when the caller explicitly sets it, so the client cannot escalate beyond the workspace on its own. The `permissions.ts` stub returning success without verification is not a privilege escalation because it grants no capability — the actual mutations still traverse the authenticated server routes, which are out of scope for this unit and owned by `desktop-web-ax-code`. The `tools.getAvailableTools` filter `tool !== "invalid"` (`desktop/packages/web/src/api/tools.ts:21`) is defensive: a malformed/broken tool id emitted by the server is dropped before reaching the UI tool registry.

## Step 5 Performance and Concurrency

The layer is stateless: each `create*API()` factory returns a fresh object literal and there is no shared mutable state, which is safe for concurrent React renders. Requests are one-fetch-per-action with no batching, which is appropriate for an adapter. `desktop/packages/web/src/api/terminal.ts:21-30` exposes a tunable retry policy (`maxRetries` 3, `initialRetryDelay` 1000 ms, `maxRetryDelay` 8000 ms, `connectionTimeout` 10000 ms, sourced from `desktop/packages/web/src/api/constants.ts:62-66`) and delegates the actual reconnect logic to `@openchamber/ui/terminalApi` (`terminal.ts:38`). `readFile` differentiates HTTP caching by intent — `cache: "no-store"` when the read is optional and `"default"` otherwise (`files.ts:167-169`) — a small but deliberate hint. The one spot worth a future look is `tools.getAvailableTools` (`tools.ts:5-22`), which refetches and re-sorts the full tool list on every call with no client memoization; if the UI calls it per-render it would generate redundant requests, though the impact is low because the list is small.

## Step 6 Design and Ownership

The adapter pattern is coherent: one factory per interface, composed at a single root (`desktop/packages/web/src/api/index.ts:12-22`) that matches the `RuntimeAPIs` shape from `@openchamber/ui/api/types`. `desktop/packages/web/src/api/git.ts` is almost entirely a passthrough re-export of `@openchamber/ui/api/gitApiHttp` (`git.ts:4-72`); the web package adds no git logic, it only satisfies the `GitAPI` contract. The `worktree` namespace at `git.ts:67-72` re-aliases `listGitWorktrees`/`validateGitWorktree`/`createGitWorktree`/`deleteGitWorktree` that are already exposed flat at `git.ts:21-24`; this is interface-driven (the `GitAPI` type exposes both the flat functions and the nested `worktree` object), not accidental duplication. The genuine duplication is the fetch-error block in `files.ts`: `const error = await response.json().catch(() => ({ error: response.statusText })); throw new Error(error.error || "...")` recurs at `files.ts:60-63`, `:87-90`, `:115-118`, `:138-141`, `:171-174`, `:196-199`, `:219-222`, `:237-240`, and `:259-262` — eight sites with only the fallback message differing, so a small `assertOk(response, fallback)` helper would remove roughly 40 lines. Finally, `desktop/packages/web/src/main.tsx:7-11` and `desktop/packages/web/src/mini-chat-main.tsx:6-10` duplicate the `declare global { interface Window { __AX_CODE_DESKTOP_RUNTIME_APIS__?: RuntimeAPIs } }` block plus the assignment, and `mini-chat-main.tsx:15` then calls `renderElectronMiniChatApp(window.__AX_CODE_DESKTOP_RUNTIME_APIS__ ?? createWebAPIs())` even though line 12 just set that global, making the `?? createWebAPIs()` fallback effectively dead.

## Step 7 Hygiene and Observability

There are no silent empty catches on production paths. The `.catch(() => null)` in `jsonOrNull` (`desktop/packages/web/src/api/github.ts:24-26`) and the `.catch(() => ({ error: response.statusText }))` blocks in `files.ts`/`settings.ts` are intentional fallback-shape constructors that feed the immediately following `throw`, not swallowed errors. Diagnostics are concentrated in `desktop/packages/web/src/api/notifications.ts`, which logs `console.info`/`console.warn` at `notifications.ts:7`, `:14`, `:20`, `:31`, and `:60` when notifications are unsupported, permission is denied, or the Tauri bridge fails — reasonable, with no telemetry leakage. The `TauriGlobal` type is declared after its uses at `notifications.ts:41` and `:71` (`notifications.ts:79-83`); TypeScript hoists types so it compiles, but placing it above the first use would read more naturally. There are no TODOs, debug breakpoints, or hardcoded `localhost` URLs — every route comes from the UI endpoint catalog. The only opaque value is the `"invalid"` sentinel at `desktop/packages/web/src/api/tools.ts:21`, which would be clearer as a named constant or a server-emitted enum.

## Step 8 Tests and Finding Disposition

I ran the three co-located vitest files: `pnpm exec vitest run src/api/files.test.ts src/api/git.test.ts src/api/notifications.test.ts` from `desktop/packages/web` → 3 files, 6 tests, all passed (vitest v4.1.9, ~132 ms). `desktop/packages/web/src/api/files.test.ts:16-28` and `:30-47` cover `createDirectory` and `downloadFile` with the `allowOutsideWorkspace` flag, `desktop/packages/web/src/api/git.test.ts:64-71` asserts `stageGitFiles`/`unstageGitFiles` are functions, and `desktop/packages/web/src/api/notifications.test.ts:25-59` is the strongest file, covering Tauri success, Web Notification fallback, and the legacy `null` result. Coverage is genuinely thin for this unit: `files.ts` exposes 10 methods but only 2 are exercised (no `listDirectory`, `search`, `statFile`, `readFile`, `writeFile`, `delete`, `rename`, `revealPath`, and no error-path coverage), `git.ts` has a single structural assertion, and `github.ts` (332 lines, 16 methods) has no co-located test at all. The `findings/` directory is empty, so there are no prior registered items. My review found no Critical issues; the noteworthy items — inconsistent query building in `github.ts`, thin co-located coverage, the repeated fetch-error block in `files.ts`, and the dead `?? createWebAPIs()` fallback — are LOW/MEDIUM and non-blocking, so no `reverify.md` is required.

## Step 9 Verification and Exit Assessment

The command `pnpm exec vitest run src/api/files.test.ts src/api/git.test.ts src/api/notifications.test.ts` (executed from `desktop/packages/web`) completed successfully with 3 files and 6 tests passing. This was a static, read-only review of the `desktop-web-src` unit; no production source or other audit unit was modified. The nine-step protocol is complete. The module is not issue-free: the highest-value follow-ups are (a) consolidating the three query-building styles in `desktop/packages/web/src/api/github.ts` onto one helper, (b) adding error-path and method coverage for `files.ts`/`github.ts`, and (c) extracting the repeated `assertOk` block in `files.ts`.
