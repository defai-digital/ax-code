## Step 1 — Map

The installation unit comprises two files: `packages/ax-code/src/installation/index.ts` (389 LOC) exporting the `Installation` namespace, and `runtime-mode.ts` (55 LOC) exporting `detectRuntimeMode`/`runtimeMode`. The `Installation` namespace exposes version detection (`VERSION`/`CHANNEL`/`USER_AGENT` constants from build-time globals at index.ts:79-88, with `isPreview`/`isLocal` helpers), version comparison (`compareVersions`, `getReleaseType` at 48-66 using `semver`), install-method detection (`method()` at 266-281 probing `process.execPath` and `brew list --formula`), latest-version lookup (`latest(installMethod)` at 283-300 hitting GitHub Releases API or `brew info --json=v2`), the upgrade orchestrator (`upgrade(m, target)` at 302-367 dispatching to `upgradeCurl` or a brew tap+pull+upgrade sequence), and `verifyActiveLauncher` (382-388) for post-upgrade PATH-shadow detection. A `withDependencies` harness (146-154) enables test injection of `fetch`/`run`/`which`. `runtime-mode.ts` classifies the runtime as compiled/source/bun-bundled/node-bundled/node-source/unknown from `process.execPath` basename + `AX_CODE_VERSION`/`AX_CODE_CHANNEL` globals. Constants (`HOMEBREW_TAP`, `INSTALL_SCRIPT_URL`, `GITHUB_LATEST_RELEASE_API_URL`, etc.) come from `@/constants/project`. Bus events `installation.updated` and `installation.update-available` are defined (33-46).

## Step 2 — Threat model

The central asset is the upgrade pipeline: `upgradeCurl(target)` fetches an install script from a hardcoded `INSTALL_SCRIPT_URL` (index.ts:223) and pipes it to `bash` (`dependencies.run(["bash"], { input: bodyBytes, ... })` at 253-256). The primary defense is the SHA-256 sidecar verification (index.ts:233-252): the script body is fetched, hashed via `crypto.subtle.digest("SHA-256", bodyBytes)`, and compared against `<scriptUrl>.sha256`; a mismatch is a hard throw (244-245), while a missing sidecar only warns and proceeds (236) for backwards compatibility with deployments lacking the sidecar — a deliberate fail-open for availability that is logged. The second asset is external-API trust: `latest()` fetches version metadata from GitHub or Homebrew formulae APIs (index.ts:294-299) and parses it with Zod schemas (`GitHubRelease`, `BrewFormula`, `BrewInfoV2` at 112-116) so a hostile/corrupt API cannot inject arbitrary structure — worst case is a parse failure surfacing as an error. The `text()` helper (179-182) swallows spawn failures to empty stdout (`.catch(() => ({ code:1, stdout:"", stderr:"" }))`) for probe commands, which is correct for best-effort detection but means a missing `brew` binary is indistinguishable from "not installed via brew" — an accepted limitation. The `runCommand` spawns via `Process.spawn` with inherited+override env (157-172); env passed to upgrade is minimal (`VERSION`, `HOMEBREW_NO_AUTO_UPDATE`).

## Step 3 — Correctness

Key invariants: (1) the SHA-256 check computes the hash over exactly the bytes that get executed — `bodyBytes` is encoded once (index.ts:229) and reused for both the hash (240) and the bash stdin (254), with an inline comment at 227-228 explaining this; (2) `compareVersions` returns `undefined` for non-semver inputs (index.ts:49) and `getReleaseType` propagates that as "unknown" (55) rather than crashing; (3) brew upgrade handles the cask/formula link conflict — after a successful `brew upgrade`, if output contains "cask is installed, skipping link" it runs `brew link` and logs success/failure (index.ts:334-345), with an inline comment at 329-333 explaining the real-world Homebrew token-collision scenario; (4) `upgrade` throws `UpgradeFailedError` on non-zero exit (356-359) so callers see a typed error; (5) `verifyActiveLauncher` (382-388) detects PATH shadowing by comparing the resolved launcher's `--version` output to the target — a genuinely useful post-upgrade safety check. The `withDependencies` save/restore (146-154) correctly uses try/finally so a thrown test fn restores the previous dependencies. Error translation: `parseJson` (194-198) surfaces contextual errors ("Failed to parse <context> as JSON") instead of raw "Unexpected end of JSON input". One subtle point: the SHA-256 catch block at 248-252 re-throws only if the message starts with "Install script integrity check failed" (250), otherwise warns and continues — this correctly distinguishes a genuine hash mismatch (fatal) from a network error fetching the sidecar (recoverable).

## Step 4 — Performance

Upgrade is an infrequent, user-initiated operation — not a hot path. The costs are dominated by external IO: `fetch` of the install script (index.ts:225), optional sidecar fetch (234), `brew` subprocess invocations (`getBrewFormula` does up to 4 sequential `brew list` probes at 211-218, and `latest` for brew does `brew info --json=v2` at 289), and the final `bash` install (253). The 4-probe `getBrewFormula` sequence (211-218) is sequential `await text(...)` calls — each spawns a process — which is the slowest part, but it short-circuits on the first hit and is only invoked during upgrade/latest, not at startup. `method()` (266-281) does up to 4 more sequential `brew list` probes — also short-circuiting. No caching, but these are one-shot detection routines where caching would risk staleness. No unbounded collections, no synchronous blocking IO on the event loop except `readFileSync` is not used here (the module uses `Process.spawn` + `buffer` from `node:stream/consumers`). `VERSION`/`CHANNEL` are computed once at module load (79-87). No performance finding; the sequential brew probes are a minor latency note but appropriate for correctness (each probe depends on the previous miss).

## Step 5 — Design

Cohesion is good: version constants/detection, method detection, latest lookup, and upgrade orchestration are clearly sectioned within `Installation`, and `runtime-mode.ts` is correctly split out as a distinct concern (the file header at runtime-mode.ts:1-12 explicitly distinguishes "which executable is loading code" from Installation's "which package manager installed"). The `Dependencies` interface (130-134) + `withDependencies` harness (146-154) + `defaultDependencies` (136-142) is a clean dependency-injection pattern enabling test doubles for `fetch`/`run`/`which` — good testability design. The `LauncherCheck` interface (369-380) and `verifyActiveLauncher` encode a real post-upgrade safety property (PATH shadowing) as a typed result. One mild smell: the brew tap/formula migration logic (legacy `LEGACY_HOMEBREW_TAP` vs canonical `HOMEBREW_TAP`, index.ts:205-220, 270-275) is spread across `getBrewFormula` and `method` with duplicated formula-name lists — a shared `BREW_FORMULA_CANDIDATES` constant would reduce drift risk, but the duplication is currently consistent. Boundary conformance: imports are `@/bus`, `@/constants`, `@/flag`, `@/util/*` — clean. The `declare global { const AX_CODE_VERSION / AX_CODE_CHANNEL }` (19-22) is the standard build-time-global pattern.

## Step 6 — Dead code / hygiene

Concrete items: the `Event.UpdateAvailable` bus event (index.ts:40-45) is defined but I did not find a producer for it within this file (only `Updated` is implied by the `log.info("upgraded", ...)` at 360) — it may be emitted elsewhere or be a planned-but-unwired event; worth confirming but not a defect. The `runtime-mode.ts` file is cleanly separated and its `cached` variable (50-54) is a legitimate module-level memo. No `TODO`/`FIXME`/`HACK` markers (inventory reports 0). No empty `catch{}`. The `.catch(() => ({ code:1, stdout:"", stderr:"" }))` at index.ts:180 in `text()` is an intentional "best-effort probe returns empty on spawn failure" pattern, documented by the comment at 174-178. The `parseJson` catch path rethrows with context (194-198). The SHA-256 catch (248-252) distinguishes fatal-mismatch from recoverable-sidecar-error as noted. The `require("../../package.json").version` at 82 inside a `try/catch` (81-85) is a CommonJS `require` in an ESM module — this works due to the bundler/esbuild transform but is a style inconsistency worth a future cleanup note; it exists to read the version in dev mode where `AX_CODE_VERSION` is undefined. No findings warranted.

## Step 7 — Tests

The MODULE-AUDIT lists `test/installation/installation.test.ts` and `test/installation/runtime-mode.test.ts`. The `installation.test.ts` file exercises the `withDependencies` injection harness (the existence of that harness at 146-154 strongly implies tests inject fake `fetch`/`run`/`which` to test curl SHA-256 verification, brew upgrade flow, version comparison, and launcher verification without real network/subprocess). `runtime-mode.test.ts` covers the `detectRuntimeMode` classification across execPath basenames (bun/node/bun.exe) and channel/version-defined combinations. Gaps: the brew cask-skip-link relink path (index.ts:334-345) is a specific real-world recovery branch worth a dedicated test; the SHA-256-sidecar-missing-but-script-valid path (236, the fail-open warning) and the sidecar-network-error recovery path (248-252) are good negative-test candidates; and the `verifyActiveLauncher` PATH-shadow detection (382-388) with a stale launcher reporting a different version is a valuable safety property to assert. These are test-gap notes.
