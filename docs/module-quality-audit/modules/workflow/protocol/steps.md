## Step 1 Scope and Inventory

The `workflow` unit under `packages/ax-code/src/workflow` is a self-contained module of 20 TypeScript files (~6,080 LOC) that implements durable multi-phase agent workflows. The barrel `packages/ax-code/src/workflow/index.ts:1` re-exports 12 sibling modules plus a curated subset of `state` IDs/records (index.ts:14–38). Layering is clean and one-directional: `spec.ts` (zod schema + `parseWorkflowSpecV1` at spec.ts:402) → `state.ts` (branded IDs + event records) → `workflow.sql.ts` (Drizzle tables) → `run/index.ts` (CRUD) + `run/internal.ts` (row parsers, assertions, event publishers) → `run/budget.ts`, `run/final-report.ts` → `scheduler.ts`, `task-queue.ts` (orchestration) → `dispatch-adapter.ts`, `planner.ts` (execution planning) → `eval.ts`, `eval-corpus.ts`, `projection.ts` (analysis) → `template.ts`, `routine.ts`, `fixtures.ts` (management). No layer cycles: `run/*` never imports from `scheduler.ts`/`task-queue.ts`, while the scheduler imports `run` (scheduler.ts:11) but not vice versa. This is the scope I will sign off.

## Step 2 Threat and Failure Model

Two risk tags drive this review: **concurrency** and **persistence**. Concurrency surface: `WorkflowScheduler.start` is guarded by a per-run `KeyedSerialQueue` (scheduler.ts:26–31, used at scheduler.ts:48), so two concurrent `start()` calls for the same `runID` are serialized. Persistence surface: all run state lives in five SQLite tables (`workflow_run`, `workflow_phase`, `workflow_child`, `workflow_artifact`, `workflow_budget_ledger` in workflow.sql.ts:18–172) with appropriate cascade deletes; JSON columns store complex types (e.g. `spec_snapshot` at workflow.sql.ts:34, `budget_usage` at workflow.sql.ts:37). The real failure modes are (a) process death leaving a run in `running` with live children — addressed by `recoverInterrupted` (run/index.ts:408) and (b) budget overrun mid-phase — addressed by the fail-and-cascade logic in `run/budget.ts:108–186` plus the sibling cleanup in `dispatch-adapter.ts:107–125`. Boundary scan found no empty catches and no secrets/IO hotspots beyond the expected `SessionVerifications.loadWithIds` reads (eval.ts:187, run/internal.ts:485).

## Step 3 Correctness

I traced the budget-enforcement control flow end to end. `evaluateWorkflowBudget` (budget.ts:44) checks five limits via `checkLimit` (budget.ts:145–159) using strict `>` for exceeded and `>= warningRatio` (default 0.8) for warnings; the ratio guard is gated on `limit > 0` (budget.ts:157), so a zero-limit field cannot divide by zero — correct. `assertWorkflowBudgetAvailable` (budget.ts:109) throws `WorkflowBudgetExceededError` only on `exceeded`, not on `warning`, matching the contract. The run-level completion gate `evaluateCompletionGate` (run/internal.ts:347) blocks `completed` transitions when verification mode is `required` and either envelopes fail (run/internal.ts:354–359) or required artifacts are missing (run/internal.ts:361–367); the fallback at run/internal.ts:377–386 rejects the degenerate "required mode, no evidence at all" case. One correctness gap: `recoverInterrupted` (run/index.ts:408–449) only re-queues runs whose status is exactly `"running"` (run/index.ts:410, `interruptedRunStatuses = ["running"]`), so a run that crashed while `"blocked"` or `"paused"` is never recovered and its `running` children stay `running` forever; the `failed` array it returns (run/index.ts:422, 445) is also never populated — dead state that misrepresents the API. Rating: MEDIUM.

## Step 4 Performance

The dominant per-run cost is `appendBudgetUsage` (run/budget.ts:44). For each call that carries a `childID`, it recomputes the child's total usage by selecting **all** `WorkflowBudgetLedgerTable` rows for that child and reducing them with `addWorkflowBudgetUsage` (run/budget.ts:66–74). Over a run with `c` children each producing `k` ledger entries, that is O(c·k) per append and O(c·k²) cumulative — fine for the seeded fixtures (eval-corpus.ts:99–134, four findings) but a latent quadratic hot spot for long bug sweeps. `getDetail` (run/index.ts:159–193) issues four sequential `select().all()` queries and parses every row through zod; `WorkflowRunDetail.parse` at run/index.ts:192 then re-validates the whole graph a second time. `WorkflowTaskQueue.syncItem` (task-queue.ts:42–102) re-aggregates phase and run status from all children/phases on every queue event (task-queue.ts:128–167, 231–239) — O(n) per event, O(n²) per run. None of these block the seeded corpus, but they are the first things to revisit before raising `WORKFLOW_MAX_TOTAL_AGENTS` (spec.ts:8, currently 1000).

## Step 5 Design and Coupling

Layering is healthy: the scheduler depends on `run` and `planner` (scheduler.ts:10–11) but `run` never depends on the scheduler. The `WorkflowRun` namespace is composed by spreading the state namespace into the CRUD object (run/index.ts:453–454, `...WorkflowRunState`), which keeps the public surface stable but does mean `WorkflowRun.Info`, `WorkflowRun.Status`, etc. are re-typed twice (run/index.ts:471–488). `WorkflowDispatchAdapter.executePhase` (dispatch-adapter.ts:30–160) is the right abstraction seam between durable children (scheduler path) and direct dispatch (read-only path). Coupling concern: three independent helpers duplicate the same predicate — `isTerminalChildStatus` exists in `run/internal.ts:263`, `scheduler.ts:501`, and `task-queue.ts:227`; `isTerminalPhaseStatus` in `run/internal.ts:259` and `scheduler.ts:497`; `isCriticMergeStrategy` in `dispatch-adapter.ts:228` and `task-queue.ts:223`. Three or more identical call sites meets the dedup threshold; these belong in `run/internal.ts` (or a new `status.ts`). Rating: LOW (cleanup, not a defect).

## Step 6 Dead Code and Duplication

Confirmed dead/misleading: the `failed: WorkflowRunState.Info[]` array in `recoverInterrupted` (run/index.ts:422, returned at run/index.ts:445) is allocated but never written to — `recoverInterrupted` only ever recovers, never fails, so the field is always `[]`. Either remove it from the return shape or actually fail unrecoverable runs. Near-duplicate: `workflowVerificationEvidence` (eval.ts:165–205) and `verificationEnvelopeEvidence` (run/internal.ts:460–504) implement the same envelope-loading + pass/fail classification against the same `SessionVerifications.loadWithIds` API, differing only in how failures are stringified (eval.ts:181 vs run/internal.ts:476–478). The critic-phase-status aggregators (`criticPhaseStatusFromResults` dispatch-adapter.ts:220 and `aggregateCriticPhaseStatus` task-queue.ts:206) share the "critic is last child AND completed > half" rule but operate on different input types, so they are harder to merge — flagged, not actionable today. No unused exports spotted: `WorkflowBudgetExceededError` (budget.ts:138) is thrown by `assertWorkflowBudgetAvailable`; `WorkflowDispatchUnsupportedMergeStrategyError` (dispatch-adapter.ts:177) is thrown by `dispatchMergeStrategy` (dispatch-adapter.ts:192).
