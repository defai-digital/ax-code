## Step 2 Trust and capability boundaries

Plugin initialization deliberately grants a local client, project/worktree paths, a server URL, and a Bun-compatible shell through `PluginInput` at `packages/plugin/src/index.ts:26-33`; the runtime constructs that object with a sanitized process environment at `packages/ax-code/src/plugin/index.ts:49-61`. Tool plugins receive an abort signal plus a permission-request function whose permission, patterns, persistence choices, and metadata are explicit at `packages/plugin/src/tool.ts:3-27`. The shell contract admits a `{ raw: string }` expression at `packages/plugin/src/shell.ts:3-8`, so callers can intentionally bypass ordinary interpolation escaping; this is a capability boundary for trusted plugin code, not a safe evaluator for untrusted input. OAuth callbacks can return access and refresh credentials at `packages/plugin/src/index.ts:119-159`, making plugin loading and auth methods security-sensitive even though this package itself does not persist or log those values.

## Step 3 Correctness and failure behavior

The `tool` factory preserves the supplied description, Zod raw shape, and async executor unchanged, and attaches the same Zod namespace as `tool.schema` at `packages/plugin/src/tool.ts:29-38`. `packages/plugin/src/example.ts:4-17` demonstrates that contract with a required string argument and an executor that returns text. The runtime consumer turns `def.args` into `z.object`, adds the current directory/worktree to the execution context, awaits the plugin executor, and truncates large output at `packages/ax-code/src/tool/registry.ts:102-128`, which agrees with the declared shapes. Hook outputs are intentionally mutable objects, such as `chat.params` at `packages/plugin/src/index.ts:185-192` and tool results at `packages/plugin/src/index.ts:198-213`; runtime dispatch awaits each registered hook in order at `packages/ax-code/src/plugin/index.ts:161-173`, so later hooks observe earlier mutations.

The release path compiles first, rewrites source export targets to `dist`, packs, publishes discovered tarballs, and restores the manifest at `packages/plugin/script/publish.ts:17-33`. Restoration is not protected by `finally`, and the tarball scan accepts every `.tgz` in the package directory at lines 30-32. A failed pack/publish can therefore leave `package.json` rewritten, while a stale tarball can make the publish invocation ambiguous. This is a non-Critical release-operations hardening gap; it does not affect installed plugin execution.

## Step 4 Performance and concurrency

Most unit code is erased TypeScript contract surface. The runtime work in the package helper is constant-time because `tool` returns its input directly at `packages/plugin/src/tool.ts:29-35`; the example performs only string interpolation at `packages/plugin/src/example.ts:12-14`. The publish script loops over the small export map at `packages/plugin/script/publish.ts:20-27` and scans one package directory at lines 30-31. At consumption time, ordinary two-argument hooks are deliberately sequential at `packages/ax-code/src/plugin/index.ts:168-172`, preserving mutation order, whereas event callbacks are isolated with `Promise.allSettled` at lines 145-151. No candidate creates timers, queues, recursive traversal, or retained per-call state, so no package-local throughput or leak defect was found.

## Step 5 Architecture and ownership

The implementation follows that boundary: SDK entities are imported only as types at `packages/plugin/src/index.ts:1-16`, and executable code is limited to the Zod-backed identity helper in `packages/plugin/src/tool.ts:1-36` plus the release script. `PluginInput` supplies project context rather than reaching into runtime singletons at `packages/plugin/src/index.ts:26-35`. The manifest keeps the public entry points narrow at `packages/plugin/package.json:13-16`, although `BunShell` remains reachable structurally through the root declaration rather than as a separately exported subpath.
