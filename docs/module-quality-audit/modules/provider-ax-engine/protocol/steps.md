## Step 1 Scope and map

The unit is a flat directory of 20 TypeScript modules with a single barrel at `packages/ax-code/src/provider/ax-engine/index.ts:1-18` that re-exports every sibling. Ownership is split cleanly by concern: `constants.ts` is the single source of truth for the model catalog contract (with `AX_ENGINE_CATALOG_SOURCE` self-identifying at `constants.ts:92`), `platform.ts` answers "can this host run ax-engine", `dependency.ts` answers "is the binary present and new enough", `model-cache.ts` (867 LOC, the largest file) owns weight presence/prepare-state/disk, `server.ts` (656 LOC) owns the sidecar process lifecycle, `connection.ts` distinguishes managed vs attach mode, `download-job.ts`/`download-progress.ts` cover transfer orchestration and progress normalization, `install.ts` covers the managed binary installer, `lifecycle.ts` maps the rich status into the shared cross-product phase set, and `catalog.ts`/`status.ts`/`prepare.ts`/`provider-loader.ts` are the aggregators that compose the pieces. No circular import was observed: the dependency direction is `constants → {platform,paths,python,hf-cache,download-progress,model-card} → {dependency,model-cache,server,connection,install} → {catalog,status,prepare,download-job,delete} → provider-loader`.

## Step 2 Threat and failure model

The unit handles bearer credentials, remote fetches, process spawning, and recursive filesystem deletion, so the boundary review focused there. Attach mode is locked to loopback: `connection.ts:39-41` rejects any non-local hostname (and explicitly `0.0.0.0`), and `connection.ts:33-35` refuses embedded `user:pass@` URLs or query/fragment suffixes. Live model-card fetches use `redirect: "error"` (`model-card.ts:127`) so a compromised or redirecting endpoint cannot pivot a fetch. The binary installer refuses to run without a pinned SHA-256 and an `https://` URL (`install.ts:215-222`) and routes the download through `Ssrf.pinnedFetch` (`install.ts:265`); the comment at `install.ts:210-214` explicitly notes that ad-hoc `codesign --verify` is not a countermeasure to a network attacker. The server spawner sanitizes the inherited environment before injecting `AX_ENGINE_API_KEY` (`server.ts:584-587`), so the child does not inherit arbitrary parent secrets. Deletion is fenced: `delete.ts:120-125` (`isEligibleDeleteTarget`) only permits paths under `AxEnginePaths.models` or HF snapshots, and `delete.ts:166-171` refuses to delete a path that overlaps the currently-loaded server model. The managed-venv resolver in `python.ts:25` and `python.ts:34` double-checks `Filesystem.contains` so a weird `$HOME` cannot turn a venv lookup into an escape. API-key size/validity is bounded at `connection.ts:159` (rejects NUL bytes and >16 KiB).

## Step 3 Correctness of public surfaces

The hot control flow holds up under scrutiny. In `download-job.ts:124-134` the orchestrator re-reads `job.status as AxEngineModelJobStatus` after the await to defeat TypeScript control-flow narrowing that would otherwise hide a concurrent cancel landing a late successful download as "complete"; the same cancellation signal is checked against `controller.signal.aborted`. The `finally` at `download-job.ts:152-158` only deletes the map entry when `jobs.get(key) === job`, so a superseding start that replaced the key cannot be evicted and made uncancellable. Progress is monotonic by construction: `applyProgressEvent` (`download-progress.ts:46-62`) takes `Math.max(previous.percent, capped)` and caps incomplete work at 99 (`RUNNING_PERCENT_CAP`), so only the orchestrator's `completeProgress` after exit-code validation publishes 100. `server.ts:296-312` re-checks `processExited()` immediately after each health probe so a child that dies while the final probe is in flight is classified as `process-exited` rather than intermittently reported as `AX_ENGINE_SERVER_HEALTH_FAILED`. The `contextMatches` comparison at `server.ts:504` normalizes both sides with `?? undefined` so a zod-optional `undefined` vs absent field does not spuriously force a relaunch. `lifecycle.ts:107-115` explicitly handles the empty-candidate case so a fully-prepared-but-idle host maps to `starting`/`missing_model` instead of falsely surfacing as needing a re-download. `getModelStatus` (`model-cache.ts:336-373`) collects per-candidate inspect errors and prefers them over a generic "not prepared" message, keeping EACCES/permission failures actionable.

## Step 4 Performance and resource behavior

The aggregators fan out with `Promise.all`: `catalog.ts:194-199` runs eligibility/dependency/jobs/server concurrently, and `catalog.ts:209-212` parallelizes the per-model `getModelStatus` + `getDiskStatus`. The download path polls the HF cache every 2 s (`model-cache.ts:558-579`) only while progress is below 85% and stops once the engine's own events take over, avoiding a permanent timer. `directorySize` (`model-cache.ts:119-146`) dedupes by `realpath` so a symlink-farm snapshot's blobs are counted once, not once per link. Server starts are coalesced per-process via `inflightEnsure` (`server.ts:457-483`) keyed on the full server identity, which prevents two concurrent `getModel` calls (main completion + prompt-title) from spawning two multi-GB servers; the cross-process `server.lock` serializes distinct models. The legacy-copy reclaimer runs at most once per process via the `reclaimStarted` guard (`provider-loader.ts:30-35`), keeping the directory scan off the hot path. Process termination in `server.ts:217-231` escalates SIGTERM→SIGKILL and waits for exit before returning, so a respawn never leaves two model servers transiently resident. The binary installer uses an in-process single-flight keyed by version (`install.ts:184`, `install.ts:309-313`) so concurrent UI clicks share one install.

## Step 5 Design and ownership boundaries

Layering is healthy and the "no upward import" rule holds. Each module owns one resource: `paths.ts` owns on-disk locations, `hf-cache.ts` owns HF hub cache resolution, `model-cache.ts` owns prepare-state + completion markers + the download subprocess, `server.ts` owns the sidecar pid, `install.ts` owns the managed binary, `delete.ts` owns HF snapshot blob accounting. The shared cross-product lifecycle contract (`lifecycle.ts:8-30`) is kept as literal string phases so AX Code / AX Studio / ax-engine docs stay in lockstep, and `status.ts:48-49` attaches the derived lifecycle to the rich status without coupling the core fields to the phase enum. Runtime injection seams are explicit and uniform: `AxEngineDownloadJobRuntime` (`download-job.ts:37-42`), `AxEnginePrepareRuntime` (`prepare.ts:27-34`), `AxEngineInstallRuntime` (`install.ts:45-51`) all default to the real implementations but accept overrides, which is what makes the cancellation/eligibility/disk logic testable without a real engine. The provider loader (`provider-loader.ts:44-60`) keeps a module-level `activeServerBaseURL` and rewrites outgoing fetches when `ensureServer` fell back to a non-default port — necessary because the OpenAI-compatible SDK is constructed once against the default port but the real address lives in server state.

## Step 6 Dead code, hygiene, and intentional gaps

No empty `catch` blocks were found (the audit's 0/0 column is accurate). The many `().catch(() => undefined)` sites are intentional best-effort filesystem cleanup (e.g. `delete.ts:101`, `delete.ts:114`, `server.ts:131`, `install.ts:164`, `install.ts:176-178`) and are paired with the destructive operation they protect. `AX_ENGINE_BINARY_RELEASE` is deliberately `undefined` (`constants.ts:73`) with a multi-line rationale: the managed binary installer is disabled until a self-contained archive exists, but the `install.ts` surface is still wired through `isAxEngineInstallable`/`getManagedBinary`/`installAxEngineBinary` and consumed by `dependency.ts:109-137`, so it is reachable forward-compat code, not dead code. The `downloadMode: "mtp"` branch in `downloadModel` (`model-cache.ts:697-701`) is retained so adding an MTP-packaged catalog entry later works without a type-narrowing false error — also documented forward-compat, not dead. `parseProgressJsonLine` is exported from `download-progress.ts:91` and consumed at `model-cache.ts:528`. I did not find unreachable exports or orphaned helpers.
