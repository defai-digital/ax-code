## Step 3 Validation and ordinary correctness

Both mutations validate `requestID` before extracting the branded value (`question.ts:53-55` and `question.ts:95-96`). Reply additionally validates the JSON shape at `question.ts:54` and then checks it against the live question definitions. The dynamic validator enforces answer-count equality (`question.ts:125-127`), trims values and rejects whitespace-only entries (`question.ts:133-137`), rejects duplicate selections (`question.ts:138-141`), enforces single-select cardinality (`question.ts:142-145`), and checks option membership when custom values are disabled (`question.ts:146-152`). ## Step 4 Concurrent settlement correctness

There is a Medium-severity time-of-check/time-of-use defect in both mutation routes. Reply lists and finds the request at `question.ts:57-58` before calling `Question.reply` at line 73; reject separately lists and checks at lines 97-98 before calling `Question.reject` at line 105. The underlying functions do not report whether they applied: an absent entry only logs and returns at `packages/ax-code/src/question/index.ts:238-244` and `question/index.ts:254-260`, while the handlers unconditionally return `true`. If two requests pass the pre-check, both can report 200; if both reach the entry before `Question.ask` removes it in its deferred `finally` (`question/index.ts:231-235`), duplicate or contradictory `question.replied`/`question.rejected` events can be published at lines 245–251 and 261–266. If cleanup wins first, the losing operation silently does nothing but still returns 200. The sibling permission implementation documents this exact retry race and solves it by returning an applied boolean (`packages/ax-code/src/permission/index.ts:418-460`) that its route checks (`packages/ax-code/src/server/routes/permission.ts:34-47`). Question settlement should likewise atomically claim/delete the entry and return an outcome.

## Step 5 Cost and scaling behavior

Pending state is an in-memory `Map` scoped by `Instance.state` at `packages/ax-code/src/question/index.ts:163-173`. `Question.list` copies all entries with `Array.from` at lines 269–272, so listing is O(p) in pending requests. Reply then scans that copied array with `find` (`question.ts:57-58`) and reject scans it with `some` (`question.ts:97-98`), adding another O(p) pass before an O(1) map lookup. Answer validation is O(values + option labels), using bounded arrays and per-question sets at `question.ts:128-155`. There is no database, filesystem, network fan-out, or unbounded recursion in the unit, and normal interactive workloads keep p small; no performance finding is warranted. The atomic settlement change from Step 4 would also remove the redundant full-list pre-check.

## Step 6 Ownership and dependency design

Responsibilities are mostly well placed. The route owns Hono/OpenAPI translation and HTTP error envelopes (`question.ts:11-108`), the `Question` namespace owns schemas, deferred state, and bus events (`packages/ax-code/src/question/index.ts:15-173`), and shared route helpers own branded parameter extraction (`packages/ax-code/src/server/routes/route-params.ts:44-70`). The request-dependent answer checks cannot be represented by the body schema alone because they require the live `Request.questions`, so keeping the adapter-level validation near `question.ts:121-157` is reasonable. The design gap is the settlement API: `Question.reply` and `Question.reject` expose no success result and leave deletion to the waiting promise's later `finally` (`question/index.ts:231-267`). Moving atomic claim/delete plus a boolean result into the state owner would give every caller one correct contract and match the proven permission design at `permission/index.ts:418-460`.

## Step 7 Maintainability and error hygiene

The route has no empty catch blocks, disabled branches, or TODO markers, and its imports at `question.ts:1-9` are all used. Validation failures use the shared structured envelope rather than throwing raw details (`question.ts:70-72`; `packages/ax-code/src/server/error.ts:260-278`), and unexpected exceptions are normalized and logged by the server handler at `packages/ax-code/src/server/server.ts:155-165`. One Low-severity documentation defect remains: the comment at `question.ts:111-114` says `validateQuestionAnswers` returns a string or null, but the actual signature at lines 121–124 and returns at lines 125–156 use a discriminated `{ ok, ... }` object. That stale contract was left behind when normalization support changed the return type and should be corrected to prevent misleading future edits.
