## Step 1 — Map

The unit covers `desktop/packages/web/server/lib/ui-auth/` — 4 files, ~1484 LOC. The primary file I read is `ui-auth.js` (649 LOC) exporting `derivePasswordBinding` (261-262) and `createUiAuth` (309-649). `createUiAuth` is a factory returning an auth middleware/controller object with `requireAuth` (474-484), session lifecycle handlers (`handleSessionStatus` 486-494, `handleSessionCreate` 496-526), passkey handlers (533-596), `handleResetAuth` (598-622), `ensureSessionToken` (643-646), and `dispose` (624-628). The companion `ui-passkeys.js` (527 LOC, 1 export `createUiPasskeys`) is imported at ui-auth.js:6 and instantiated at 378. Auth uses JWT (HS256 via `jose` `SignJWT`/`jwtVerify`, 2) with a per-install secret from `getOrCreateJwtSecret()` (271-295) persisted to `~/.config/openchamber/jwt-secret` (mode 0o600, 288). Password verification uses `scryptSync` + `timingSafeEqual` (374, 432-433). Rate limiting is in-memory (`loginRateLimiter` Map, 18) with per-IP (10 attempts/5min) and no-IP (3 attempts/5min) tiers, a 15-min lockout (108-123), and an `unref`'d cleanup interval (184-191). Cookies are built with `HttpOnly` + `SameSite=Strict` always, `Secure` when the request is HTTPS (236-252). When no password is configured, the factory returns a disabled-mode object (312-371) where `requireAuth` is a pass-through and session handlers return errors.

## Step 2 — Threat model

This unit is the loopback HTTP server's authentication boundary for the Desktop web UI — the asset is unauthorized access to the local server (which proxies project files, terminal, git, etc.). The dominant defense is the password + JWT-session model: `handleSessionCreate` (496-526) rate-limits (497), verifies the password via `scryptSync`+`timingSafeEqual` (513, constant-time), records failures (514), clears on success (520), and issues a JWT cookie (522-524). The rate limiter is the anti-brute-force boundary — 10 attempts/5min per IP with a 15-min lockout (108-114), and a stricter 3-attempt tier when no IP is resolvable (`rate-limit:no-ip`, 41-46) since the loopback server may not always have a meaningful client IP. The JWT secret boundary: `getOrCreateJwtSecret` (271-295) prefers env (`AX_CODE_JWT_SECRET`), then reads the persisted file, then generates+persists a 32-byte hex secret with `mode: 0o600` (285-288) — so a fresh install gets a strong secret, and the file is owner-only readable. Cookie defense: `HttpOnly` prevents JS access (237), `SameSite=Strict` prevents CSRF (237), and `Secure` is set only on HTTPS (247-249) — appropriate since the loopback server is typically HTTP (setting `Secure` on HTTP would drop the cookie). The `handleResetAuth` path (598-622) has a specific guard: it refuses to clear passkeys when `AX_CODE_JWT_SECRET` is env-pinned (606-610), because `rotateJwtSecret()` would throw a 400 _after_ `clearAllPasskeys()` already persisted an empty store — the inline comment at 600-605 documents this exact destructive-before-failing race that was fixed. The `isSecureRequest` helper trusts `x-forwarded-proto` (204-208) which is correct for a reverse-proxied deployment but could be spoofed if the server were directly exposed — acceptable given the loopback trust model.

## Step 3 — Correctness

Key invariants: (1) password verification is constant-time — `scryptSync(candidate, salt, 64)` then `timingSafeEqual(candidateHash, expectedHash)` (ui-auth.js:432-433), with a `try/catch` returning false on any crypto failure (434-436); (2) sessions are JWT-signed with HS256 and expiry (`SignJWT.setExpirationTime`, 453-457), validated by `jwtVerify` (444) which checks signature + expiry; (3) `requireAuth` (474-484) short-circuits OPTIONS preflight (475-477), checks the cookie token via `isSessionValid` (479), clears the cookie on failure (482), and returns 401 with JSON or text per `Accept`/path (464-472); (4) rate limiting uses an in-process lock chain (`acquireRateLimitLock`, 53-58) to serialize concurrent attempts per key — preventing a thundering-herd bypass where parallel requests all read the count before any increments; (5) the disabled-mode (no-password) branch (312-371) correctly makes `requireAuth` a pass-through but returns 400 for all mutation handlers, so a server started without a configured password cannot create sessions but is openly accessible — this is the documented "password not configured" degraded state; (6) `dispose` (624-628) clears the rate limiter, stops the cleanup timer, and disposes the passkey controller — correct teardown. The `handleResetAuth` env-pinned guard (606-610) is the most subtle correctness fix: it prevents the half-destructive state where passkeys are deleted but the JWT secret (and thus existing sessions) remain valid. The rate-limiter `try/catch` blocks around `get`/`set`/`delete` (68-78, 92-97, 110-114, 143-155) all `console.error` and continue (fail-open for availability) — logged, not silent.

## Step 4 — Performance

Auth checks run on every authenticated request via `requireAuth` → `jwtVerify` (ui-auth.js:444), which is a fast symmetric HMAC verify (~microseconds for HS256) — negligible per-request overhead, no hot-path concern. Password verification on login uses `scryptSync` (432) which is intentionally CPU-heavy (memory-hard KDF) — but logins are low-frequency and rate-limited, so the cost is acceptable and correct for brute-force resistance. The `scryptSync` in `derivePasswordBinding` (262) is called at factory time (376) and on JWT rotation (382-389), not per-request. The rate limiter is an in-memory `Map` with O(1) `get`/`set`/`delete` per key; the cleanup interval (184-191) runs hourly (`RATE_LIMIT_CLEANUP_MS = 1h`, 15) iterating all keys — O(keys) but bounded by distinct client IPs (small on a loopback server) and `unref`'d so it does not keep the process alive. The `acquireRateLimitLock` promise-chain (53-58) serializes per-key but does not block cross-key attempts. No unbounded growth: `loginRateLimiter` is bounded by distinct IPs and cleaned hourly; the passkey store is disk-backed (ui-passkeys.js). No caching of JWT validations (each request re-verifies) — correct for security (immediate revocation on secret rotation). No performance finding.

## Step 5 — Design

The factory pattern `createUiAuth({ password, cookieName, sessionTtlMs })` (ui-auth.js:309) cleanly encapsulates all auth state behind a returned object — good closure-based encapsulation. The disabled-mode branch (312-371) returning a structurally-compatible but no-op object is a sound null-object pattern: callers do not need to branch on whether auth is enabled. The rate-limiter is well-factored into `checkRateLimit`/`recordFailedAttempt`/`clearRateLimit`/`cleanupRateLimitRecords` with the per-IP vs no-IP tier split (40-51) reflecting the real deployment constraint (loopback without meaningful client IP). One mild design smell: the rate-limiter state (`loginRateLimiter`, `rateLimitLocks`, `rateLimitCleanupTimer`) is module-level (18-21) rather than enclosed in the factory, meaning multiple `createUiAuth` calls would share state — acceptable because the server creates one auth instance, but it makes the factory less pure and harder to test in isolation. The JWT-secret lifecycle (`getOrCreateJwtSecret`/`persistJwtSecret`/`rotateJwtSecret`, 271-307, 386-390) correctly handles env-pin vs file-persist and the rotation-rebuilds-passkey-controller dependency (380-390). Cookie building (236-252) is explicit and sets all recommended attributes. The passkey controller is delegated to `ui-passkeys.js` with a clean `createUiPasskeys({ passwordBinding })` contract.
