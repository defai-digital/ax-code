# Nine-step review: memory

## Step 1 Map and boundaries

The `memory` unit owns project/global memory persistence, project scanning, curated-entry mutation, applicability, recall/evaluation, diagnostics, and system-prompt rendering. Its public barrel is `packages/ax-code/src/memory/index.ts:12-44`; durable shapes are defined at `packages/ax-code/src/memory/types.ts:5-69`. Project state is stored at `<project>/.ax-code/memory.json` and global state under the test-home or user home (`packages/ax-code/src/memory/store.ts:15-20`). User-visible callers include the CLI commands in `packages/ax-code/src/cli/cmd/memory.ts:47-60`, session prompt injection at `packages/ax-code/src/session/system.ts:254-265`, and app-context warmup/clear routes at `packages/ax-code/src/server/routes/app-context.ts:123-179`. There are no native, network, database, subprocess, event, or generated-code pieces in this unit.

```text
CLI / tool / app-context route -> generator or recorder -> store -> memory.json
session prompt -> injector -> applicability -> project/global store
evaluation -> recall -> applicability -> project/global store
```

## Step 2 Threat and failure model

The principal assets are user-curated rules/preferences, their project/global scoping metadata, and the integrity of system-prompt delimiters. Recorder input crosses CLI and model-tool boundaries; the tool requires `memorywrite` permission before persisting (`packages/ax-code/src/tool/memory.ts:37-82`), while `recordEntry` rejects blank names/bodies and invalid confidence/expiry values (`packages/ax-code/src/memory/recorder.ts:145-178`). Store parsing distinguishes missing files from corrupt data and propagates corruption rather than replacing it (`packages/ax-code/src/memory/store.ts:199-216`). Prompt rendering escapes literal wrapper tags in curated entry fields (`packages/ax-code/src/memory/injector.ts:13-29`) and filters expired/agent/path-scoped entries at lines 44-55. Scanned repository-controlled text is rendered without the same escaping at lines 130-151, so README/config content remains an untrusted prompt input even though it sits inside the memory wrapper. Failure modes reviewed were partial writes, stale cache reads, concurrent lost updates, corrupt JSON, oversized or invalid legacy data, stale scans, silent scanner degradation, and scoped content leaking into an inapplicable prompt.

## Step 3 Correctness and concurrency

The normal mutation invariant is load, replace/remove by case-insensitive name, recompute tokens/hash/timestamp, then atomically save (`packages/ax-code/src/memory/recorder.ts:145-217`). Recorder mutations share both an in-process write lock and cross-process file lock (`packages/ax-code/src/memory/recorder.ts:128-135`); `Filesystem.write` uses a temporary file plus rename (`packages/ax-code/src/util/filesystem.ts:83-115`). Cached reads re-stat, coalesce only matching in-flight reads, verify metadata after reading, and decode a fresh object on every call (`packages/ax-code/src/memory/store.ts:123-180`, `208-216`). Applicability composes expiry, exact agent allow-list, all-tag matching, and containment-aware glob candidates (`packages/ax-code/src/memory/applicability.ts:20-66`). A residual race remains across the public warmup workflow: `generate` loads the old snapshot before asynchronous scanning (`packages/ax-code/src/memory/generator.ts:255-278`), but CLI and server callers save the returned snapshot later without the recorder lock (`packages/ax-code/src/cli/cmd/memory.ts:92-114`; `packages/ax-code/src/server/routes/app-context.ts:140-146`). Atomic rename prevents torn JSON but does not serialize that read-modify-write sequence. A concurrent `recordEntry` can therefore persist a new curated entry during the scan and have it overwritten by warmup's older snapshot.

## Step 4 Performance and resource bounds

Prompt-loop loading is intentionally live, but the store avoids repeated disk reads with an mtime/size cache capped at 32 paths and an in-flight-read map whose entries are removed in `finally` (`packages/ax-code/src/memory/store.ts:86-115`, `157-179`). Prompt building copies and sorts each entry section (`packages/ax-code/src/memory/injector.ts:36-55`), while recall performs a linear scan and then sorts collected results (`packages/ax-code/src/memory/recall.ts:60-86`, `89-142`). Those costs are modest for intended files, but `RecordInput` and the persisted Zod schema impose no entry-count or string-size ceiling (`packages/ax-code/src/memory/recorder.ts:67-90`; `packages/ax-code/src/memory/store.ts:23-67`), and curated entries may exceed `maxTokens`. Warmup parallelizes four scanners (`packages/ax-code/src/memory/generator.ts:267-278`), caps traversal depth and ignores common generated directories at lines 78-118, then truncates output at lines 289-310; the directory listing is accumulated before truncation, so a very wide tree still incurs full scan allocation. No timer, listener, stream, or process-lifetime queue is owned here.

## Step 5 Design and ownership

The module follows `packages/ax-code/ARCHITECTURE.md:11-23`: domain behavior stays under `src/memory`, while the CLI and server remain adapters. Types, applicability, hash rendering, storage, mutation, recall, diagnostics, evaluation, and prompt rendering have distinct files rather than being folded into the interface layer. Shared policy is mostly centralized: `entryApplies` serves injector and recall (`packages/ax-code/src/memory/applicability.ts:62-67`), and `computeContentHash` serves generator and recorder (`packages/ax-code/src/memory/hash.ts:37-49`). One ownership seam is incomplete: persistence serialization is private to `recorder.ts`, so the generate-plus-save warmup transaction cannot reuse it. A domain-level `warmup` operation owning lock, reload/merge, and save would keep that invariant out of both CLI and route adapters.
