## Step 1 Scope and map

The `project` unit is two sub-layers fused under one directory. The identity/persistence layer holds: `schema.ts:7` (branded `ProjectID` plus the `global` sentinel at `schema.ts:9`), `project.sql.ts:5` (the Drizzle `project` table with JSON-typed `sandboxes`/`commands` columns), `project.ts:18` (the 504-LOC `Project` namespace: discovery, persistence, migration, icon discovery, sandbox CRUD), and `project-identity.ts:5` (worktree-duplication queries used by the worktree-remove UI flow). The runtime/lifecycle layer holds: `instance.ts:196` (the ALS-context `Instance` object, lifecycle event emitter, dispose/reload), `state.ts:4` (a generic per-root memoization primitive with dispose hooks), `bootstrap.ts:79` (`InstanceBootstrap` startup orchestration), and `vcs.ts:9` (git branch tracking via the file watcher).

Exports reconcile with MODULE-AUDIT §1 (40 public exports across the eight files; the audit's sample list matches what I read at `project.ts:21`–`503` and `instance.ts:196`–`404`). No stray files in the directory, no XL filter applied.

## Step 2 Threat and failure model

The `persistence` risk tag is the right lens. The fail-prone surfaces I traced by reading control flow:

1. `Project.fromDirectory` performs filesystem walks, up to three `git` subprocess invocations, a best-effort cache write to `.git/ax-code`, and a Drizzle upsert — in that order (`project.ts:183`–`262` for discovery, `project.ts:242` for the cache write, `project.ts:299`–`330` for the upsert). The cache write is wrapped in `.catch(() => undefined)` (`project.ts:242`), so a read-only `.git` does not abort discovery; that is intentional and commented.
2. `migrateGlobalSessionsToProject` (`project.ts:136`–`150`) re-parents legacy global sessions. It is invoked from `project.ts:333` via `Database.use((d) => migrateGlobalSessionsToProject(...))` — i.e. **not** inside `Database.transaction`. Each matching row is updated in its own `db.update(...).run()` inside the `for` loop (`project.ts:145`–`148`). A crash mid-loop leaves a partially-migrated set. Re-running `fromDirectory` re-runs migration (the call is unconditional on the non-global branch), so it is eventually consistent, but there is a window of inconsistency and no atomicity guarantee.
3. `State.create` stores the result of `init()` synchronously (`state.ts:46`–`50`) and attaches a rejection handler that evicts a failed Promise from the cache (`state.ts:55`–`63`). A Promise that neither resolves nor rejects (stuck LSP initialize) is **not** evicted by this path; it is bounded only by the 5 s per-entry dispose cap (`state.ts:18`, exercised by `test/project/state.test.ts:190`–`217`).
4. `Instance.disposeAll` (`instance.ts:342`–`403`) disposes instances serially inside one async IIFE; errors are pushed to an array and only the first is re-thrown (`instance.ts:377`–`382`). Other disposal errors are logged at most once via `Log.Default.warn` (`instance.ts:356`) and then discarded — acceptable for teardown but worth noting for post-mortem debugging.
5. `bootstrap.ts` runs most services through `background(...)` / `fireAndForget(...)` (`bootstrap.ts:70`–`77`, calls at `bootstrap.ts:109`–`174`). A init failure surfaces only as `Log.Default.warn` (`bootstrap.ts:33`); the tracked variants additionally capture a `runtimeSnapshot` on failure/timeout (`bootstrap.ts:55`–`67`). Recovery is observability-only.

No secret-bearing surfaces in this unit. `Instance.directory` / `Instance.worktree` are the only boundary-crossing values and they are path strings already scoped inside the instance ALS context.

## Step 3 Correctness — control flow of the public surface

- `Project.fromDirectory` (`project.ts:442` → `fromDirectoryPromise` at `project.ts:178`) walks `Filesystem.up({ targets: [".git"] })` and branches four ways: no `.git` → directory-hash id with `fakeVcs` (`project.ts:191`–`197`); `.git` but no `git` binary → cached id or `ProjectID.global` (`project.ts:203`–`210`); `git rev-parse --git-common-dir` failure → same fallback (`project.ts:213`–`220`); otherwise derive id from `git rev-list --max-parents=0 HEAD`, sorted, first root (`project.ts:232`–`240`). The multi-root case takes the lexicographically-smallest root SHA — deterministic but undocumented; no test covers it.
- The upsert at `project.ts:299`–`330` uses `onConflictDoUpdate` and writes `time_initialized: result.time.initialized`. Because `result = { ...prev, ... }` (`project.ts:283`–`288`) and `prev` is the parsed existing row (`project.ts:266`), a previously-set `initialized` timestamp survives a later `fromDirectory` call. Correct.
- **Correctness gap (MEDIUM):** the project-row upsert (`project.ts:299`, one `Database.use`) and `migrateGlobalSessionsToProject` (`project.ts:333`, a separate `Database.use`) are two distinct database interactions with no enclosing transaction. A process exit between them leaves a persisted project row whose legacy global sessions have not yet been re-parented. The next `fromDirectory` call re-runs migration (the branch at `project.ts:332` is gated only on `data.id !== ProjectID.global`), so the system is eventually consistent — but the contract "project row exists ⇒ its sessions are claimed" does not hold instantaneously. Wrapping both writes in a single `Database.transaction` would close the window.
- `Project.addSandbox` / `removeSandbox` (`project.ts:405`–`440`) both use `Database.transaction((d) => ...)` and re-read the row inside the transaction before mutating. Safe under SQLite's serial writer model; `test/project/project.test.ts:596`–`609` asserts the transaction is actually used.
- `parseRow` / `safe` / `fromRow` (`project.ts:57`–`107`): sub-field parse failures (vcs, sandboxes, commands) log a warning and fall back to safe defaults (`project.ts:65`, `70`, `76`); a whole-row Zod failure logs and returns `undefined` (`project.ts:93`), which `fromRow` escalates to a throw (`project.ts:102`) and `list()` silently drops via `flatMap` + `safe` (`project.ts:456`). The asymmetry is intentional — `list()` must not crash the UI on one bad row — but a dropped row is only observable via a warn log.
- `Instance.provide` (`instance.ts:197`) caches `Promise<Shape>` per resolved directory; the `track()` wrapper deletes the cache entry only on rejection (`instance.ts:187`–`194`). Concurrent first-callers share the in-flight boot Promise. Correct.
- `Instance.containsPath` (`instance.ts:241`–`249`) special-cases `worktree === "/"` to avoid the legacy sentinel matching every absolute path. The branch is documented inline (`instance.ts:244`–`247`); it is correct but encodes a historical data shape in a hot path.
- `State.create` (`state.ts:32`) keys entries by `(root(), init)` where `init` is the function reference. Two distinct `Instance.state(...)` callsites with distinct arrow functions get distinct entries. The rejection-eviction path guards against a concurrent `invalidate()` + re-init clobber via identity check `current.state === state` (`state.ts:59`). Correct.
- `Vcs` state init (`vcs.ts:35`–`72`) subscribes to `FileWatcher.Event.Updated` and filters on `evt.properties.file.endsWith("HEAD")` (`vcs.ts:58`). This also matches any file whose name ends in `HEAD` (e.g. `NOTMYHEAD`); a `path.basename(file) === "HEAD"` check would be tighter.

## Step 4 Performance

- `Project.list` (`project.ts:450`) is a full-table `select().all()` with an in-process `flatMap(safe)` filter. N is the number of distinct repos the user has ever opened (small in practice); acceptable.
- `Project.fromDirectory` issues up to three `git` subprocess calls (`git rev-parse --git-common-dir`, `git rev-list --max-parents=0 HEAD`, `git rev-parse --show-toplevel`) plus two `.git/ax-code` reads (`project.ts:201`, `228`). `git rev-list --max-parents=0 HEAD` in a very large monorepo can traverse many commits; LOW concern, runs once per instance boot.
- `ProjectIdentity.listWorktreeIdentities` (`project-identity.ts:11`–`25`) is a single LEFT JOIN + GROUP BY + count(SessionTable.id). Performance depends on the `session.project_id` index; the query is correct and bounded.
- `State.dispose` fans out all dispose hooks concurrently via `Promise.all` with a 5 s per-entry cap (`state.ts:103`–`119`). `Instance.disposeAll` then serializes across instances (`instance.ts:352`), so worst-case teardown is `instances × max(state-entries-per-instance) × 5 s`. For the typical 1–3 instances this is fine; a host with many cached instances could see slow shutdown.
- `Project.discover` (`project.ts:347`–`365`) globs the whole worktree for `favicon.*` and base64-encodes the shortest match. It is fire-and-forget (`project.ts:275` `void discover(...).catch(...)`) and gated by `Flag.AX_CODE_EXPERIMENTAL_ICON_DISCOVERY` (`project.ts:274`), so it does not block the request path; the glob cost is paid once in the background.

## Step 5 Design

- The `Project` namespace (504 LOC) co-locates identity discovery, persistence, migration, icon discovery, and sandbox CRUD. The mix is dense but cohesive around "everything about a project row." Splitting discovery (`fromDirectory` + git logic) from CRUD (`update`, `addSandbox`, `removeSandbox`, `setInitialized`) would improve readability but is not forced — the call graph stays internal to the namespace.
- `Instance` (`instance.ts:196`) is a clean ALS-context anchor: `Shape` (`instance.ts:16`–`20`) is the minimal context object; `provide` / `current` / `bind` / `state` / `runtime` form a small, well-named surface. `Instance.state` (`instance.ts:259`–`261`) delegates to `State.create(() => Instance.directory, ...)`, cleanly decoupling the generic memoization primitive from the instance concept.
- `State` (`state.ts:4`) is a genuinely reusable primitive (keyed by `(root, init)` with optional dispose and a `Getter.invalidate()` escape hatch). The `invalidate()` contract is documented with a concrete consumer example (`state.ts:22`–`27`, referencing `Provider.invalidate()` and issue #13).
- `bootstrap.ts` ordering is intentional and commented: TaskQueue recovery awaited first (`bootstrap.ts:81`–`108`), then Plugin/LSP/DiagnosticCorrelation in parallel (`bootstrap.ts:114`–`130`), provider warmup moved out of the prompt loop to avoid first-message hang (`bootstrap.ts:131`–`139` with the explanatory comment), then LSP prewarm with bounded file/language caps (`bootstrap.ts:140`–`154`). Good ordering discipline.
- `ProjectID` branded-string typing (`schema.ts:3`–`10`) prevents accidental mixing with plain strings; the `global` sentinel is the one escape hatch and is consistently checked at `project.ts:332` and `project-identity.ts` call sites.
- One design wrinkle: `fakeVcs` is parsed from `Flag.AX_CODE_FAKE_VCS` at module load (`project.ts:152`). The flag is meant for dev/test, so read-once semantics are acceptable, but it does mean the value is frozen at first import of `project.ts`.

## Step 6 Dead code and hygiene

- No empty catches and no TODOs in any of the eight files (matches MODULE-AUDIT §1). The `.catch(() => undefined)` sites (`project.ts:175` `readCachedProjectId`, `project.ts:242` cache write, `project.ts:275` discover) are intentional best-effort and commented.
- `runtimeLog.info("runtime snapshot", { ..., snapshot: result })` (`instance.ts:82`–`87`) logs the full snapshot including `services`, `tasks`, `queues`. Diagnostic-only; verbose at info level but not incorrect.
- Type erosion is minimal and localized: `State.Entry.state: unknown` + `dispose?: (state: any) => Promise<void>` (`state.ts:6`–`7`) — required because the dispose hook signature varies per caller; `Instance.bind<F extends (...args: any[]) => any>` (`instance.ts:255`) preserves the return type while accepting any args, documented as the ALS re-entry primitive.
- `disposeAll` performs the `cache.get(key) !== value` guard twice (`instance.ts:353` and `instance.ts:366`). Belt-and-suspenders against concurrent mutation during the async loop, not dead code.
- `normalizeSandboxDirectory` (`project.ts:117`–`123`) has a try/catch fallback to `Filesystem.windowsPath` — a Windows-compatibility shim, intentional.

## Step 7 Tests

Coverage is strong and well-targeted. `test/project/project.test.ts` (625 LOC) exercises: fromDirectory across git/no-git/commit/subdir/worktree cases (`project.test.ts:93`–`341`), ID stability across calls and separate clones (`project.test.ts:131`–`136`, `275`–`292`), malformed-row recovery in `get`/`list`/`fromDirectory` (`project.test.ts:511`–`562`), sandbox transaction usage with a `vi.spyOn(Database, "transaction")` assertion (`project.test.ts:596`–`609`), and icon discovery success/non-image paths (`project.test.ts:343`–`372`). `test/project/migrate-global.test.ts` explicitly pins the migration regression — including the "row already exists" case (`migrate-global.test.ts:80`–`102`) and the "don't steal from unrelated directories" guard (`migrate-global.test.ts:147`–`164`). `test/project/state.test.ts` covers caching, isolation, dispose-on-reload, concurrent-init dedup, `invalidate()` semantics, and the 5 s stuck-dispose cap (`state.test.ts:190`–`217`). `test/project/instance-context.test.ts` covers lifecycle event sequences (`instance-context.test.ts:39`–`61`), bound async callbacks, runtime snapshots, and boot-failure events for unprintable errors (`instance-context.test.ts:63`–`98`). `test/project/vcs.test.ts` covers branch read + HEAD-change event (skipped in CI without native @parcel/watcher). `test/project/worktree-remove.test.ts` covers worktree removal failure recovery.

Gaps: (a) the multi-root git case (`git rev-list --max-parents=0 HEAD` returning ≥2 SHAs, handled at `project.ts:232`–`240`) has no test; (b) `InstanceBootstrap` (`bootstrap.ts:79`) is not unit-tested directly — the TaskQueue recovery loop at `bootstrap.ts:84`–`106` (requeued + scheduled restart) is non-trivial and only exercised indirectly through end-to-end runs; (c) the non-atomic migration window identified in Step 3 has no regression test that crashes between the two `Database.use` calls (such a test is hard to write without instrumentation but is the gap that lets the MEDIUM finding persist undetected).
