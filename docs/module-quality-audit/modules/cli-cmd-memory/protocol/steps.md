## Step 2 Threat and failure boundaries

This CLI can write or delete project memory and the user-level global store. The scope choice is made at `packages/ax-code/src/cli/cmd/memory.ts:238-253` for remember and at `packages/ax-code/src/cli/cmd/memory.ts:156-176` for clear; the resolved paths are `.ax-code/memory.json` under the project or home directory at `packages/ax-code/src/memory/store.ts:15-20`. Eval intentionally accepts a user-supplied cases path and reads it at `packages/ax-code/src/memory/evaluation.ts:85-90`. No shell command, network request, credential, or environment value is constructed by this module. Destructive behavior is restricted to the explicit `clear` subcommand, although there is no confirmation prompt. Store writes are atomic (`packages/ax-code/src/memory/store.ts:182-196`) and non-ENOENT deletion errors propagate (`packages/ax-code/src/memory/store.ts:219-239`), preventing a false success after permission or I/O failures.

## Step 3 Correctness and input validation

The public kind names are consistently translated to storage kinds at `packages/ax-code/src/cli/cmd/memory.ts:15-20`, and remember forwards all optional metadata at `packages/ax-code/src/cli/cmd/memory.ts:238-253`. Downstream validation rejects blank names/bodies, out-of-range confidence, and invalid expiry dates at `packages/ax-code/src/memory/recorder.ts:108-121` and `packages/ax-code/src/memory/recorder.ts:145-176`. Two numeric boundaries are weaker. Warmup declares `--max-tokens` and `--depth` as unrestricted numbers at `packages/ax-code/src/cli/cmd/memory.ts:70-79`; `generate` consumes them unchanged and persists `maxTokens` at `packages/ax-code/src/memory/generator.ts:255-257` and `:314-322`, so negative values can produce an empty scan with invalid negative metadata. Recall and eval similarly accept any numeric limit at `packages/ax-code/src/cli/cmd/memory.ts:334-337` and `:498-502`. A limit of zero or less becomes unlimited in `packages/ax-code/src/memory/recall.ts:86`, while eval retains that value as its reported k at `packages/ax-code/src/memory/evaluation.ts:91-105`, making output such as `Recall@0` at `packages/ax-code/src/cli/cmd/memory.ts:539-541` semantically false.

## Step 4 Efficiency and resource behavior

Warmup performs its four independent scans concurrently with `Promise.allSettled` at `packages/ax-code/src/memory/generator.ts:267-278`, and the token budget loop is bounded to four scanned sections at `packages/ax-code/src/memory/generator.ts:296-310`. Recall is linear in stored entries and sorts the accumulated matches at `packages/ax-code/src/memory/recall.ts:60-86`; output is also linear at `packages/ax-code/src/cli/cmd/memory.ts:376-385`. For `scope=all`, project and global files are loaded sequentially at `packages/ax-code/src/memory/recall.ts:64-72`; this is a minor latency opportunity, not a material CLI bottleneck. Clear performs an existence check followed by a separate unlink at `packages/ax-code/src/cli/cmd/memory.ts:156-176`, even though `store.clear` already returns false for ENOENT at `packages/ax-code/src/memory/store.ts:225-239`. That extra syscall also creates a harmless race in which a concurrently removed file is still reported as successfully cleared.
