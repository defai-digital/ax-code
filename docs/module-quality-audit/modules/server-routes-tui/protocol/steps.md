## Step 3 Input validation wiring

Body schemas are applied through the project-local `validator` wrapper (`server/validation.ts:4-14`), which delegates to `hono-openapi`'s `openApiValidator` and converts a failed `result.success` into `invalidRequest(c)` (HTTP 400). Three payload-bearing endpoints use a real zod schema: `/append-prompt` validates `TuiEvent.PromptAppend.properties` (`tui.ts:54`, schema at `event.ts:6`), `/show-toast` validates `TuiEvent.ToastShow.properties` (`tui.ts:218`, schema at `event.ts:32-40`), and `/execute-command` validates `z.object({ command: z.string() })` (`tui.ts:192`). The remaining five `executeCommand` routes correctly omit validators because they accept no body. The wrapper's `as never` cast at `validation.ts:14` is a typing escape hatch worth noting but does not weaken runtime checks.

## Step 4 Publish-endpoint union discriminator and the null-guard fix

The `/publish` handler (`tui.ts:224-275`) is the most complex surface. Its validator builds `z.union(Object.values(TuiEvent).map(def => z.object({ type: z.literal(def.type), properties: def.properties }).meta({ ref: "Event." + def.type })))` at `tui.ts:242-256`, discriminating the four event types (`tui.prompt.append`, `tui.command.execute`, `tui.toast.show`, `tui.session.select`) defined in `event.ts:5-47`. The handler then re-derives the definition with `Object.values(TuiEvent).find(d => d.type === evt.type)` (`tui.ts:263`). The comment at `tui.ts:259-262` documents that this `find` previously fed a non-null assertion straight into `Bus.publish` and crashed when the type did not match; the explicit `if (!def)` guard at `tui.ts:264-267` now returns a 400 `invalidRequest` with `details.resource: "tuiEvent"` and emits `log.warn("unknown tui event type", …)`. Because the union's `type` field is a `z.literal`, the untyped branch is unreachable in practice, but the defensive guard is correct and matches the project pattern of never trusting an unchecked lookup.

## Step 5 SessionSelect authorization paths

Two routes can drive a session navigation: `/select-session` (`tui.ts:276-301`) and `/publish` with `type: "tui.session.select"` (`tui.ts:268-271`). Both funnel through `requireCurrentProjectSession` (`server/routes/session-lookup.ts:16-22`), which calls `Session.get(sessionID)` and throws `HTTPException(409, …)` via `Session.isCompatibleWithCurrentProject` when the session belongs to another project directory. The `/publish` branch additionally re-parses with `TuiEvent.SessionSelect.properties.parse(evt.properties)` at `tui.ts:269` before extracting `properties.sessionID`; this is redundant with the union validator (which already validated `properties` against the same schema) but is a safe defensive parse and does not change behavior. The sessionID flows to `Bus.publish` at `tui.ts:272` and `tui.ts:298` using the validated value, not a raw body field, so there is no path-trimming or substitution risk on this field.

## Step 6 OpenAPI error-response fidelity gaps

`errors(...codes)` (`server/error.ts:363-364`) attaches canned error response entries to each operation. Several declarations under-document what the handler can actually emit. `/select-session` declares `errors(400, 404)` at `tui.ts:291`, but `requireCurrentProjectSession` can throw `HTTPException(409)` (`session-lookup.ts:19-21`), so a 409 is reachable but missing from the spec; the same 409 path applies to `/publish`, which only declares `errors(400)` at `tui.ts:239` and also omits the 404 that `Session.get` raises for an unknown id. Conversely, `/show-toast` (`tui.ts:201`) applies a validator but does not declare `errors(400)` at all, so its OpenAPI entry lacks the bad-request response that `validation.ts:11` can produce. These are documentation/SDK-fidelity gaps, not runtime defects — the centralized `appErrorEnvelope` (`server/error.ts:242-254`) still serializes whatever the handler throws — but they will produce drift between the generated SDK and observed behavior. Severity: MEDIUM.

## Step 7 Command surface asymmetry and duplication

`TUI_COMMAND_MAPPINGS` at `tui.ts:14-27` is a closed map of twelve external command names to internal `session.*`/`agent.cycle` strings. The `/execute-command` handler enforces this allow-list at `tui.ts:195-196`, returning 400 for anything unmapped. However, the same internal channel is reachable without that restriction through `/publish` with `type: "tui.command.execute"`: the `CommandExecute` schema (`event.ts:7-31`) is `z.union([z.enum([…15 values]), z.string()])`, so the trailing `z.string()` branch accepts arbitrary command strings. `/execute-command` therefore exposes only twelve curated commands while `/publish` can submit any string to the same bus topic. This is intentional flexibility on the bus side (the TUI consumer ultimately decides what to do), but it means the strictness of `/execute-command` is advisory rather than a true security boundary. Additionally, the enum at `event.ts:11-27` and the map at `tui.ts:14-27` are two sources of truth that must be updated together; commands like `prompt.clear`, `prompt.submit`, `session.list`, `model.list`, `theme.switch`, and `help.show` appear in `event.ts` but are deliberately absent from the map because they are reached via dedicated routes. Severity: LOW (design note).
