## Step 2 Inspect Trust and Secret Boundaries

Remote connections validate the configured URL before transport construction and replace the SDK fetch with an SSRF-pinned implementation (`packages/ax-code/src/mcp/impl.ts:575-596`); explicit authentication repeats the public-URL check before starting OAuth (`packages/ax-code/src/mcp/impl.ts:1284-1293`). Local servers receive a sanitized parent environment plus only the explicitly configured overlay after process-injection variables are stripped (`packages/ax-code/src/mcp/impl.ts:712-734`, `packages/ax-code/src/util/env.ts:64-99`), and child stderr is redacted and capped at 2,000 characters (`packages/ax-code/src/mcp/impl.ts:41-41`, `:735-742`). Persisted access tokens, refresh tokens, client secrets, and PKCE verifiers are encrypted before the mode-0600 auth file is written (`packages/ax-code/src/mcp/auth.ts:54-85`, `:120-145`). Startup and explicit connect both require an `McpTrust` decision before process or network creation (`packages/ax-code/src/mcp/impl.ts:339-343`, `:875-884`).

## Step 3 Trace State Transitions and Disposal Races

Startup records disabled and trust-gated entries, creates the remaining clients concurrently, and closes any client whose connection completes after disposal (`packages/ax-code/src/mcp/impl.ts:317-377`). Teardown marks state disposed before closing registered clients and invalidating the tool cache (`packages/ax-code/src/mcp/impl.ts:379-401`); `connectImpl` likewise checks disposal both before and after `create()` and closes a late result (`packages/ax-code/src/mcp/impl.ts:886-905`). A real gap remains in `add`: it captures state, awaits `create`, and then writes the returned client at `packages/ax-code/src/mcp/impl.ts:487-520` without checking `s.disposed`. If instance disposal wins that await, the disposer sees no new client and `add` subsequently installs a live client into dead state. This is a non-Critical resource-leak/race candidate, and the missing guard is conspicuous beside the protections at lines 360-367 and 899-905.

## Step 4 Evaluate Concurrency and Work Bounds

Same-name add, connect, disconnect, and untrust operations are serialized by `KeyedSerialQueue` (`packages/ax-code/src/mcp/impl.ts:837-856`, `:934-978`), whose implementation preserves parallelism across different keys and removes settled tails (`packages/ax-code/src/util/queue.ts:92-122`). Remote and local connects and the initial `listTools` request use configurable or default deadlines (`packages/ax-code/src/mcp/impl.ts:598-605`, `:744-747`, `:796-808`), and tool enumeration fans out across connected clients while coalescing concurrent callers (`packages/ax-code/src/mcp/impl.ts:988-1038`). Discovery also runs candidate checks concurrently (`packages/ax-code/src/mcp/discovery.ts:273-305`). One Low inefficiency remains: the Playwright `check` invokes `discoverPlaywrightCandidate`, then `resolve` invokes it again (`packages/ax-code/src/mcp/discovery.ts:229-242`), repeating project, executable, and CDP probes for a detected candidate despite the nearby single-resolution commentary.

## Step 5 Assess Responsibility Boundaries

Transport selection, connection status, cache invalidation, trust transitions, and OAuth orchestration are cohesively owned by `MCP` in `packages/ax-code/src/mcp/impl.ts:487-530`, `:855-980`, and `:1264-1519`. Credential persistence remains in `McpAuth`, including URL binding for stored material (`packages/ax-code/src/mcp/auth.ts:93-108`), while the OAuth provider adapts those records to the SDK (`packages/ax-code/src/mcp/oauth-provider.ts:62-88`, `:107-183`). The callback module owns its loopback listener, waiter cap, and five-minute expiry (`packages/ax-code/src/mcp/oauth-callback.ts:63-102`, `:205-245`). Discovery is used only on the CLI listing path and templates only on interactive add (`packages/ax-code/src/cli/cmd/mcp-impl.ts:102-115`, `:640-715`), so neither is entangled with automatic connection state. The separation is understandable, though the 1,553-line implementation remains a large concentration of lifecycle policy.

## Step 6 Review Failure Semantics and Logging Hygiene

Discovery failures intentionally collapse to unavailable results after killing a still-running probe (`packages/ax-code/src/mcp/discovery.ts:41-63`), while malformed or absent project metadata is only a negative web-project signal (`packages/ax-code/src/mcp/discovery.ts:94-119`). Connection creation records actionable failed status rather than silently omitting a server (`packages/ax-code/src/mcp/impl.ts:345-357`), closes failed or unused transports (`packages/ax-code/src/mcp/impl.ts:612-618`, `:637-691`), and turns tool-list failure into client removal and closure (`packages/ax-code/src/mcp/impl.ts:1023-1050`). A second non-Critical concern is that local startup failure logs the complete configured command array at `packages/ax-code/src/mcp/impl.ts:759-765`; the CLI accepts a free-form command line at `packages/ax-code/src/cli/cmd/mcp-impl.ts:725-736`, so a credential supplied as an argument can enter logs even though stderr is redacted. Command logging should redact credential-like arguments or avoid echoing the full array.
