## Step 2 Trust boundaries and failure model

Queue identifiers, optional session filters, state changes, executable payloads, priorities, and positions cross the request boundary. The route validates IDs with the branded `TaskQueueID.zod` schema (`task-queue.ts:13,36-38`), caps list requests at 500 (`task-queue.ts:15-19`), and delegates malformed-input responses to the shared validator, which returns `invalidRequest` on failed parses (`packages/ax-code/src/server/validation.ts:4-12`). Upstream middleware can require a process-local runtime token or configured Basic Auth (`packages/ax-code/src/server/server.ts:166-182`), rejects cross-origin browser mutations (`server.ts:183-195`), and establishes the requested project `Instance` before route dispatch (`server.ts:258-277`). The listener itself is restricted to loopback addresses by `packages/ax-code/src/runtime/listen-security.ts:27-31`. The principal assets are durable queue integrity and the ability to launch prompts, commands, shell work, or workflow children through send-now.

## Step 3 Validation and ordinary correctness

The HTTP adapter consistently validates before dispatch: list parses query input before `TaskQueue.list` (`task-queue.ts:60-63`), enqueue parses `TaskQueue.EnqueueInput` before insertion (`task-queue.ts:83-86`), every item route validates `:taskID`, and edit/reorder additionally validate JSON bodies (`task-queue.ts:152-154,258-261`). `OptionalQueryNumber` rejects non-finite and unsafe integer forms before applying the positive integer limit (`packages/ax-code/src/server/routes/query.ts:15-27`), while `JsonNumber`-backed priority and position schemas accept JSON-compatible numeric forms but retain integer/range constraints (`task-queue.ts:32-34`; `packages/ax-code/src/session/task-queue.ts:69-87,103-114`). The storage owner rechecks schemas, session/project compatibility, and state-specific action preconditions (`session/task-queue.ts:288-290,333-365,472-499,723-727`). These layers make the non-racing request paths coherent and project-scoped.

## Step 4 Concurrent mutation correctness

There is a Medium-severity race between send-now and an already-starting executor. `TaskQueueExecutor.sendNow` first awaits `TaskQueue.sendNow` and only then calls `start` (`packages/ax-code/src/session/task-queue-executor-impl.ts:82-85`). The storage operation reads and validates the old state, then unconditionally rewrites the row to `queued` in a later transaction (`packages/ax-code/src/session/task-queue.ts:677-701`). A concurrent `start` can atomically claim that same row as `running` at `session/task-queue.ts:406-434` and schedule detached work at `task-queue-executor-impl.ts:117-123`; send-now can then overwrite it back to `queued` and its subsequent `start` can claim a second execution. The keyed lock only wraps each `start` claim sequence (`task-queue-executor-impl.ts:99-124,137-153`), not the preceding `TaskQueue.sendNow` mutation or detached execution lifetime. Pause has the analogous stale-check pattern at `session/task-queue.ts:472-475`: a claim between `get` and `setStatus` can leave actively executing work marked paused. State-changing updates need compare-and-set predicates (or the same lock around the complete action) to prevent duplicate or contradictory execution.

## Step 5 Cost and scaling behavior

List work is bounded at the HTTP layer to 500 rows (`task-queue.ts:15-19`), and the database query uses project/session/status filters plus ordered positions (`packages/ax-code/src/session/task-queue.ts:288-310`). Supporting indexes cover project-position, project-status, and session lookups (`packages/ax-code/src/session/session.sql.ts:132-165`). Reorder is O(q): it loads every row for the project and may update every changed position (`session/task-queue.ts:640-674`). Send-now is also O(q), incrementing every other project row and publishing an update for each shifted item (`session/task-queue.ts:681-700`). Enqueue is not capped, so repeated reorder/send-now calls can become costly for an unusually large retained queue; however, the operations are local SQLite transactions and normal interactive queues are small. This is a scaling caveat, not a separate severity finding for this route.

## Step 6 Ownership and API design

The basic separation is sound: the route owns Hono/OpenAPI translation (`task-queue.ts:40-280`), `TaskQueue` owns schemas, persistence, project checks, events, and transition helpers (`packages/ax-code/src/session/task-queue.ts:17-131,232-249,368-520`), and `TaskQueueExecutor` owns executable-item claiming, serialization, watchdogs, and detached completion (`packages/ax-code/src/session/task-queue-executor-impl.ts:65-135,156-251`). One boundary is not actually enforced: the route calls the unrestricted `TaskQueue.setStatus` for an “Internal lifecycle hook” (`task-queue.ts:112-136`) after checking only the fixed literal header declared at lines 27–31. OpenAPI publishes that exact value as `const: "1"` (`packages/sdk/openapi.json:2764-2795`), and the generated SDK exposes it directly in `taskQueue.status` (`packages/sdk/js/src/gen/sdk.gen.ts:1452-1485`). This Medium-severity design flaw lets any ordinary API client bypass pause/resume/cancel/retry preconditions and assign arbitrary terminal or active states. Internal lifecycle mutation should be removed from the public contract or protected by a real process-internal capability.

## Step 7 Error contracts and code hygiene

The candidate file has no catch blocks, TODO markers, disabled branches, or unused-looking imports; handlers remain thin and unexpected errors are normalized by the server-level handler (`packages/ax-code/src/server/server.ts:155-165`). A Low-severity OpenAPI drift remains: edit correctly declares 409 (`task-queue.ts:145-150`), but pause, resume, cancel, retry, and send-now declare only 400/404 (`task-queue.ts:163-168,180-185,197-202,214-219,232-237`) even though `assertActionStatus` throws 409 (`packages/ax-code/src/session/task-queue.ts:723-727`). List/enqueue can also return 409 for a session from another project (`session/task-queue.ts:177-183,288-290,333-335`), and get/reorder/delete can return 409 from project ownership checks (`session/task-queue.ts:232-237,368-375`). Generated client error unions therefore under-document reachable responses. The declared response maps should include 409 wherever these calls can propagate it.

## Step 9 Findings and exit decision

Primary review registered four items: (1) **Medium — send-now can race an existing claim and launch duplicate detached execution**, evidenced by `session/task-queue.ts:406-434,677-701` and `task-queue-executor-impl.ts:82-124`; (2) **Medium — the public status operation exposes its fixed “internal” header and permits unrestricted lifecycle assignment**, evidenced by `task-queue.ts:27-31,112-136`, `packages/sdk/openapi.json:2764-2795`, and `packages/sdk/js/src/gen/sdk.gen.ts:1452-1485`; (3) **Low — reachable 409 responses are absent from multiple OpenAPI response maps**, evidenced by `task-queue.ts:57-58,80-81,127,167,184,201,218,236,255,275` against `session/task-queue.ts:177-183,232-237,723-727`; and (4) **Low — action/concurrency/contract branches lack direct route tests**, evidenced by the covered cases at `task-queue-routes.test.ts:14-550`. The pre-existing ledger contains no accepted entry (`docs/module-quality-audit/modules/server-routes-task-queue/MODULE-AUDIT.md:60-64`), and `findings/` was empty during review. No Critical or High item was found, so the Critical-only `protocol/reverify.md` artifact is not required. The nine review steps are complete and ready for independent `ax-code-glm` verification.
