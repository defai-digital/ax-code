## Step 3 Correctness of the reply path

The POST handler (`permission.ts:32-48`) is the load-bearing piece of this unit. It captures the _applied_ outcome of `Permission.reply(...)` at `permission.ts:39` (`const applied = await Permission.reply(...)`), then branches on it at `permission.ts:40`: when `applied === false` it returns a 404 via `notFound(c, {...})` with the `PermissionUnavailableError` envelope (`permission.ts:41-46`); otherwise it returns `c.json(true)` at `permission.ts:47`. The inline comment at `permission.ts:34-38` documents exactly why the pre-call pendingness check is insufficient (a concurrent reply for the same `requestID` — e.g. a client retry after a timed-out first attempt — can resolve the request in the gap between a pre-check and the reply call). The contract is real: `Permission.reply` returns `Promise<boolean>` (`permission/index.ts:675-677`) and the underlying `replyPromise` returns `false` only when the pending entry is absent (`permission/index.ts:427-428`) or already deleted under the `always` mutex (`permission/index.ts:464`). The handler does not synthesize success for a no-op.

## Step 4 Concurrency and race review

`server-routes-permission` does not itself touch shared state, so its own concurrency posture is delegated. But the route interacts with three independent concurrency mechanisms inside the Permission module that the reviewer must confirm are not violated by the HTTP surface: (1) the per-instance `state()` map (`permission/index.ts:181-199`) which owns `pending`; (2) the per-instance `alwaysReplyQueue` mutex serializing `"always"` replies (`permission/index.ts:178`, `212-224`); (3) the cross-process `FileLock.acquire(\`${Database.Path}.permissions\`)` at `permission/index.ts:475` protecting the read-modify-write of the approved-ruleset row. Because the route simply awaits `Permission.reply` and reports its boolean, two simultaneous HTTP POSTs for the same `requestID` are safe: the first to win the `pending.delete` returns `true`; the second sees `pending.delete(...) === false` and the route surfaces 404. This matches the explicit test in `packages/ax-code/test/server/route-validation.test.ts:594-625`, which POSTs to `/permission/${PermissionID.ascending()}/reply`for a never-asked ID and asserts the 404`PermissionUnavailableError` envelope. No TOCTOU was introduced at the route layer.

## Step 5 Performance and resource shape

Both endpoints are O(1) in route code. `GET /` calls `Permission.list()` which in turn calls `listPromise()` (`permission/index.ts:531-534`) — a synchronous `Array.from(pending.values(), item => item.info)` over the in-memory pending map. It performs no DB I/O and no async wait on the network, so the GET handler is effectively constant-time in the size of pending requests and does not block on the file lock. The POST handler awaits `Permission.reply`, which for `"always"` replies acquires the file lock and a DB transaction (`permission/index.ts:475-495`); this is unavoidable persistence work owned by the module, not the route. There is no N+1, no unbounded loop, no allocation growth attributable to this file. The `lazy()` wrapper (`util/lazy.ts:7-33`) memoizes the Hono instance so the route table is built once per process.

## Step 6 API design and contract consistency

The OpenAPI metadata is well-formed: each route declares a unique `operationId` (`permission.reply` at `permission.ts:17`, `permission.list` at `permission.ts:55`), summaries, descriptions, and response schemas via `resolver(...)`. The POST route documents 200/400/404 (`permission.ts:18-29`) using the shared `errors(400, 404)` helper from `error.ts:363`.
