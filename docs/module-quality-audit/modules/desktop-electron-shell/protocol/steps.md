## Step 1 — Map

The `desktop-electron-shell` unit covers the Electron main-process shell/window and host-configuration helpers in `desktop/packages/electron/src`. I read 21 of the unit's files in full. The shell/window surface groups into four clusters: (a) boot + window chrome — `desktop-boot-outcome.js` (10 LOC) is a factory returning `{ target: "local", status: "ok" }` (lines 3-6) for preload injection; `desktop-window-title.js` (17 LOC) sanitizes renderer-supplied titles via `sanitizeDesktopWindowTitle` (5-12), stripping C0/DEL controls and capping length to `MAX_DESKTOP_WINDOW_TITLE_LENGTH = 160` (3); `desktop-dialog.js` (57 LOC) builds sanitized `openFile`/`openDirectory` Electron dialog options via `buildDesktopOpenDialogOptions` (3-39) and resolves the owning window via `resolveDesktopDialogOwnerWindow` (41-52). (b) Filesystem + capture policy leaf helpers — `desktop-read-file-policy.js` (64 LOC) with `DENIED_SEGMENTS` (6-24), `DENIED_BASENAMES` (25), and `assertDesktopReadFileAllowed` (36-59); `desktop-browser-capture-policy.js` (15 LOC) scoping capture to a host-owned webview (`isDesktopBrowserCaptureTargetForSender`, 3-11); the contract test `desktop-capture-page-policy.test.mjs` (55 LOC) verifies the `desktop_capture_page_rect` command stays `safeForRemote: false`. (c) Host configuration — `desktop-hosts.js` (223 LOC), the largest unit-owned file, exposing URL normalization (`normalizeHostUrl`, 5-19), loopback detection (`isLoopbackDesktopHostname`, 26-29), local-sender classification (`isLocalDesktopSenderUrl`, 31-46), target-allow matching (`targetMatchesHostUrl`, 60-77, and `isAllowedDesktopHostTargetUrl`, 79-87), local-only config gating (`isLocalOnlyDesktopHostsConfigInput`, 89-94), remote-access key purging (`removeDisabledRemoteAccessSettingsFromRoot` + `DISABLED_REMOTE_SETTINGS_KEYS`, 96-116), client-token storage (`sanitizeClientTokenForStorage`, 50-53; `resolveStoredClientTokenForUrl`, 118-131), and the read/apply round-trip pair `readDesktopHostsConfigFromRoot` (133-155) and `applyDesktopHostsConfigToRoot` (157-210). (d) LAN + file-search + cache helpers — `desktop-lan-address.js` (92 LOC) with `isUsableLanIPv4Address` (6-20), `selectLanIPv4Address` (22-31), UDP-routed detection (`detectRoutedIPv4Address`, 33-74), and the public `detectLanIPv4Address` (76-85); `desktop-file-search.js` (23 LOC) with `toNativeSearchRelativePath` (5-7) and `shouldIncludeNativeSearchEntry` (9-18); `external-url.js` (28 LOC) with `normalizeSafeExternalUrl` (13-24); `installed-apps-cache.js` (31 LOC) with `normalizeInstalledAppsCache` (9-27). The large `main.js` (2767 LOC) wires these helpers but is not the focus of this shell-helpers unit.

## Step 2 — Threat model

This unit sits at the trust boundary between the untrusted Electron renderer and the privileged main process, but the dominant risk here is **data integrity of host configuration and credential hygiene** rather than capability exposure (capability allowlisting belongs to the sibling `desktop-electron-security` unit). Concrete assets: (1) `desktop-hosts.js` persists remote host URLs and `clientToken` bearer secrets — `sanitizeClientTokenForStorage` (50-53) trims/returns null, and `readDesktopHostsConfigFromRoot` defaults to `includeSecrets: false` (133) so tokens are omitted from renderer-facing round-trips unless explicitly requested; the round-trip preservation logic in `applyDesktopHostsConfigToRoot` (157-210) must NOT carry a token across a URL change (test at `desktop-hosts.test.mjs:212-277` proves this). (2) `normalizeHostUrl` (5-19) strips `username`, `password`, `search`, `hash` before any storage or comparison, blocking credential leakage in URLs and query-string token bleed. (3) `isAllowedDesktopHostTargetUrl` (79-87) is the navigation allowlist — renderer-initiated window navigations and fetches must be confined to `localOrigin` plus declared host URLs (the optional `includeApiUrls` flag at 79 is the only path by which API URLs become navigation-legal). (4) `removeDisabledRemoteAccessSettingsFromRoot` (107-116) is the "remote access disabled" kill switch — it must delete `desktopHosts`, `desktopLocalClientToken`, `desktopSshInstances`, `desktopLanAccessEnabled`, `desktopUiPassword`, `publicOrigin`, etc.; a miss leaks a credential or keeps a stale remote endpoint reachable. (5) `desktop-read-file-policy.js` is defense-in-depth for filesystem reads (covered more fully in the security unit). (6) `external-url.js` rejects `file:`, `javascript:`, userinfo-bearing, and control-char-bearing URLs before `shell.openExternal`. (7) `desktop-lan-address.js` chooses the address advertised to LAN clients — selecting a `0.0.0.0`/`169.254.x`/`127.x` would misbind or leak.

## Step 3 — Correctness

I traced the control flow of each public export against its tests. (1) `applyDesktopHostsConfigToRoot` correctly preserves the existing `clientToken` only when the renderer omits the field AND both URL and apiUrl are unchanged (`desktop-hosts.js:170-184`); the `existingApiUrl === apiUrl` guard at 182 prevents token carryover on API-only endpoint change (verified by `desktop-hosts.test.mjs:245-277`). When the renderer explicitly passes `clientToken: ""`, the entry omits the key (`desktop-hosts.js:180-181`, 191; test at `desktop-hosts.test.mjs:185-210`). (2) `targetMatchesHostUrl` (60-77) normalizes trailing slashes via `normalizePathForHostMatch` (55-58) and treats host path `/` as a prefix match (72) — so `https://remote.example.com/app` matches `https://remote.example.com/app/session/abc` but not `https://remote.example.com/app2` (73, tested at `desktop-hosts.test.mjs:279-315`). (3) `isLocalDesktopSenderUrl` (31-46) only returns true when the URL port equals `serverPort` (37) or matches `devRendererUrl` origin (38-41); `0.0.0.0` and `::` are correctly rejected because `isLoopbackDesktopHostname` (26-29) only permits `localhost`, `::1`, and `127.0.0.0/8`. (4) `normalizeHostUrl` (5-19) returns null for non-http(s) (10) and clears userinfo/query/hash (11-14); this is what makes `readDesktopHostsConfigFromRoot` token-safe by default. (5) `detectRoutedIPv4Address` (33-74) uses a `settled` latch (40, 43) so the promise resolves exactly once even if both the `error` handler and the `connect` callback fire; `socket.close()` is wrapped in try/catch (45-49). (6) `normalizeInstalledAppsCache` (`installed-apps-cache.js:9-27`) correctly treats a future `updatedAt > nowSecs` as stale (20, tested at `installed-apps-cache.test.mjs:42-57`), preventing a corrupted future timestamp from freezing the cache forever. (7) `buildDesktopOpenDialogOptions` (`desktop-dialog.js:3-39`) defaults `directory: false` to `openFile` (8-10), filters out filter rows with empty extensions (23-31), and trims title/defaultPath only when non-empty (17-22). (8) `isDesktopBrowserCaptureTargetForSender` rejects same-sender, destroyed webContents, and non-webview targets before checking `hostWebContents === senderWebContents` (`desktop-browser-capture-policy.js:4-10`). No correctness defect found.

## Step 4 — Performance

All helpers in this unit are synchronous, in-memory gate/normalization functions with no IO on the hot path except `detectLanIPv4Address`/`detectRoutedIPv4Address`. Cost profile: `normalizeHostUrl` parses a single `URL` per call (5-19) — `targetMatchesHostUrl` parses two URLs (66-67) and is invoked once per host per `isAllowedDesktopHostTargetUrl` call via `Array.some` (83-86), bounded by host list size (typically <5). `readDesktopHostsConfigFromRoot`/`applyDesktopHostsConfigToRoot` iterate the host list twice (read-then-merge) on config writes, which are infrequent (settings round-trip), not per-IPC. `detectRoutedIPv4Address` (33-74) opens one UDP socket, performs a connect (no packets sent — UDP connect only sets the routing entry), reads `socket.address()`, and closes synchronously in the callback; the `settled` latch and `socket.once("error")` ensure the socket does not leak past resolution. `detectLanIPv4Address` (76-85) prefers the routed path and falls back to `selectLanIPv4Address(networkInterfaces())` (84) only on failure — `os.networkInterfaces()` is a single syscall returning a small map. `isUsableLanIPv4Address` (6-20) is a 4-octet regex + range check; `selectLanIPv4Address` (22-31) iterates interface entries linearly. `assertDesktopReadFileAllowed` is `Array.some` over ~17 segments plus a `Set.has` (`desktop-read-file-policy.js:46, 52`) — O(1)-ish per read. `sanitizeDesktopWindowTitle` and `buildDesktopOpenDialogOptions` run only on user-initiated title set / dialog open. No unbounded allocation, no tight-loop allocation, no measurable event-loop blocking.

## Step 5 — Design

The unit's design follows a clean "small pure helper module + thin Electron-side wiring" pattern, and the helper split is well-factored: `desktop-hosts.js` is the one substantive module (223 LOC) and concentrates all host-config and token-storage invariants in one file with a consistent `sanitize*ForStorage` / `normalize*` / `isAllowed*` naming convention, making the trust boundary easy to audit. Good cohesion: each file owns a single concern (boot outcome, dialog options, capture scoping, host config, LAN detection, file search, read policy, title sanitization, external URL, app cache). The dependency-injection seams are correct and minimal: `pathTools` (`desktop-read-file-policy.js:27, 37`; `desktop-file-search.js:5`), `createSocket`/`networkInterfaces`/`connectHost`/`connectPort` (`desktop-lan-address.js:33-37, 76-81`), and `options.home`/`options.tmp` (`desktop-read-file-policy.js:38-39`) make the modules unit-testable cross-platform without monkey-patching Node builtins. One mild design note: `desktop-boot-outcome.js` returning a hard-coded `{ target: "local", status: "ok" }` is effectively a constant factory — the test at `desktop-boot-outcome.test.mjs:15-21` defends this as "fresh object per call so renderer code cannot mutate a shared singleton," which is a defensible reason to keep it a factory rather than a frozen constant. `installed-apps-cache.js` returns a derived `{ apps, hasCache, isCacheStale }` shape rather than mutating input — clean. No over-abstraction, no premature factory hierarchy, and no layering violation toward `desktop/packages/web` or `packages/ax-code`.

## Step 6 — Dead code / hygiene

The only registered finding is `AUDIT-desktop-electron-shell-empty-catch` (silent-error, Low, deferred to 2026-09-11, codex-sol verifier) documenting 5 empty-catch sites: `main.js:1646`, `main.js:1656`, `main.js:2168`, `server-process.js:51`, `startup-diagnostics.js:51` — these live in the large wiring files outside the helper modules I read, and the finding carries explicit per-site disposition (4 review-needed, 1 accepted-missing-ok). Within the shell helpers themselves, the two empty catches are both deliberate and locally justified: `normalizeHostUrl`'s `} catch { return null }` at `desktop-hosts.js:16` swallows `URL` parse failure as a normalized "invalid input" sentinel (the whole function returns null on any malformed input, which is its contract); `detectRoutedIPv4Address`'s `} catch { /* ignore */ }` at `desktop-lan-address.js:47` guards `socket.close()` after resolution (a double-close or already-closed socket must not throw the resolve path). The `hasUrlControlCharacter` byte loop in `external-url.js:5-11` is a defensive header-injection guard, not dead code. No TODO/FIXME markers in any file I read. No unreachable branches: the `hasApiUrl`/`hasClientToken` `Object.hasOwnProperty` checks in `applyDesktopHostsConfigToRoot` (`desktop-hosts.js:171-184`) are required to distinguish "field absent" from "field explicitly empty," which is load-bearing for the token-clearing behavior tested at `desktop-hosts.test.mjs:185-210`.

## Step 7 — Tests

Every shell helper has a companion `.test.mjs` and the coverage is substantive, not token-vital. Highlights: `desktop-hosts.test.mjs` (357 LOC) covers URL-credential stripping (47-74), token omission by default vs. `includeSecrets` (76-121), token resolution across host and API URL path-prefix matches (123-144), token preservation across renderer round-trips (146-183), explicit-empty token clearing (185-210), and the critical no-token-carryover-on-endpoint-change cases for both URL and apiUrl (212-277). `desktop-read-file-policy.test.mjs` exercises Windows drive-letter case-insensitivity (9-17), sibling-path rejection (19-27), post-normalization secret-dir denial (29-37), and a multi-target credential-store sweep (49-61). `desktop-lan-address.test.mjs` injects a socket factory to assert the `settled` latch closes the socket on both success and connect-error paths (57-70). `desktop-capture-page-policy.test.mjs` reads the `desktop-ipc-contract.json` and asserts `desktop_capture_page_rect` stays `safeForRemote: false` (41-46) AND source-greps `main.js` to confirm the handler body does not contain `safeForRemote: true` (48-54) — a strong regression guard against silently remote-enabling pixel capture. `installed-apps-cache.test.mjs` proves the future-timestamp staleness invariant (42-57). Gaps worth noting for the verifier lane: (a) no negative test asserting `isAllowedDesktopHostTargetUrl` rejects when `localOrigin` itself is malformed/null (only the positive local-origin match is tested at `desktop-hosts.test.mjs:285-290`); (b) `desktop-lan-address` has no test exercising the `socket.address()` throw branch (`desktop-lan-address.js:63-68`); (c) no test pinning the `DISABLED_REMOTE_SETTINGS_KEYS` set against a future settings key addition (the purge test at `desktop-hosts.test.mjs:29-45` covers current keys but would not catch a new remote-leak key being added without registration in the constant).
