## Step 1 — Map

This is a Wave 1 L-sized unit covering the Electron security policies in `desktop/packages/electron/src`. The MODULE-AUDIT inventories 30 files (~6080 LOC); the security-relevant policy modules I read are: `preload-ipc-policy.js` (69 LOC) — the allowlist `DESKTOP_INVOKE_COMMANDS` Set (6-60) and `isAllowedDesktopInvokeCommand` guard (62-64); `desktop-read-file-policy.js` (64 LOC) — `assertDesktopReadFileAllowed` (36-59) enforcing home/tmp containment plus a `DENIED_SEGMENTS` blocklist (.ssh, .aws, .gnupg, .kube, .config/gh, browser cred dirs at 6-24) and `DENIED_BASENAMES` (.env, .netrc, .npmrc, .pypirc + .env.\*/.pem/.key suffixes at 25, 50-58); `desktop-browser-capture-policy.js` (15 LOC) — `isDesktopBrowserCaptureTargetForSender` (3-11) ensuring capture targets are a different, non-destroyed `webview` typed webContents whose host is the sender; `external-url.js` (28 LOC) — `normalizeSafeExternalUrl` (13-24) restricting to http/https/mailto/tel, rejecting userinfo and control chars; `renderer-crash-policy.js` (33 LOC) — `createRendererCrashPolicy` (8-29) bounding crash reloads to `maxReloads` (default 3) with a `markStable` reset. The large `main.js` (2767 LOC, inventory-reported 3 empty catches) wires these policies into the BrowserWindow/webContents/session lifecycle. `preload.js` (covered in its own unit) bridges via `contextBridge`.

## Step 2 — Threat model

This unit is the Electron trust-boundary core: the renderer process is untrusted (it loads local+remote web content), so every capability exposed to it must be deliberately allowlisted, and every privileged main-process action invoked on the renderer's behalf must be validated. The dominant assets are: (a) the IPC surface — `preload-ipc-policy.js`'s `DESKTOP_INVOKE_COMMANDS` is the capability list; any main-process `ipcMain.handle` not in this set is unreachable from the renderer via the `__TAURI__.core.invoke` shim (preload.js gates with `isAllowedDesktopInvokeCommand`, rejecting with "Desktop IPC command is not available"). The risk is scope creep: adding a new privileged handler to main.js without adding it here leaves it inaccessible (fail-closed, correct), but adding it here without security review expands the attack surface — the file header comment (3-5) documents this review obligation. (b) Filesystem reads via `desktop_read_file` — `assertDesktopReadFileAllowed` is the boundary, blocking reads outside home/tmp and denylisting credential/key dirs and sensitive basenames; path traversal is mitigated because the policy operates on the `realPath` (callers must resolve symlinks upstream). (c) External navigation — `normalizeSafeExternalUrl` prevents `javascript:`/`file:`/custom-protocol URLs and embedded credentials from reaching `shell.openExternal`. (d) Cross-webContents capture — the capture policy prevents a renderer from screenshotting arbitrary other windows. (e) Crash loops — `renderer-crash-policy` prevents an infinite reload loop from a persistently-crashing renderer.

## Step 3 — Correctness

Observed invariants: (1) IPC is fail-closed — `isAllowedDesktopInvokeCommand` does a `Set.has` membership test (preload-ipc-policy.js:62-64), so unknown commands return false; (2) file-read containment checks `isInsideOrSameDirectory(home, realPath)` OR `tmp` first (desktop-read-file-policy.js:41-43), then applies the segment denylist (46-48) and basename denylist (50-58) — order matters: a path must be inside an allowed root _and_ not hit a denied segment/basename; the `toPosixRelativePath` lowercasing (45) makes the segment check case-insensitive on macOS/Windows which is correct for those filesystems but would under-match on case-sensitive Linux (a subtle platform-dependent edge, not a defect); (3) external-url rejects `parsed.username || parsed.password` (external-url.js:19) preventing `https://user:pass@host` credential-in-URL, and rejects control chars (5-11) preventing CR/LF injection in headers; (4) capture policy requires `targetWebContents.getType() === "webview"` (browser-capture-policy.js:8) and `hostWebContents === senderWebContents` (10) — a renderer can only capture its own embedded webview, not sibling windows; (5) crash policy's `shouldReload` returns false when `quitting` (renderer-crash-policy.js:17) so app shutdown isn't deferred, and `beginReload` increments before checking the cap (20-24) so the counter cannot overshoot indefinitely. The 5 empty-catch sites (AUDIT-desktop-electron-security-empty-catch, deferred Low) are in main.js/server-process.js/startup-diagnostics.js; 4 are marked review-needed, 1 accepted-missing-ok — they are tracked, not bulk-ignored.

## Step 4 — Performance

These policy modules are synchronous, in-memory, and called per-IPC-invocation / per-file-read / per-navigation — they are hot-adjacent but each check is O(1): `Set.has` for IPC allowlist (preload-ipc-policy.js:63), `Array.some` over a ~16-element `DENIED_SEGMENTS` list plus a `Set.has` for basenames (desktop-read-file-policy.js:46, 52), a single `URL` parse + `Set.has` for protocols (external-url.js:18-20), and direct webContents property reads for capture (browser-capture-policy.js:4-10). None does IO, none allocates unbounded structures, none blocks the event loop measurably. `createRendererCrashPolicy` is a tiny closure factory (renderer-crash-policy.js:8-29) with two number counters — negligible memory. The `loginRateLimiter` cleanup timer (in ui-auth, covered by its own unit) has an `unref()` to avoid keeping the process alive. No performance finding; the policies are deliberately lightweight gate functions, which is the correct design for security checks on the hot path. The only growth concern (the IPC allowlist growing large) is bounded by deliberate human review per the file comment.

## Step 5 — Design

The design follows the correct Electron security pattern: capability-based IPC (explicit allowlist, not `ipcRenderer.invoke` pass-through), path-based filesystem policy (containment + denylist), protocol allowlist for external navigation, and typed-webContents scoping for capture. Each policy is a small, independently testable module (all have `.test.mjs` companions per the MODULE-AUDIT inventory) — good cohesion and separability. The `pathTools` injection parameter in `desktop-read-file-policy.js` (27, 37) and `options.home`/`options.tmp` (38-39) is a clean test-seam for cross-platform path semantics. One mild design smell: the `DESKTOP_INVOKE_COMMANDS` allowlist (preload-ipc-policy.js:6-60) is a flat 54-entry Set with no grouping/commenting by capability domain (filesystem, window, SSH, updates, etc.) — section comments or a structured map would improve reviewability as it grows, but the flat form is simple and complete. Boundary conformance: these are leaf policy modules with only `path`/`os` Node built-in deps — no cross-package leakage. The `main.js` wiring (not fully read here due to size) is where these policies are \*applied`; the policies themselves are correctly externalized.
