## Step 1 Scope and public surface

The unit is implemented by `packages/ax-code/src/skill/authoring.ts`, `discovery.ts`, `index.ts`, and `validate.ts`. `Skill.Info` defines the shared runtime record, including provenance, compatibility, trigger paths, and standard issues at `packages/ax-code/src/skill/index.ts:28-44`; the public lookup surface is `get`, `all`, `dirs`, and permission-filtered `available` at `packages/ax-code/src/skill/index.ts:393-413`. This matches the four-file scope declared in `docs/module-quality-audit/modules/skill/MODULE-AUDIT.md:20-29`.

## Step 2 Trust boundaries and security controls

Remote indexes and skill files cross the strongest trust boundary. Fetches use the SSRF-pinned client at `packages/ax-code/src/skill/discovery.ts:91-99`; downloaded bodies are limited to 1 MiB and optionally hash-checked at `packages/ax-code/src/skill/discovery.ts:64-79`, and accepted index entries must supply valid hashes at `packages/ax-code/src/skill/discovery.ts:141-160`. Cache destinations receive lexical containment checks at `packages/ax-code/src/skill/discovery.ts:164-190`. Local creation has a remaining symlink concern: `assertContained` uses only `path.resolve` at `packages/ax-code/src/skill/authoring.ts:110-119`, then `createSkill` writes at `packages/ax-code/src/skill/authoring.ts:192-199`; `Filesystem.write` follows the parent directory when it creates a temporary file and renames it at `packages/ax-code/src/util/filesystem.ts:83-100`. A symlinked in-worktree base can therefore redirect creation outside the stated worktree/home boundary. The existing server check covers an explicit absolute `/tmp` path, not a symlinked allowed base (`packages/ax-code/test/server/skill.test.ts:129-143`). This is a concrete follow-up security concern, though the requested artifact set does not include a new finding file.

## Step 3 Control-flow correctness

Initialization has explicit precedence: built-ins load first (`packages/ax-code/src/skill/index.ts:247-257`), compatibility locations follow (`packages/ax-code/src/skill/index.ts:259-288`), then config directories, configured paths, and URLs (`packages/ax-code/src/skill/index.ts:290-322`). Duplicate names are logged and overwritten in the name-keyed record at `packages/ax-code/src/skill/index.ts:73-90`. That conflicts with the doctor logic, which counts duplicate entries at `packages/ax-code/src/skill/authoring.ts:138-148`: production callers pass `Skill.all()`, which is already reduced to `Object.values(s.skills)` at `packages/ax-code/src/skill/index.ts:398-400`. Consequently the CLI/server doctor cannot actually report discovered duplicate names. The unit test proves the helper only with an artificially duplicated array at `packages/ax-code/test/cli/skill.test.ts:120-140`; an integration test through discovery is missing.

## Step 4 Performance and resource bounds

Remote installation bounds per-skill work to four concurrent skills and eight files at `packages/ax-code/src/skill/discovery.ts:13-16`, then also uses the process-wide outbound limiter at `packages/ax-code/src/skill/discovery.ts:193-198`. Cached content with a valid digest avoids another download at `packages/ax-code/src/skill/discovery.ts:102-117`, and the cache behavior is exercised at `packages/ax-code/test/skill/discovery.test.ts:239-256`. The individual payload cap does not cover the index response itself: `fetchArrayBuffer(index)` consumes the whole response before parsing at `packages/ax-code/src/skill/discovery.ts:130-137`, while the Zod index schemas at `packages/ax-code/src/skill/discovery.ts:31-47` impose no array-count or byte bound. A public endpoint can therefore cause disproportionate memory and validation work with an oversized index even though each downloaded skill file is capped.

## Step 5 Design and ownership

Responsibilities are generally cohesive: `validate.ts` owns standard compliance (`packages/ax-code/src/skill/validate.ts:3-31`), `discovery.ts` owns remote materialization, `index.ts` owns source aggregation and permission filtering, and `authoring.ts` owns reports and creation shared by CLI and HTTP. The server consumes those same schemas and functions at `packages/ax-code/src/server/routes/skill.ts:5-20` and `packages/ax-code/src/server/routes/skill.ts:65-87`, avoiding duplicated API business logic. The duplicate-name rule is the notable ownership leak: detection lives after aggregation even though aggregation destroys the required evidence. It belongs in the discovery state (for example, retained collision metadata) or must run before `state.skills[name]` is replaced.

## Step 6 Error handling and maintainability

Malformed local frontmatter is surfaced through the session error channel and logs at `packages/ax-code/src/skill/index.ts:57-65`; scoped directory scan failures log and degrade to no matches, while unscoped failures propagate at `packages/ax-code/src/skill/index.ts:146-158`. Remote index failures are intentionally normalized to an empty result at `packages/ax-code/src/skill/discovery.ts:132-139`, and file failures are logged then returned as `false` at `packages/ax-code/src/skill/discovery.ts:102-121`. This keeps optional remote sources from aborting startup, but callers cannot distinguish “valid source with zero skills” from DNS, HTTP, parse, or integrity failure without reading logs. The silent `catch` around the absent build-time constant at `packages/ax-code/src/skill/index.ts:204-209` is narrow and intentional feature detection, not an actionable swallowed error.
