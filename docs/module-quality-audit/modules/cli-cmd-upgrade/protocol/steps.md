## Step 1 Scope and inventory

The unit under review is exactly one file: `/Users/akiralam/code/ax-code/packages/ax-code/src/cli/cmd/upgrade.ts`. It exports a single yargs command descriptor `UpgradeCommand` (line 44) with `command: "upgrade [target]"` (line 45), a `builder` (lines 47–59) that declares one positional `target` and one `--method/-m` option constrained to `["curl","brew"]`, and an async `handler` (lines 60–133). The handler is the entire behavior surface; the two module-private helpers `formatShadowedLauncherWarning` (lines 6–26) and `formatMissingLauncherWarning` (lines 28–42) are pure string formatters invoked only from the success path of the handler (lines 126 and 128). Imports are `@clack/prompts`, `../ui`, and `../../installation` — a deliberately narrow dependency set for a user-facing interactive command.

## Step 2 Threat and failure model

This is a CLI command that shells out to a remote install script and a package manager, so the failure surface is real. The handler never constructs a command string itself — all spawning is delegated to `Installation.upgrade` / `Installation.latest` / `Installation.verifyActiveLauncher`, and those in `packages/ax-code/src/installation/index.ts` use array-form `dependencies.run(["brew", ...])` / `["bash"]` (lines 253, 313, 321, 328, 335) rather than a shell string, so the command handler introduces no injection vector of its own. The user-controlled input is `args.target`, which on line 93 is sanitized only by stripping a leading `v` (`args.target.replace(/^v/, "")`) and then forwarded verbatim to `Installation.upgrade(method, target)` and into `upgradeCurl`'s `env: { VERSION: target }` (installation/index.ts:255). The curl installer trusts that env var, so a malformed `target` (e.g. `"; rm -rf ~"`) is only safe because the downstream bash script is expected to quote it — that contract is not visible from this file and is the single largest implicit trust in the unit. No secrets are handled here; the only network calls are delegated.

## Step 3 Correctness — control flow

Walking the handler: line 67 detects the install method; line 68 lets `--method` override it; lines 69–86 handle the `"unknown"` case by prompting the user and correctly treat `prompts.isCancel(install)` the same as "No" (line 82) — the inline comment on lines 79–81 documents why a naive `!install` check would still upgrade on Ctrl-C, which is a real bug that was correctly avoided. Lines 92–99 resolve the target inside a try/catch and exit cleanly on failure. Lines 102–106 short-circuit when already up to date. The upgrade itself on line 111 uses the `.catch((err) => err)` idiom to convert rejection into a value so the spinner can report `.error()` (line 113); error rendering on lines 114–116 handles `UpgradeFailedError` (logs `stderr`) and generic `Error` (logs `message`). **Gap:** if `Installation.upgrade` ever throws a non-`Error` value (e.g. a string or a rejected promise with `null`), neither branch on lines 114–116 matches, the spinner already printed `.error("Upgrade failed")`, but no diagnostic is logged — the user sees a failure with no reason. Lines 123–130 run the post-upgrade launcher verification and branch on `activePath` presence. Logic is otherwise sound.

## Step 4 Correctness — the silent `--method` regression

The most substantive issue I found. Line 68 resolves `method = (args.method as Installation.Method) ?? detectedMethod`, honoring an explicit `--method curl` from the user. Line 93 then does `target = args.target ? args.target.replace(/^v/, "") : await Installation.latest()` — it calls `Installation.latest()` **without forwarding `method`**. Looking at `packages/ax-code/src/installation/index.ts:283-300`, `latest(installMethod?)` re-runs `method()` internally when `installMethod` is omitted, so when a user runs `ax-code upgrade --method curl` (no explicit target) on a machine where `method()` detects Homebrew, the latest-version lookup queries the Homebrew formula API (line 294) instead of the GitHub release (line 298). The version string can legitimately differ between the two sources during a release skew window, and the user's explicit method choice is silently ignored for version resolution even though it is honored for the actual install on line 111. The fix is one argument: `await Installation.latest(method)`. This is a correctness/UX defect, not a crash.

## Step 5 Performance

The handler is interactive and I/O-bound; there is no hot path. Two minor observations. (a) Line 67 `Installation.method()` and line 93 `Installation.latest()` are both async and run sequentially, but they are independent when the user passed an explicit `--method`; in that case `method()` is still awaited on line 67 purely to fall back into `detectedMethod` which is then discarded — a wasted `brew list --formula` round-trip on every invocation that passes `--method`. (b) `Installation.upgrade` itself ends with `await text([process.execPath, "--version"])` (installation/index.ts:366) as a smoke test, and then line 123 calls `verifyActiveLauncher` which runs `which ax-code` plus another `[activePath, "--version"]` (installation/index.ts:382-387) — two process spawns for version probes back-to-back. Neither is worth optimizing aggressively for a command run interactively a few times a week, but the wasted `method()` call on the `--method` path is the same root cause as Step 4 and is fixed for free by the same change.

## Step 6 Design and coupling

Coupling to `Installation` is appropriately one-directional: the command knows only the high-level operations `VERSION`, `method()`, `latest()`, `upgrade()`, `verifyActiveLauncher()`, the `Method` / `LauncherCheck` types, and the `UpgradeFailedError` class — exactly the public surface a CLI driver should consume. The two warning formatters (lines 6–42) are well-factored pure functions and were the right extraction. One design smell: the `.catch((err) => err)` pattern on line 111 conflates "success returning `undefined`" with "failure" by reusing the `err` variable name for the success case's `undefined` value and then testing `if (err)`. It reads as if an error always exists; a small refactor (`const result = await Installation.upgrade(...).then(() => null, e => e); if (result) { ... }`) would make the success/failure split explicit. This is a readability nit, not a defect.

## Step 7 Dead code and hygiene

No dead exports, no unused imports, no empty catch blocks, no TODO/FIXME markers — the module is clean. The only minor hygiene note is the duplicated platform branch inside `formatShadowedLauncherWarning` (lines 21–24): the win32 vs unix recovery advice is inlined into the formatter, which is fine for a single call site but couples user-facing copy to the formatter rather than to a constants module. ## Step 9 Findings register and verification

Findings accepted during this primary review of `cli-cmd-upgrade`:

1. **[MEDIUM] `--method` ignored during latest-version resolution** — `upgrade.ts:93` calls `Installation.latest()` without forwarding the resolved `method`; an explicit `--method curl` is silently bypassed for version lookup. Fix: `await Installation.latest(method)`.
2. **[MEDIUM] No direct tests for `UpgradeCommand.handler`** — the cancel guard, up-to-date short-circuit, and launcher-warning branches are uncovered; the similarly-named `test/cli/upgrade.test.ts` targets a different file.
3. **[LOW] Non-`Error` throws from `Installation.upgrade` render no diagnostic** — `upgrade.ts:114-116` only matches `UpgradeFailedError` / `Error`; a string/null throw leaves the user with "Upgrade failed" and no reason.
4. **[INFO] `.catch((err) => err)` idiom** — `upgrade.ts:111` reuses `err` for the success value; minor readability improvement available, not a defect.

No Critical findings; the `findings/` directory remains empty, so no `reverify.md` is required for this unit. Verification of this protocol was performed by reading the four source/test files cited above; no code was modified (read-only review lane).
