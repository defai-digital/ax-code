## Step 1 Scope and map

The `mcp-oauth-trust` unit comprises four files in `packages/ax-code/src/mcp/`. `auth.ts` (254 lines) owns the encrypted credential store at `${Global.Path.data}/mcp-auth.json`, exposing `McpAuth` namespace operations (`get`, `getForUrl`, `set`, `remove`, `updateTokens`, `updateClientInfo`, `updateCodeVerifier`, `clearCodeVerifier`, `updateOAuthState`, `clearClientInfo`, `clearTokens`, `isTokenExpired`). `oauth-provider.ts` (209 lines) implements the `OAuthClientProvider` interface from `@modelcontextprotocol/sdk/client/auth.js` via `McpOAuthProvider`, bridging the SDK contract to `McpAuth` storage. `oauth-callback.ts` (291 lines) runs the loopback HTTP server (`127.0.0.1`, OS-assigned port) that receives the authorization-code redirect. `trust.ts` (174 lines) maintains a separate fingerprint ledger at `${Global.Path.data}/mcp-trust.json` keyed `project:${Instance.project.id}:${name}:${fingerprint}`. Verified export counts against MODULE-AUDIT inventory (43 public exports across the four files) and confirmed the only out-of-module callers of the credential clear path are `McpAuth.clearCodeVerifier` in `packages/ax-code/src/mcp/impl.ts:1475` and the two `new McpOAuthProvider(...)` constructions at `packages/ax-code/src/mcp/impl.ts:558,1311` plus the CLI bridge at `packages/ax-code/src/cli/cmd/mcp-impl.ts:948`.

## Step 2 Threat and failure model

Assets on disk are access tokens, refresh tokens, the OAuth `clientSecret`, the PKCE `codeVerifier`, and the CSRF `oauthState` (all in `mcp-auth.json`), plus the trust ledger in `mcp-trust.json`. Confidentiality is enforced by `encryptField`/`decryptField` in `packages/ax-code/src/auth/encryption.ts` (AES-256-GCM, per-install secret, file mode `0o600` via `Filesystem.writeJson(..., 0o600)` at `auth.ts:126,144,152` and `trust.ts:130`). Integrity of the OAuth handshake rests on three controls: PKCE (`codeVerifier` bound to `serverUrl` per the M-02 fix at `auth.ts:174-183` and validated via `getForUrl` at `oauth-provider.ts:149-158`), CSRF state (validated against the in-memory `pendingAuths` map at `oauth-callback.ts:164`), and loopback-only binding (`hostname: "127.0.0.1"` at `oauth-callback.ts:114`). The failure modes I traced: concurrent OAuth completions for different MCP servers racing on the shared JSON file, mid-flow URL changes reusing credentials, runaway in-flight callbacks leaking memory, and lock-instance mismatch allowing a parallel writer to resurrect invalidated tokens. Each has an explicit mitigation in-code (see Steps 3 and 5).

## Step 3 Correctness

The credential store's read-modify-write atomicity is the core correctness property. Every mutating operation now funnels through `withLock(filepath, ...)` either directly (`set` at `auth.ts:138`, `remove` at `auth.ts:149`) or via `withFileEntryLock` (`auth.ts:120-129`, used by `updateTokens`, `updateClientInfo`, `updateCodeVerifier`, `clearCodeVerifier`, `updateOAuthState`, `clearOAuthState`, `clearOAuthStateIfMatches`, `clearClientInfo`, `clearTokens`). The block comment at `auth.ts:220-229` documents why `invalidateCredentials` was rewritten to use these atomic field-clears: the prior version locked on `mcpName` then called `set()` which locks on `filepath` — two different `Lock` instances — so a parallel `updateTokens()` could land between the get and set and have its write trampled. The fix in `oauth-provider.ts:186-206` dispatches to `remove`/`clearClientInfo`/`clearTokens`, all of which share the `filepath` lock. The `getForUrl` guard (`auth.ts:97-108`) correctly returns `undefined` for entries lacking a `serverUrl` (legacy entries) or whose `serverUrl` differs, and `tokens()`, `clientInformation()`, and `codeVerifier()` in `oauth-provider.ts` all route through it. One asymmetry: `oauthState` is NOT bound to `serverUrl` — `updateOAuthState` (`auth.ts:192-196`) takes no URL argument and `state()` (`oauth-provider.ts:160-184`) never passes one, unlike `saveCodeVerifier` which passes `this.serverUrl`. Because the CSRF check at `oauth-callback.ts:164` validates `state` against the in-memory `pendingAuths` map (not the file), the practical impact is limited, but it is a defense-in-depth gap relative to the PKCE verifier binding.

## Step 4 Performance

`McpAuth.all()` (`auth.ts:110-118`) decrypts every entry on each call, and `get()`/`getForUrl()` both call `all()`. Each `decryptEntry` invokes `decryptField` up to four times (tokens.accessToken, tokens.refreshToken, clientInfo.clientSecret, codeVerifier), and each `decrypt` does up to four PBKDF2 derivations in the worst-case fallback path (`encryption.ts:171-226`). The encryption module mitigates this with a process-wide `keyCache` (`encryption.ts:118-131`, capped at 512 entries with clear-on-overflow) and the v2 reduced iteration count (`PBKDF2_ITERATIONS_V2 = 10_000`, `encryption.ts:39`) when the per-install secret is present. The callback server uses an OS-assigned ephemeral port (`port: 0` at `oauth-callback.ts:115`) instead of the fixed `OAUTH_CALLBACK_PORT = 19876`, avoiding `EADDRINUSE` collisions with other tooling; the actual port is published back via `setCallbackPort` (`oauth-callback.ts:195`) and read lazily by `McpOAuthProvider.redirectUrl` (`oauth-provider.ts:47-49`). No N+1 or unbounded-loop patterns were found in the four files.

## Step 5 Design and coupling

The layering is clean: `oauth-provider.ts` is the only file that imports `@modelcontextprotocol/sdk`, isolating the SDK type surface from the storage layer; `auth.ts` depends only on `Global`, `Filesystem`, `encryption`, and `Lock`; `trust.ts` depends on `Config`, `Instance`, `Filesystem`, `Lock`, and `crypto`. `oauth-callback.ts` depends on `oauth-provider` only for the `OAUTH_CALLBACK_PORT`/`OAUTH_CALLBACK_PATH`/`setCallbackPort` constants, not on the provider class itself — a narrow, intentional seam. The two persistence files (`mcp-auth.json`, `mcp-trust.json`) are owned by disjoint namespaces (`McpAuth`, `McpTrust`) with no cross-writes, keeping ownership unambiguous. The `Lock` primitive (`packages/ax-code/src/util/lock.ts`) is a single-process read/write lock; both namespaces correctly use `Lock.write(filepath)` for the same key across all write paths, which is sufficient because all access is intra-process. The `_actualCallbackPort` module-level mutable (`oauth-provider.ts:20`) is a reasonable tradeoff versus threading the port through every provider construction, since only one callback server runs per process.

## Step 8 Findings register

No Critical or High severity findings were identified in this independent review. Two LOW severity observations are recorded for the ledger (not blocking):

1. **[LOW] `oauthState` is not bound to `serverUrl`.** `updateOAuthState` (`auth.ts:192-196`) and `state()` (`oauth-provider.ts:160-184`) do not persist or validate a URL binding, unlike `updateCodeVerifier`/`codeVerifier()` which explicitly bind to `serverUrl` (M-02). The in-memory `pendingAuths` CSRF check (`oauth-callback.ts:164`) limits practical impact, but the asymmetry is a defense-in-depth gap. Suggested action: thread `serverUrl` through `updateOAuthState` and validate via `getForUrl` in `state()`, mirroring the verifier path.
2. **[LOW] Sensitive-key heuristic in `trust.ts` misses hyphenated variants.** `isSensitiveRecordKey` (`trust.ts:60-72`) matches `apikey`, `api_key`, `token`, `secret`, `password`, and the literal `key`, but not hyphenated forms like `x-api-key` or `x-auth-token` (the latter is caught by `token`, the former is not). A remote MCP `headers` entry named `x-api-key` would have its raw value folded into the SHA-256 fingerprint rather than just a presence boolean, so rotating that key would silently change the fingerprint and force re-trust. Suggested action: add `lower.includes("api-key")` to the predicate.

No findings were accepted into `findings/` at Critical severity, so no `reverify.md` is required for the gate.
