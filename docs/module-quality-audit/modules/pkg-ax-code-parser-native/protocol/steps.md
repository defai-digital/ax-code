## Step 1 Scope and public contract

The reviewed package is the native declaration wrapper at `packages/ax-code-parser-native/index.d.ts:1-9`, with packaging context in `packages/ax-code-parser-native/package.json:2-24`. ## Step 2 Native trust and failure boundaries

Both parsing entry points accept caller-controlled strings (`packages/ax-code-parser-native/index.d.ts:3,7`). On the native side, `extract_symbols` selects a grammar and returns a JavaScript exception for unsupported languages or parser failure (`crates/ax-code-parser/src/lib.rs:518-537,549-556`). `parse_batch` deserializes the complete JSON envelope before doing work, so malformed JSON rejects the whole call (`crates/ax-code-parser/src/lib.rs:560-562`), while an unsupported language in a valid batch is isolated into that file's `error` field (`crates/ax-code-parser/src/lib.rs:569-579`). The declaration exposes only an opaque JSON `string` result and therefore cannot statically describe the `Symbol`/`FileSymbols` structures defined at `crates/ax-code-parser/src/lib.rs:10-43`. No filesystem path is opened by this crate: `FileInput.path` is serialized back as an identifier, while parsing consumes `content` supplied in memory.

## Step 3 Declaration-to-implementation correspondence

The generated camelCase declarations correspond to the four `#[napi]` Rust exports: `extractSymbols(source: string, language: string): string` at `packages/ax-code-parser-native/index.d.ts:3` matches `extract_symbols(String, String) -> napi::Result<String>` at `crates/ax-code-parser/src/lib.rs:549-556`; `hasGrammar` at declaration line 5 matches `has_grammar` at Rust lines 601-604; `parseBatch` at declaration line 7 matches `parse_batch` at Rust lines 559-585; and `supportedLanguages(): Array<string>` at declaration line 9 matches the `Vec<String>` return at Rust lines 587-599. Rust `napi::Result<String>` failures surface as thrown JavaScript errors even though TypeScript return types conventionally omit thrown-error information. The advertised language set is internally consistent: registry aliases are selected at `crates/ax-code-parser/src/lib.rs:47-57` and the exported list enumerates the same eight names at lines 588-598.

## Step 4 Control-flow correctness

Single-file extraction creates a parser, validates the requested grammar, sets it, rejects a missing parse tree, and recursively derives symbols (`crates/ax-code-parser/src/lib.rs:518-545`). Recursive qualification is deterministic: a child name is joined to its parent with `::` at lines 89-109. Batch behavior also preserves per-file success or error output and emits one `FileSymbols` result per input (`crates/ax-code-parser/src/lib.rs:566-584`). One real contract defect is visible across the boundary: the declaration names a meaningful `concurrency` parameter (`packages/ax-code-parser-native/index.d.ts:7`), but Rust deliberately binds it as `_concurrency` and never reads it (`crates/ax-code-parser/src/lib.rs:560`). Callers cannot limit or tune parallel work as the API promises; this is a non-Critical Medium correctness/operability finding.

## Step 5 Performance and resource behavior

Batch parsing uses Rayon `par_iter()` and `map_init(Parser::new, ...)`, giving each worker its own tree-sitter parser and avoiding a shared parser mutex (`crates/ax-code-parser/src/lib.rs:564-582`). That is an appropriate CPU-bound structure, and collection over the indexed slice retains input order. However, because the public concurrency value is ignored at `crates/ax-code-parser/src/lib.rs:560`, execution always uses the process-global Rayon pool. The JSON envelope is fully materialized before parsing (`crates/ax-code-parser/src/lib.rs:561-562`) and every source string is retained in the deserialized `Vec<FileInput>` (`crates/ax-code-parser/src/lib.rs:31-36`), with no batch-size or source-size guard. In the current repository this risk is bounded because the only production call to `NativeAddon.parser()` is the doctor load check at `packages/ax-code/src/cli/cmd/doctor.ts:399-408`; no internal caller invokes `parseBatch`.

## Step 6 Packaging, loading, and ownership

The package correctly owns the JS/N-API boundary while the implementation remains in the Rust crate. Its build scripts point directly to `crates/ax-code-parser/Cargo.toml` and regenerate both `index.js` and `index.d.ts` (`packages/ax-code-parser-native/package.json:22-24`). The workspace driver registers the package, verifies that `ax-code-parser.node` exists, and writes the CommonJS shim expected by `main` (`script/build-native.ts:33-44,56-84`). Runtime access is centralized: `ParserBinding` is a type-only import and `NativeAddon.parser()` loads `@ax-code/parser` behind the native-parser flag (`packages/ax-code/src/native/addon.ts:23-30,47-64,83-86`). Node-bundled distributions copy the native package into the scoped output at `packages/ax-code/script/build-node-tui.ts:460-476`, so declaration, loader, and release assembly agree on the package identity.

## Step 7 Hygiene, reachability, and maintainability

The candidate explicitly identifies itself as NAPI-RS generated and disables linting (`packages/ax-code-parser-native/index.d.ts:1-2`), so changes to its four signatures should be made in Rust and regenerated, not hand-maintained. The declaration contains no stale imports, suppressions beyond the generator banner, optional `any`, or duplicate overloads (`packages/ax-code-parser-native/index.d.ts:1-9`). Repository reachability is thin: the parser flag defaults on (`packages/ax-code/src/flag/flag.ts:318-324`) and doctor reports it (`packages/ax-code/src/cli/cmd/doctor.ts:518-524`), but the actual syntactic extraction path imports `web-tree-sitter` and instantiates its own parser (`packages/ax-code/src/code-intelligence/syntactic.ts:75-83,124-139`). Thus the native API is presently a shipped, externally usable surface and a doctor probe, not an active internal acceleration path; that is a Low ownership/dead-surface concern rather than proof that the public package may be removed.
