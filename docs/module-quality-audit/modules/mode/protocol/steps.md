# Protocol steps — unit `mode`

Primary reviewer: ax-code-glm (model zai-coding-plan/glm-5.2[1m]). Independent verifier lane: codex-sol.
Scope: `packages/ax-code/src/mode/` (15 files, ~1917 LOC). All evidence below is from files read this run; no template scaffolding.

## Step 1 Scope and inventory

The `mode` unit is a horizontally-sliced policy layer for ADR-049 multi-model execution. `packages/ax-code/src/mode/index.ts:1-13` is a clean barrel re-exporting 12 namespaces (`Hybrid`, `ModePolicy`, `Council`, `Arena`, `ModeProtocol`, `Debate`, `Budget`, `ModeMemory`, `WorktreePolicy`, `ImplementArena`, `EnsemblePreflight`, `EnsembleShared`, `WorkMode`). Notably absent from the barrel: `json-mode-prompt.ts` — its two free functions are imported directly by `src/tool/arena.ts:16` and `src/tool/council.ts:13`, so consumers bypass the index. That is an intentional-but-inconsistent export choice worth normalizing. LOC counts in `docs/module-quality-audit/modules/mode/MODULE-AUDIT.md:24-40` match what I read (council.ts 349, memory.ts 198, preflight.ts 159).

## Step 2 Threat and failure model

The unit is almost entirely pure-by-design. arena.ts, budget.ts, council.ts, debate.ts, hybrid.ts, policy.ts, preflight.ts, protocol.ts, work-mode.ts, worktree-policy.ts, implement-arena.ts and json-mode-prompt.ts carry "Pure — no IO" headers and I confirmed no filesystem/network/DB calls. Only two files do IO: `memory.ts` (JSON store at `Global.Path.state/mode-ensemble-memory.json`) and `ensemble-shared.ts` (provider listing + memory read). The interesting correctness risk is not secrets (the audit tag is `correctness`, and there is no secret handling here) but fail-closed budget behavior: `budget.ts:37-100` `check()` returns `{ok:false,...}` for `requestedMembers<1`, arena `<2` after cap, and USD overruns — the right posture for a cost gate. No empty catches in the unit; the one comment-only catch is `ensemble-shared.ts:162-164` (`// memory is best-effort`), which is defensible because `ModeMemory.load()` already swallows its own errors (`memory.ts:121-132`).

## Step 3 Correctness — control flow and edge cases

Read the decision paths end to end. `policy.ts:104-169` `resolveMode` has a deliberate but easily-missed asymmetry: council is enabled by default (`config.council?.enabled === false` at policy.ts:82 disables), while arena is disabled by default (`config.arena?.enabled !== true` at policy.ts:85-88). The inline comment "Arena defaults off until Phase 2 productization" documents intent, but a config author setting neither will get council-on/arena-off silently — worth a preflight note. In arena ranking, `arena.ts:78-82` primary-sorts on `VERIFY_RANK` then `b.score - a.score`, so a `pass` (+100 base) always beats `unknown`/`fail` regardless of later fingerprint adjustments (`arena.ts:104-111`), correctly honoring the "never popularity-first" contract. One real cross-boundary bug: `budget.ts:26` clamps to `HARD_MAX = 6`, but the arena tool at `src/tool/arena.ts:32` uses `HARD_MAX = 5`. A user configuring `modes.arena.maxContestants: 6` passes `Budget.check` (6 allowed) then gets clamped to 5 by the tool layer — the gate and the caller disagree.

## Step 4 Performance

No N+1 or hot-loop concerns: ranking is O(n²) per tier in `arena.ts:93-129` but n is bounded by `HARD_MAX`, so negligible. `debate.ts:48-53` `redactMemberIdentities` builds a per-identity lookbehind/lookahead regex with `giu` and runs `.replace` in a loop; identities are bounded by memberIds in the report and output is sliced to 20 (`debate.ts:82`), so bounded. `memory.ts:134-152` `append` serializes writes through a module-level `writeChain` Promise plus `Lock.write` (in-process) and `FileLock.acquire` (cross-process), then load+rewrite — correct ordering under concurrency. `MAX_OUTCOMES = 2000` (`memory.ts:18`) with `slice(-MAX_OUTCOMES)` caps file growth. No unbounded Map/Set growth; the `usedFingerprints` set in arena.ts:85 is per-call.

## Step 5 Design — coupling, cohesion, boundaries

Cohesion is strong: each namespace owns one decision (placement in hybrid.ts, ranking in arena.ts, aggregation in council.ts, isolation in worktree-policy.ts). The one documented coupling escape is `ensemble-shared.ts:4-9`, which explains that `MemberSelectionSchema` is kept local to each tool on purpose to avoid a module-load cycle (arena-implement → session → prompt-tools → registry → tool modules). That is a reasoned decision, not an accident, and the file limits itself to IO orchestration while keeping validation local — a good boundary. `implement-arena.ts:36-46` extends `Arena.RankedCandidate` via intersection rather than redefining fields, preserving the type contract. `worktree-policy.ts:26-64` correctly delegates the multi-writer decision to `WriteIsolation.evaluateParallelAgents` and only translates the result per isolation mode — clean single-responsibility split.

## Step 6 Dead code and hygiene

`implement-arena.ts:152-158` `isolationForContestants` is annotated `@deprecated Reserved for future use — not currently called from production code.` Grep confirms the only references are the definition and its own unit test (`test/mode/implement-arena.test.ts:144-146`); no production caller. Per the unit conventions this is dead-in-production code that should either be wired up or dropped with its test. Magic-number duplication: the "max members" cap exists as four independent literals — `budget.ts:26` `HARD_MAX = 6`, `council.ts:328` inline `Math.min(maxMembers, 6)`, plus the tool-layer `src/tool/arena.ts:32` (5) and `src/tool/council.ts:27` (6). These must agree but cannot enforce it; consolidating to a shared exported constant in budget.ts would prevent drift. `work-mode.ts:53-62` hardcodes `#22c55e/#3b82f6/#a855f7` chip hex — justified by the inline rationale (theme.primary is peach in the default theme), so acceptable.
