## Step 1 — Map

The hooks unit is a single file `packages/ax-code/src/hooks/lifecycle.ts` (349 LOC) exposing the `LifecycleHooks` namespace. It maps Claude-style event names (`PreToolUse`, `PostToolUse`, `Stop`, `UserPromptSubmit`, `PreCompact`, `SubagentStop`, lifecycle.ts:47-54) onto shell-command packs sourced from three locations: built-in packs hardcoded in the file (`BUILTIN_PACKS`, lifecycle.ts:97-159 — `format-after-edit`, `block-force-push`, `require-tests-on-stop`, `protect-env-files`, `log-bash-commands`), project file `.ax-code/hooks.json` (`loadProjectHooks`, lifecycle.ts:182-204), and config-supplied pack names (`resolveHooks`, lifecycle.ts:207-219). The execution path is `runForWorkspace` → `resolveHooks` → `runHooks` → `runHook` → `runHookProcess` (lifecycle.ts:320, 302, 293, 227), where each hook command is launched with `spawn(hook.command, { shell: true, ... })` (lifecycle.ts:241-247). Inputs to spawned processes flow through environment vars (`HOOK_EVENT`, `HOOK_TOOL`, `HOOK_SESSION_ID`, `HOOK_ARGS_JSON` capped at 32 KiB, lifecycle.ts:229-239) plus stdin (`HOOK_ARGS_STDIN: "1"`, lifecycle.ts:237, 261). The public types `EventName`, `HookCommand`, `Pack`, `RunInput`, `RunResult` are Zod-derived (lifecycle.ts:69-95). Cross-module deps: `ProjectConfigTrust` from `@/config/project-config-trust`, `Instance` from `@/project/instance`, `Global`, `Log`, and `parseJsonResult` from `@/util/json-value`.

## Step 2 — Threat model

The central asset is the host shell: every hook is an arbitrary shell command (`command: z.string().min(1).max(100_000)`, lifecycle.ts:58) executed with `shell: true` (lifecycle.ts:242) and inherits `process.env` (lifecycle.ts:230). The dominant trust boundary is repository-controlled input — `.ax-code/hooks.json` lives in the checkout, so opening an attacker-controlled repo and running a tool previously meant immediate RCE via the matching hook. The current defense is `loadProjectHooks(directory, trusted = ProjectConfigTrust.enabled())` which returns `[]` immediately when `trusted` is false (lifecycle.ts:182-186), and `ProjectConfigTrust.enabled()` (project-config-trust.ts:10-12) reads only `AX_CODE_TRUST_PROJECT_CONFIG` from the environment — a repository cannot set that through its own config, so the gate is genuinely out-of-band (this is AUDIT-hooks-001, verified-fixed). Secondary failure modes: (a) hook output is captured up to `MAX_CAPTURE_BYTES = 1 MiB` (lifecycle.ts:27, 221-225) so a pathological hook cannot exhaust memory, but capture silently truncates; (b) `HOOK_ARGS_JSON` is capped at `MAX_COMPAT_ENV_BYTES = 32 KiB` (lifecycle.ts:28, 236) with the remainder sent via stdin to avoid `E2BIG`; (c) process-group kill on timeout uses `process.kill(-child.pid, "SIGKILL")` on non-Windows (lifecycle.ts:272-277) — correct for `detached` cleanup; (d) `child.stdin.on("error", () => undefined)` (lifecycle.ts:260) suppresses EPIPE when a hook exits before reading stdin — intentional but a genuinely swallowed error.

## Step 3 — Correctness

Observed invariants: (1) project hooks never execute without trust — `loadProjectHooks` short-circuits at line 186 before any `fs.readFile`, and `resolveHooks` always passes through `ProjectConfigTrust.enabled()` as the default (lifecycle.ts:182-184, 212); (2) project JSON is schema-validated with `ProjectHooksSchema.safeParse` and a parse failure returns `[]` rather than partial trust (lifecycle.ts:192-194) — the regression at lifecycle.test.ts:138-148 confirms malformed `{event: "NotAnEvent", command: 42}` yields empty; (3) `blockOnFailure` only vetoes on `PreToolUse` and `UserPromptSubmit` (`BLOCKABLE_EVENTS`, lifecycle.ts:67, 311) — confirmed by lifecycle.test.ts:110-118 where `Stop`/`PostToolUse`/`PreCompact`/`SubagentStop` never block even with `blockOnFailure: true` and `exit 2`; (4) hooks run sequentially within `runHooks` (lifecycle.ts:306 `for...of`) and block-on-failure breaks the loop (lifecycle.ts:313); (5) concurrency is capped by `acquireHookSlot`/`releaseHookSlot` at `MAX_CONCURRENT_HOOKS = 4` (lifecycle.ts:26, 34-46) with a waiter queue. Error translation: hook non-zero exits are `log.warn`-ed, not thrown (lifecycle.ts:309-311); spawn errors append to stderr and finish with exit 1 (lifecycle.ts:283-286); timeout yields exit code 124 (lifecycle.ts:287). The fixed `settled` flag (lifecycle.ts:251, 264-266) prevents double-resolution of the exit promise. Evidence: AUDIT-hooks-001 regression at lifecycle.test.ts:73-84 writes a project hooks.json, asserts default load is empty, then asserts trusted load returns the pack.

## Step 4 — Performance

This is a hot-adjacent path (hooks fire on every `PreToolUse`/`PostToolUse`/`Stop`) but each invocation shells out, so the cost is dominated by process spawn, not by this module's JS. The module bounds resource use explicitly: `MAX_CONCURRENT_HOOKS = 4` caps parallelism via the slot semaphore (lifecycle.ts:26, 34-46); `MAX_CAPTURE_BYTES = 1 MiB` bounds stdout/stderr retention (lifecycle.ts:27, 221-225) with truncation rather than growth; `HOOK_TIMEOUT_MS = 30_000` bounds wall time per hook (lifecycle.ts:25, 270-282) with SIGKILL on the process group; `MAX_COMPAT_ENV_BYTES = 32 KiB` keeps large args off the environment (lifecycle.ts:28, 236) and routes them through stdin instead. The waiter queue (`hookWaiters`, lifecycle.ts:32, 39, 43-45) is FIFO and bounded by the number of pending hooks in a turn — no unbounded growth since `releaseHookSlot` either wakes one waiter or decrements. `selectHooks` (lifecycle.ts:178-180) is O(hooks) per event which is fine given the `.max(100)` schema cap (lifecycle.ts:73). No caching concerns (hooks are resolved fresh per workspace run, which is correct because the file may change). No performance finding.

## Step 5 — Design

Cohesion is strong for a single-file module: schema definitions (lifecycle.ts:47-75), built-in pack catalog (97-159), resolution (161-219), execution (221-300), and the workspace entrypoint (302-348) are clearly sectioned. The trust policy is correctly externalized to `ProjectConfigTrust` (project-config-trust.ts) — the hooks module has no knowledge of how trust is decided, only that it receives a boolean, which is the right separation of "what is trusted" (env policy) from "what trusted config does" (this module). One mild smell: the built-in packs embed `node -e "..."` scripts as command strings (lifecycle.ts:118, 142, 154) which are hard to read and test in isolation; an external script file would be more maintainable but less self-contained. The `matcherHits` glob (lifecycle.ts:165-176) implements a minimal `|`-separated + trailing-`*` matcher rather than full glob — deliberately small surface, adequate for tool-id matching. Boundary conformance: imports stay within `@/util`, `@/config`, `@/project`, `@/global` — no leakage into UI/server/tool layers. `packCatalogMarkdown` (lifecycle.ts:326-344) is a docs helper that belongs here. `globalHooksDir` (lifecycle.ts:346-348) returns a path but I did not find a reader for it in this file — see Step 6.

## Step 6 — Dead code / hygiene

Concrete items: `globalHooksDir()` (lifecycle.ts:346-348) is exported and returns `path.join(Global.Path.config, "hooks")`, but this module never reads from that directory and `resolveHooks` only consults the project file plus config pack names — it appears to be a planned-but-unwired global hooks directory (or consumed by a caller outside this unit), worth confirming whether it is live or a stub. No `TODO`/`FIXME`/`HACK` markers in the file (inventory reports 0). The `child.stdin.on("error", () => undefined)` handler (lifecycle.ts:260) is an intentionally empty callback — it is documented inline as suppressing EPIPE during teardown (lifecycle.ts:258-259), so it is justified rather than a silent-error defect; the comment makes the rationale auditable. The `READ_HOOK_ARGS` constant (lifecycle.ts:29-30) is a shared JS preamble string inlined into `node -e` commands — duplication-by-construction, not dead code. No empty `catch{}` in the main path; the `catch { return [] }` at lifecycle.ts:201-203 around `fs.readFile`/parse is a deliberate "treat unreadable/invalid project hooks as none" policy that returns an explicit empty array rather than swallowing a throw silently in a way that hides it (it is the pre-trust-guarded path, and trust is already required to reach it). No findings warranted.

## Step 7 — Tests

`test/hooks/lifecycle.test.ts` (149 lines) covers: built-in pack count and event coverage (7-23), `packCatalogMarkdown` completeness (17-22), `matcherHits` pipe alternatives and `*` (26-30), the `block-force-push` PreToolUse positive/negative (32-51), large-arg stdin transport with a 64 KiB payload (53-71), project hooks.json load with and without trust (73-84, the AUDIT-hooks-001 regression), `UserPromptSubmit` blockOnFailure (86-108), non-blockable events never blocking (110-118), new lifecycle events accepted from project config (120-136), and malformed entry rejection (138-148). `test/session/prompt-loop-result-stop-hooks.test.ts` covers Stop-hook integration in the session prompt loop. Gaps: I did not locate a dedicated test for the timeout path (30s SIGKILL, exit 124) — this is hard to test without a `sleep 999` hook but is a real correctness branch; similarly the `MAX_CONCURRENT_HOOKS` semaphore (lifecycle.ts:34-46) and the waiter-queue wake-up ordering lack an explicit concurrency test; and the `MAX_CAPTURE_BYTES` truncation behavior (lifecycle.ts:221-225) is not asserted. These are test-gap notes, not findings, because the invariants are simple and the critical trust gate is well covered.
