# Protocol Steps — prompt-history

Unit: `prompt-history` · Reviewer lane: `ax-code-glm` · Model: `zai-coding-plan/glm-5.2[1m]` · Date: 2026-08-11

This is the primary-reviewer 9-step pass for the `prompt-history` unit. Evidence is cited as `file:line` against the three in-scope sources plus the call site and tests I opened to confirm behavior.

## Step 1 — Inventory and public surface

The unit is three files under `packages/ax-code/src/prompt-history/`: `index.ts` (101 lines, namespace `PromptHistory`), `prompt-history.sql.ts` (24 lines, Drizzle table), and `schema.ts` (17 lines, zod schemas). The public exports are `PromptHistory.list` (`packages/ax-code/src/prompt-history/index.ts:29`), `PromptHistory.append` (`index.ts:58`), and the constant `PromptHistory.MAX_ENTRIES` (`index.ts:9`, value `50`). The only consumer outside the unit is the HTTP route in `packages/ax-code/src/server/routes/prompt-history.ts` (`GET /` at line 38, `POST /` at line 62), which imports both `PromptHistory` and the `PromptHistoryEntry` schema. The `prompt_history` table is referenced nowhere else in `src/` (grep of `prompt_history` returned only the two lines in `prompt-history.sql.ts`), so the blast radius of any change here is small and contained to this route pair.

## Step 2 — Threat and failure model

The unit carries the `persistence` risk tag in MODULE-AUDIT. It writes to SQLite through Drizzle's parameterized builder — there is no string interpolation into SQL anywhere (`index.ts:32-40`, `76-86`, `88-96`), so injection is not a realistic vector. Inputs are validated twice on the write path: once by the route's `validator("json", PromptHistoryEntry)` (`server/routes/prompt-history.ts:59`) and again by `PromptHistoryEntry.parse(entry)` inside `append` (`index.ts:59`). Read-path rows are defensively re-parsed with `safeParse` and invalid rows are dropped with a structured `log.warn` rather than thrown (`index.ts:43-54`), so a single corrupted row cannot poison the whole recall list. No secrets, tokens, or PII shape appear in `schema.ts` (`input` is a free string, `parts` is `Record<string,unknown> & {type: string}`); the module is not a secrets boundary.

## Step 3 — Correctness of the read path

`list` orders rows by `desc(time_created), desc(id)` and then calls `rows.reverse()` to return chronological (oldest-first) order (`index.ts:37,42`). That matches what the route test asserts: after writing `prompt 0..prompt 54`, the trimmed list runs from `prompt 5` to `prompt 54` in ascending index order (`test/server/prompt-history.test.ts:83-85`). `normalizeListLimit` (`index.ts:19-23`) sends non-finite values (NaN, Infinity) to `0`, which `list` short-circuits to `[]` (`index.ts:30-31`) — covered by the "normalizes non-finite direct list limits" test (`test/server/prompt-history.test.ts:88-104`). One subtle edge: `limit: 0` is _not_ treated as "return nothing"; `Math.max(Math.floor(0), 1)` yields `1`, so a caller asking for zero rows gets one. Same for any negative number. No test exercises `limit: 0`. This is a low-severity behavioral surprise worth a note but not a defect on its own.

## Step 4 — Correctness of the write path and dedup

`append` runs everything inside `Database.transaction` (`index.ts:62`), whose callback contract is synchronous (`packages/ax-code/src/storage/db.ts:279,314-330`). Inside the tx it (a) reads the single most-recent row (`index.ts:63-69`), (b) compares it to the incoming entry via `entryKey` (`index.ts:25-27, 72-74`), (c) inserts if different (`76-86`), and (d) trims any rows past `MAX_ENTRIES` (`88-97`). The dedup key is `JSON.stringify([input, mode ?? null, parts])`, so consecutive identical submits are suppressed — exactly what the "does not append duplicate consecutive entries" test verifies (`test/server/prompt-history.test.ts:106-125`). The check is intentionally last-row-only, so `A, B, A` keeps the third `A`; that matches a recall-history mental model and is not a bug. The `id()` generator (`index.ts:12-17`) composes `Date.now()` + a process-scoped `sequence` (mod 1_000_000) + `crypto.randomUUID()`; even if two appends land in the same millisecond with the same sequence value, the UUID still guarantees primary-key uniqueness, so there is no collision risk.

## Step 5 — Performance and indexing

Both queries that order results use `desc(time_created), desc(id)`, and the table declares `index("prompt_history_project_time_idx").on(project_id, time_created, id)` (`prompt-history.sql.ts:23`). That index covers the `WHERE project_id = ?` plus the `ORDER BY time_created DESC, id DESC` shape used by both `list` (`index.ts:33-39`) and the trim SELECT (`index.ts:88-93`), so the read path and the post-insert trim are index-served. The trim itself re-runs the full project SELECT after every insert and then loops `rows.slice(MAX_ENTRIES)` issuing one `DELETE` per overflow row (`index.ts:95-97`). For the steady state of "one new entry past the 50-row cap" that is exactly one extra DELETE per append — negligible. There is no N+1 risk on the read path; `list` issues a single bounded `SELECT ... LIMIT n`.

## Step 6 — Design and ownership boundaries

The unit owns its own table, schema, and dedup policy, and reaches out only to `Instance` (`Instance.project.id`, `Instance.directory` at `index.ts:60-61`) and `Database` (`index.ts:1`). Project scoping is enforced by `eq(PromptHistoryTable.project_id, Instance.project.id)` on every query (`index.ts:36, 66, 91`), and the route test confirms two different `tmpdir({git:true})` projects see only their own entries (`test/server/prompt-history.test.ts:27-63`). `MAX_ENTRIES` is exported and reused by the route layer for its zod `max()` (`server/routes/prompt-history.ts:12`), so the cap has a single source of truth. The schema uses `.passthrough()` (`schema.ts:15`), which is permissive on extra keys; combined with the route's strict `validator("json", ...)` this is fine, but it means a direct programmatic caller of `append` could smuggle extra fields into the stored object — they would be ignored by `entryKey` and never re-serialized into the row (only `input`, `mode`, `parts`, `time_created`, `project_id`, `directory`, `id` are written at `index.ts:76-85`). No leakage.

## Step 7 — Hygiene and dead code

Two items. (1) The `time_updated` column on `PromptHistoryTable` is declared with `.$onUpdate(() => Date.now())` (`prompt-history.sql.ts:21`) but this module never issues an `UPDATE` — every write is either `insert` (`index.ts:76`) or `delete` (`index.ts:96`). `time_updated` is therefore always NULL in practice; the `$onUpdate` hook fires only on Drizzle UPDATEs. This is a dead column (low severity). (2) `sequence` (`index.ts:10`) is a module-level mutable counter shared across all projects and threads in the process. It exists only to spread same-millisecond IDs; because the UUID suffix already guarantees uniqueness, the counter is best-effort and harmless, but it is shared global mutable state worth a comment. Empty-catch scan: none — the only swallowed branch is `parsed.success === false` in `list` (`index.ts:48-54`), which is an explicit, logged drop, not a silent catch.
