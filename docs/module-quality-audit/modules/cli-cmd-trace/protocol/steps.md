## Step 2 Public surface and contract

The contract advertised by `TraceCommand.builder` (lines 107–145) promises seven options: `errors`, `slow`, `service`, `limit`, `json`, `logs`, `risk`, plus the `sessionID` positional. Inspecting the handler reveals an asymmetry: `--errors`, `--slow`, and `--service` are only honored in the legacy `--logs` branch (filters at lines 314–328). In the default replay branch none of those filters apply — the user receives the full last-N slice regardless of `--errors`/`--slow`/`--service`. `--risk` is similarly branch-conditional: it short-circuits at lines 170–177 inside `if (!args.logs)`, so `trace --logs --risk` silently ignores the risk flag and prints a log timeline instead. This is a contract drift worth flagging on the help text or routed consistently across both modes.

## Step 3 Correctness of control flow

The replay branch gates on `EventQuery.bySessionWithTimestamp(sessionID).length === 0` (line 163) and exits cleanly. Duration math uses `events[0].time_created` and `events[events.length - 1].time_created` (lines 186–187); this is safe because `bySessionWithTimestamp` orders by `EventLogTable.sequence` (query.ts:125) and `time_created` is monotonic with sequence in practice. The legacy log reader is more fragile: `fs.readdir(logDir).catch(() => [] as string[])` at line 257 swallows every readdir failure (ENOENT, EACCES, EMFILE) into an empty list, then reports “No log files found” (line 272). A user with a misconfigured `$XDG_STATE_HOME` or a permission-locked log dir gets a misleading diagnostic indistinguishable from “no logs yet.” The `MAX_LOG_SIZE` guard at lines 277–287 correctly returns early before the `readFile("utf8")` at line 288, bounding peak resident memory. `normalizeTraceLimit` (lines 89–94) throws synchronously inside the async handler at line 147; yargs absorbs the rejection, which is acceptable.

## Step 4 Performance and resource use

Two memory/concurrency points deserve mention. First, the replay branch calls `EventQuery.bySessionWithTimestamp(sessionID)` (line 162) which is capped at `BY_SESSION_LIMIT = 10_000` rows in query.ts:20 — trace.ts then displays only `events.slice(-limit)` (default 50, line 189). For a 9k-event session this materializes 9k rows of `tool.result` payloads (which query.ts:16–19 explicitly warns can each be megabytes) just to render the last 50. `EventQuery.recentBySession` (query.ts:101) already exists for exactly this “tail N” use and would avoid the full load. Second, the legacy path does `content = await handle.readFile("utf8")` (line 288) on up to 50 MB and then `content.split("\n")` (line 292), briefly doubling resident memory; this is bounded and acceptable, but a streaming line reader would let the 50 MB cap move higher without memory pressure.

## Step 5 Design, cohesion, and boundaries

The handler at lines 146–405 is a single 260-line function that interleaves two unrelated rendering pipelines (replay-event switch at lines 200–242 vs. legacy log pretty-printer at lines 348–384). The replay renderer hardcodes ANSI escapes inline (e.g. `\x1b[31mBLOCKED\x1b[0m` at line 211, `\x1b[32mOK\x1b[0m` at line 225, `\x1b[31mERROR\x1b[0m` at line 237), as does the log renderer (lines 360–379). There is no TTY check, so `ax-code trace > trace.txt` embeds raw escape codes in the captured file. The codebase already ships `packages/opentui-*` theming for the TUI; the CLI surface here predates that and bypasses it. Extracting `runReplayTrace(args)` and `runLegacyLogTrace(args)` (mirroring the two-mode split already documented in the header) plus a tiny `ansi` helper would localize the escape sequences and shrink the handler to two readable functions of ~100 lines each. This is a readability suggestion, not a blocker.
