## Step 1 Scope and public surfaces

The `desktop-web-projects` unit contains three production concerns and their direct tests. External registry ingestion exposes `parseCodexProjectsToml`, `parseKimiWorkspacesJson`, `discoverExternalProjects`, and `registerDiscoverExternalProjectRoutes` at `desktop/packages/web/server/lib/projects/discover-external.js:40`, `:76`, `:128`, and `:225`. Scheduled-task persistence is exported through `createProjectConfigRuntime` at `desktop/packages/web/server/lib/projects/project-config.js:292`; its returned API lists, upserts, deletes, updates task state, and resolves the backing JSON path at `:508-514`. Deterministic project identity is the small `createProjectIdFromPath` export at `desktop/packages/web/server/lib/projects/project-id.js:6-12`. The route composition root mounts discovery and scheduled-task consumers at `desktop/packages/web/server/lib/ax-code/feature-routes-runtime.js:111-126`, while `desktop/packages/web/server/index.js:333-337` constructs the config runtime with the desktop projects directory.

## Step 2 Inputs, assets, and failure boundaries

Discovery reads user-controlled local registries at `~/.codex/config.toml` and `~/.kimi-code/workspaces.json` (`desktop/packages/web/server/lib/projects/discover-external.js:139-166`) and returns absolute workspace paths, names, source metadata, and disk-existence state. Relative roots are rejected before use at `discover-external.js:19-25`, but readability and `stat` failures intentionally collapse to unavailable/not-present states at `:148-166` and `:252-258`. Project configuration contains executable prompts, provider/model selection, schedule data, queue/session state, and last errors. The file sink is protected from traversal by the project-ID allowlist at `desktop/packages/web/server/lib/projects/project-config.js:307-320`; task strings are bounded at `:5-9`, `:19-26`, `:171-193`, and `:214`. The scheduled-task HTTP adapter first confirms the requested ID belongs to a configured project at `desktop/packages/web/server/lib/scheduled-tasks/routes.js:22-40,59-67`, so arbitrary allowed-character IDs cannot directly select unrelated files through that route.

## Step 3 Normalization and state correctness

Schedule validation is substantive: dates are round-tripped through Luxon (`desktop/packages/web/server/lib/projects/project-config.js:37-50`), weekday values must be unique integers 0–6 (`:52-73`), timezones must be valid IANA zones (`:75-89`), and daily/weekly/once/cron variants are normalized separately at `:104-164`. Task identity is immutable on updates and required fields are enforced at `:236-284`. Two correctness gaps remain. First, Codex trust lookup scans a fixed 240-character suffix rather than ending at the next TOML section (`desktop/packages/web/server/lib/projects/discover-external.js:47-59`); a project section with no `trust_level` can inherit the following project's value. This metadata is informational, limiting impact. Second, the server ID helper only changes separators and strips trailing slashes (`desktop/packages/web/server/lib/projects/project-id.js:1-12`), whereas the UI canonicalizes a lowercase Windows drive letter before encoding (`desktop/packages/ui/src/lib/projectResolution.ts:4-13`); the UI contract test requires `c:\Repo\` and `C:/Repo` to match at `desktop/packages/ui/src/lib/projectId.test.ts:5-8`. The server helper returns different IDs for those forms, risking split project-scoped storage on Windows.

## Step 4 Concurrency, atomicity, and cost

Per-project mutations are serialized by a promise chain in `desktop/packages/web/server/lib/projects/project-config.js:377-397`, and writes use a unique temporary file followed by rename at `:360-375`; readers therefore see the old or new complete JSON rather than a partial write. Upsert, delete, and state update all execute inside that lock (`:404-438`, `:441-464`, `:466-506`). The lock is process-local, so a separate writer to the same file could still race the read/merge/write sequence at `:365-374`, but the desktop runtime normally has one owning process. Discovery deduplicates candidates with maps and sets at `desktop/packages/web/server/lib/projects/discover-external.js:168-192` and sorts in O(n log n) at `:209-217`. Disk checks are awaited serially at `:194-207`; a very large external registry therefore scales linearly in both count and I/O latency, though ordinary registries are small and this endpoint is user-initiated rather than a hot loop.

## Step 5 Ownership and composition

The separation is mostly cohesive. `discover-external.js` owns registry parsing, cross-source merging, enrichment, and its thin Express route, with injected home/filesystem/settings dependencies at `desktop/packages/web/server/lib/projects/discover-external.js:225-260`. `project-config.js` owns schema normalization plus JSON persistence and exposes a narrow runtime object at `desktop/packages/web/server/lib/projects/project-config.js:508-514`; scheduling/execution remains in the neighboring runtime rather than this persistence layer. Unknown project-config keys are deliberately preserved by spreading the existing object before replacing version/tasks at `:365-370`, matching the regression assertion in `desktop/packages/web/server/lib/projects/project-config.test.js:168-207`. The design weakness is duplicated identity ownership: the server encoder at `desktop/packages/web/server/lib/projects/project-id.js:1-12` and UI encoder at `desktop/packages/ui/src/lib/projectId.ts:3-20` are independent implementations, and their normalization drift is already observable on Windows inputs. A shared path-identity contract or mirrored server test would make project storage ownership safer.

## Step 6 Error handling and maintainability

The registered empty catch at `desktop/packages/web/server/lib/projects/project-config.js:343-352` is not merely cosmetic: invalid persisted tasks are omitted without a warning, and the next mutation reads that reduced list then overwrites `scheduledTasks` at `:419-431`, potentially making the omission permanent. The existing ledger records this site as Low/deferred and review-needed at `docs/module-quality-audit/modules/desktop-web-projects/findings/AUDIT-desktop-web-projects-empty-catch.md:5-19`; logging the task ID/reason or quarantining invalid records would improve recoverability. Other catches have clear sentinel semantics: invalid JSON produces no Kimi candidates (`desktop/packages/web/server/lib/projects/discover-external.js:81-86`), invalid cron returns false (`desktop/packages/web/server/lib/projects/project-config.js:91-101`), and ENOENT alone becomes an empty raw config while other read/parse failures propagate (`:323-334`). There are no TODO/FIXME markers in the five candidate files. The small `project-id.js` export lacks its own server-side test, which made the cross-layer drift easier to introduce.
