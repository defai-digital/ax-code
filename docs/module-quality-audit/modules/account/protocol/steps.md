## Step 1 — Map

The account unit (`packages/ax-code/src/account`, 4 files / 831 LOC) implements the control-plane identity layer: a SQLite-backed account store plus an OAuth 2.0 device-code service. The schema layer (`schema.ts:9-25`) exposes branded string types (`AccountID`, `OrgID`, `AccessToken`, `RefreshToken`, `DeviceCode`, `UserCode`) and a fixed set of poll result classes (`PollSuccess`/`PollPending`/`PollSlow`/`PollExpired`/`PollDenied`/`PollError`, schema.ts:88-120). The service surface lives in `Account.create()` (index.ts:254-435), whose `Interface` (index.ts:236-247) exposes `active`, `list`, `orgsByAccount`, `remove`, `use`, `orgs`, `config`, `token`, `login`, and `poll`; a module-level singleton is also re-exported as bare functions at index.ts:439-448. Persistence is in `repo.ts` (`AccountRepo.active/list/remove/use/getRow/persistToken/persistAccount`, repo.ts:117-212) over two Drizzle tables in `account.sql.ts` (`AccountTable`, `AccountStateTable`, plus a legacy `ControlAccountTable`). All outbound HTTP responses are validated through Zod schemas (`TokenRefresh`, `DeviceAuth`, `DeviceTokenSuccess/Error`, `User`, `OrgList`, `RemoteConfig`, index.ts:72-114). Cross-module dependency: token at-rest encryption is delegated to `packages/ax-code/src/auth/encryption.ts` (`encrypt`/`decrypt`/`isEncrypted`), which is the subject of AUDIT-account-001.

## Step 2 — Threat model

The dominant asset is the persisted access/refresh token pair (`AccountTable.access_token` / `refresh_token`, account.sql.ts:10-11). The trust boundary is disk: any process or backup that reads the SQLite file reaches ciphertext, so the security posture depends entirely on `encryption.ts` AES-256-GCM + PBKDF2 derivation keyed off `machineId()` (encryption.ts:106-110). A real failure mode is silent key downgrade: if `getInstallSecret()` cannot read or write `.install-secret` it returns `""`, `machineId()` collapses to the low-entropy `hostname-platform-arch`, and `encrypt()` selects version 1 with the full 600k iterations (encryption.ts:145-146) — weaker but not catastrophic, and now logged (AUDIT-account-001). A second failure mode is legacy plaintext acceptance: `decryptToken` (repo.ts:24-46) treats any non-`EncryptedValue` row as plaintext so old installs keep working, which previously hid corruption/tamper; it now `log.warn`s (AUDIT-account-002). A third boundary is the network: device-code and token-refresh POSTs carry `refresh_token`/`device_code` bodies (index.ts:276-280, 401-406) and `server` is caller-supplied in `login(server)`/`poll(input.server)`, so a hostile server URL is an assumed-trust input from the CLI caller (no allowlist here — that belongs to the CLI/server layer). Token refresh has a concurrency hazard: rotated refresh tokens can be invalidated by a second in-flight request using the old token, mitigated by the singleton `tokenRefreshes` map (index.ts:257, 263-314) that coalesces concurrent refreshes for the same account.

## Step 3 — Correctness

Key invariants and their observed enforcement: (1) at most one token refresh per account is in flight — guaranteed because the promise is registered in `tokenRefreshes` before the first `await` and cleared in `finally` (index.ts:270-314); (2) proactive refresh failure does not break a still-valid token — `resolveToken` catches the error and returns `row.access_token` when `row.token_expiry > now()`, otherwise rethrows (index.ts:295-307); (3) HTTP transient failures retry — `fetchWithReadRetry` retries 408/429/>=500 up to 3 times with exponential+jittered backoff (index.ts:134-164); (4) every remote body is schema-validated before use (`jsonBody` + Zod `safeParse`, index.ts:174-189), so a malformed `/api/orgs` cannot inject an arbitrary `OrgID`; (5) DB errors are translated to `AccountRepoError` and HTTP errors to `AccountServiceError` (repo.ts:74-88, index.ts:116-124). One observed availability/consistency tradeoff: `orgsByAccount` uses `Promise.allSettled` and silently drops accounts whose org fetch failed (index.ts:336-346) — correct for a listing UX but means a token/refresh failure is invisible except via `log.warn`. The legacy plaintext path (repo.ts:26-33) is an intentional compatibility relaxation of the "tokens are always encrypted" invariant, now observable. Evidence: AUDIT-account-001 and AUDIT-account-002 are both `verified-fixed`; regression tests exist at `test/auth/encryption.test.ts` and `test/account/repo.test.ts`.

## Step 4 — Performance

The hot path is startup-adjacent token resolution: `Account.active()`/`token()` flow through `resolveToken` → `decryptToken`, and decryption dominates because `auth.all()`-style flows decrypt every field. `encryption.ts` mitigates this with an LRU-ish `keyCache` (encryption.ts:118-131, cap 512 entries, clears on overflow) so repeated PBKDF2 derivation for the same `(password, salt, iterations)` is memoized, and v2 entries use `PBKDF2_ITERATIONS_V2 = 10_000` instead of 600k precisely to cut the per-field ~35ms cost (encryption.ts:30-46). Within the account module itself there is no unbounded growth: the `tokenRefreshes` map is bounded by the number of accounts and drained on completion (index.ts:312-313). `fetchWithReadRetry` caps attempts at 3 (index.ts:149). No synchronous heavy work beyond `pbkdf2Sync` (which is in the cross-module encryption layer, already cached). No N+1: `orgsByAccount` fans out with `Promise.allSettled` rather than serial awaits (index.ts:338-339). No findings to raise here; performance-sensitive design is documented inline in encryption.ts comments.

## Step 5 — Design

Cohesion is good: `schema.ts` (types + branded primitives + error/result classes), `account.sql.ts` (Drizzle tables), `repo.ts` (DB access + encrypt/decrypt translation), and `index.ts` (service + HTTP) are cleanly separated along the policy/IO axis — DB errors never leak as HTTP errors and vice versa. The `Account.Interface` (index.ts:236-247) is the real public contract; the bare re-exported functions at index.ts:439-448 (`export let active = defaultService.active` ...) are a module-level singleton convenience that is slightly weaker design because `let` bindings are mutable and hide the dependency on the default service — but they are a deliberate compat shim for call sites that import `{ Account }` functions directly. Boundary conformance is correct: the module imports `Database` from `@/storage/db`, encryption from `@/auth/encryption`, and `Log`/`parseJsonRecord` from `@/util/*` — no UI, server-route, or tool-layer leakage. One smell: `ControlAccountTable` (account.sql.ts:25-39) is exported and re-exported via `storage/schema.ts:1` but never referenced by any query in `repo.ts`; see Step 6. The branded `stringBrand()` helper (schema.ts:3-7) is a zero-runtime-cost pattern reused consistently.

## Step 7 — Tests

Test coverage maps to the risk paths: `test/account/repo.test.ts` covers `decryptToken` legacy-plaintext logging and encryption round-trips (the AUDIT-account-002 regression); `test/account/token-decode.test.ts` covers `parseEncryptedToken`/`decodeEncryptedTokenValue` negative shapes (non-JSON, missing fields, arrays); `test/account/service.test.ts` covers the device-code login/poll/refresh HTTP flow with an injected `fetch`; `test/cli/account.test.ts` covers the CLI command surface. The cross-module regression for AUDIT-account-001 lives in `test/auth/encryption.test.ts` (asserts `log.warn` matches `/install secret unavailable/i` and that encrypt falls back to v1). Gaps: the singleton refresh-dedup invariant (index.ts:263-314) — that two concurrent `token()` calls share one refresh — is not asserted by a dedicated concurrency test that I could locate, and the proactive-refresh-failure-but-still-valid fallback branch (index.ts:295-307) is a subtle availability path worth a targeted test. The `orgsByAccount` `allSettled` drop-on-failure behavior is another candidate for an explicit negative test.
