## Step 2 — Threat model

This is a scoring/heuristic module, not a trust boundary enforcer — its output drives human review prioritization, not authorization decisions. The primary asset is therefore _decision integrity_: a miscalibrated score could cause a reviewer to under-react to a HIGH/CRITICAL change or waste time on a LOW one. The module is a pure consumer of two untrusted-by-design inputs: persisted diff JSON files on disk (`diffs()`, score.ts:220-233, where a corrupt file is logged and treated as "no diff" — `diffState: "missing"`) and session event records (`EventQuery.bySession`, which surface tool calls and their outputs). The diff decoder defends via `parseJsonResult` + Zod `safeParse` (score.ts:88-100), so a malformed diff cannot inject an arbitrary `Snapshot.FileDiff[]` — worst case is `success: false` and the scorer falls back to derived estimates (score.ts:503). The `SECURITY_PATTERNS` regex list (102-117) drives `isSecurityRelated` classification by filename; this is best-effort signal-gathering, not a security control, so false negatives (a sensitive file not matching the list) are an accepted limitation rather than a vulnerability. No network, no shell, no persistence writes — the module only reads, so the failure model is "wrong/missing inputs → conservative/low-confidence output," which `confidence()` (185-200) explicitly quantifies (down to 0.1 when signals are missing).

## Step 3 — Correctness

Key invariants: (1) scores are bounded to [0,100] via `Math.min(score, 100)` (score.ts:312) and `levelForScore` maps monotonically (>=70 CRITICAL, >=45 HIGH, >=20 MEDIUM, else LOW, score.ts:512-514); (2) confidence is clamped to [0.1, 0.99] (score.ts:199) so a score is never reported with 0 or 1.0 certainty; (3) `normalize` (163-183) fills all optional `Signals` fields with deterministic defaults (e.g. `diffState` derived from whether files/lines changed, `validationState` from `validationPassed` or coverage); (4) readiness precedence is sensible — `completionGateBlocked` → "blocked" first, then validation failed → "blocked", then `needs_validation` if files changed but no validation, then `needs_review` for low confidence or recovered subagent results (score.ts:202-210). The `fromSession` event loop (410-470) correctly pairs `tool.call` with `tool.result` via a `validationMap` keyed by `callID` (432, 439, 447) so a bash validation command's exit/output can be classified by `validationFailed` (533-543). One subtle correctness point: `isCrossModule` (123-131) deliberately groups by the first path segment only (with an inline comment at 124-128 explaining that `slice(0,2)` previously caused false positives) — this is a documented fix. The `validationFailed` heuristic (533-543) parses test-output text for failure markers; it accepts "0 fail"/"0 errors" as pass and counts "N fail"/"FAIL" as fail, which is reasonable but could misclassify a command whose output happens to contain the word "FAIL" in prose — an accepted heuristic limitation.

## Step 4 — Performance

`assess(signals)` is a pure synchronous function over an already-materialized `Signals` object — O(1) relative to score inputs, with a fixed set of `push` calls (score.ts:245-311), so it is cheap and not a hot path concern. `fromSession(sessionID)` is the costlier path: it calls `EventQuery.bySession(sessionID)` (score.ts:396) which materializes the full session event stream, then iterates it once (410-470) — O(events) with a single pass, accumulating into a `Set<string>` for files and a `Map` for validation runs. The diff-file read (223-233) is a single synchronous `readFileSync` + Zod parse; for large diffs the `Snapshot.FileDiff.array()` parse is O(diff size) but bounded by what was persisted. `isSecurityRelated`/`isCrossModule`/`api` (119-139) are O(files × patterns) with small constant pattern lists. No caching exists here, but the module is stateless and callers (TUI/server/CLI) cache `Assessment` results as needed. No unbounded growth in the module itself: all accumulators (`files`, `validationMap`, `runs`) are bounded by the session's tool-call count. No performance finding; the synchronous `readFileSync` at 224 is a minor blocking concern but appropriate for a single small JSON file in a CLI/TUI context.

## Step 5 — Design

Cohesion is strong: the file defines types, normalization, scoring, session-replay aggregation, and rendering in clearly ordered sections, all under one `Risk` namespace. The separation between `assess` (pure scoring over normalized signals) and `fromSession` (impure aggregation that produces signals) is the right seam — `assess` is independently testable and reusable. The `Factor` push pattern (score.ts:239-243, with the `push` closure) makes the scoring rules readable and extensible. One mild design smell: the scoring thresholds (e.g. `filesChanged > 10 ? 25 : > 5 ? 15 : > 1 ? 8 : 0` at 248) are magic numbers inline rather than a named table — a `SCORING_RULES` constant would make calibration tuning easier and more auditable, but the current form is readable. The `text(Readiness)` helper (212-214) does `replaceAll("_", " ")` for display — trivial but places display logic next to the type. Boundary conformance is clean: imports are `@/replay`, `@/snapshot`, `@/session/semantic-core`, `@/global`, `@/util/*` — no UI/server/tool leakage. The `decodeSessionDiffJson`/`decodeSessionDiffValue` pair (88-100) is a small reusable decoder exported for callers that need to validate diffs independently, which is good API hygiene.
