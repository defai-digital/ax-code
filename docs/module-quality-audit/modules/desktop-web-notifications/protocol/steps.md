## Step 2 Threat and boundary model

The module sits inside the desktop web server and touches three trust boundaries: (a) the stdout IPC channel to the Tauri/Electron shell (`emitter-runtime.js:49`), (b) the SSE fanout to UI clients (`emitter-runtime.js:83` and `routes.js:30`), and (c) outbound `fetch` calls to the local ax-code HTTP API (`runtime.js:90`, `template-runtime.js:126,194`). No secrets are handled here; auth headers come from `getAxCodeAuthHeaders()` and timeouts are bounded (`AbortSignal.timeout(2000)` at `runtime.js:96`, `3000` at `template-runtime.js:132`). The SSE endpoint gates on `uiAuthController.ensureSessionToken` or falls back to `getUiSessionTokenFromRequest` (`routes.js:33-35`); the shell-stdout path is gated by `getDesktopNotifyEnabled()` (`emitter-runtime.js:28`). The risk surface is well-contained.

## Step 3 Control-flow correctness

Tracing the dispatch entry `maybeDispatchNotificationForTrigger` (`runtime.js:148`): the `message.updated` branch fans into completion (`finish === "stop"`, line 158) and error (`finish === "error"`, line 233) sub-branches, each guarded by `nativeNotificationsEnabled` before any emit (lines 219, 269). The completion branch applies a 5s per-session cooldown keyed on `lastReadyNotificationAt` (lines 178-183) and a subtask-suppression path that consults `notifyOnSubtasks` plus the cached/looked-up `parentID` (lines 161-168). The `permission.asked` handler reuses the question template/settings (`runtime.js:404` checks `notifyOnQuestion === false` for a permission trigger), which is intentional per the fallback at line 425 but worth flagging as a coupling between two semantically distinct triggers. The `permission.replied` debounce-clear logic (`runtime.js:366`) deliberately clears when either side lacks a `requestKey` or they match — consistent with the inline comment. One correctness gap: when `/api/notifications/stream` cannot resolve a `uiToken`, the handler returns without sending any HTTP status (`routes.js:36-38`), leaving the client with a hanging connection rather than a 401/403.

## Step 4 Performance and resource hygiene

The fanout hot path is debounced (question 500ms at `runtime.js:349`, permission 500ms at `runtime.js:458`) and the completion path is cooldown-limited, so template resolution + git spawn are not on a per-event critical path. `sessionParentIdCache` and `sessionInfoCache` are TTL-evicted (`runtime.js:35`, `template-runtime.js:12`, both 60s). However two collections grow without bound for the lifetime of the server process: `notifiedPermissionRequests` (`runtime.js:29`) only ever `add`s, and `lastReadyNotificationAt` (`runtime.js:30`) keeps one entry per session ever seen. On a long-lived desktop server this is a slow leak — Low severity today, but the parent-cache pattern (TTL + delete-on-expiry at `runtime.js:55-57`) should be mirrored here. `fetchSessionParentId` (`runtime.js:90`) fetches the entire `/session` collection and linear-scans for a match on each cache miss — acceptable given the 60s cache, but it will scale poorly if session counts grow.

## Step 5 Design and ownership

The dependency-injection style is consistent: each factory takes a `deps`/`dependencies` object and returns closures, which keeps the modules testable (the three test files construct runtimes with `vi.fn` stubs, e.g. `runtime.test.js:8-26`). Late-binding setters exist for two cross-cutting concerns — `setOnDesktopNotification` (`emitter-runtime.js:19`) and `setGetIsWindowFocused` (`runtime.js:20`) — both documented with rationale comments (`emitter-runtime.js:14-16`, `runtime.js:18`), which is a clean way to break the construction-ordering dependency without service-locator noise. The split between `emitter-runtime` (channel delivery) and `runtime` (trigger decisioning) is a sound boundary. The one design smell is that `createNotificationEmitterRuntime` and `registerNotificationRoutes` are not re-exported from `index.js:1-3` while `createNotificationTriggerRuntime`/`createNotificationTemplateRuntime` are — the barrel is inconsistent, and `desktop/packages/web/server/index.js:56-59` reaches past it.

Cross-referencing against the wiring in `desktop/packages/web/server/index.js:210-221`, only `fetchFreeZenModels` and `getCachedZenModels` are actually forwarded (consumed by `lib/ax-code/openchamber-routes.js`); `resolveZenModel`, `validateZenModelAtStartup`, and `summarizeText` are exported by the factory but never destructured by the server.
