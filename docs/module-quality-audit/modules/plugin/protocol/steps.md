## Step 1 — Map

The plugin unit is `packages/ax-code/src/plugin/index.ts` (183 LOC) exporting the `Plugin` namespace with four members: `trigger<Name>(name, input, output)` (index.ts:161-174), `list(): Promise<Hooks[]>` (176-178), `init()` (180-182), and the internal `state` factory (46-159). It composes a `PluginInput` (index.ts:52-61) carrying a `RuntimeLocalClient`, project/worktree/directory, a `serverUrl` getter, and a sanitized-env `$` shell (via `Bun.$.env(Env.sanitize(process.env))`), then loads two plugin classes: `INTERNAL_PLUGINS` hardcoded as `[xaiAuthPlugin]` (index.ts:33) imported directly, and config-supplied plugins from `cfg.plugin` (index.ts:75). Config plugins take two forms: npm-spec strings (`pkg@version`) installed via `BunProc.install` (index.ts:82-93), and `file://` URLs that must pass a trust-containment check against `Instance.directory`, `Instance.worktree`, or `Global.Path.config` before import (index.ts:94-107). Loaded plugin modules' exported functions are invoked as `fn(input): Promise<Hooks>` (index.ts:115). All hooks are then subscribed to `Bus.subscribeAll` so every hook's `event` handler receives every event (index.ts:145-152).

## Step 2 — Threat model

The dominant asset is the host shell and the plugin code-execution surface: importing a plugin module runs its top-level code, and `fn(input)` hands that code a `$` shell helper and a `RuntimeLocalClient`. The trust boundary for file-URL plugins is the `Filesystem.contains` check (index.ts:96-99) — a `file://` path outside the project directory, worktree, or config directory is refused with `Session.publishError` (index.ts:100-104). This is the right boundary for "plugins live inside trusted trees", though it does not defend against a malicious plugin _inside_ the trusted tree (that is an assumed-trust author, same as any project dependency). The npm-install path (index.ts:82-93) has a different boundary: `BunProc.install(pkg, version)` trusts whatever npm resolves, with a `DEPRECATED_PLUGIN_PACKAGES` skip-list (index.ts:36) for old names — npm resolution is an external trust root, consistent with normal package-manager behavior. Secondary concerns: `Env.sanitize(process.env)` (index.ts:60) strips dangerous env vars before handing `$` to plugins, limiting secret leakage; `withTimeout(..., PLUGIN_TIMEOUT_MS=15_000)` (index.ts:20, 65-68, 109, 115, 132-136) bounds init/load/config time so a hung plugin cannot freeze startup; the `seen` Set (index.ts:111-114) dedupes the same plugin function exported under multiple names.

## Step 3 — Correctness

Observed invariants: (1) file-URL plugins outside trusted trees never import — the `allowed` check at index.ts:96-100 short-circuits with `continue` before `import(plugin)`; (2) every plugin invocation is timeout-bounded (`PLUGIN_TIMEOUT_MS=15_000` wrapping init, import, and config — index.ts:65, 109, 115, 132); (3) a failing plugin does not abort sibling plugins — internal-plugin failure is `.catch`-logged (index.ts:69-71), config-plugin import/init failure publishes a session error (index.ts:118-122), and config-hook failure splices that hook out of the array (index.ts:138-142) so the rest keep firing; (4) the config-hook loop iterates a snapshot `[...hooks]` (index.ts:128) with a comment explaining that mutating the live array during `for...of` would skip the next hook — a subtle but real correctness guard; (5) event fanout uses `Promise.allSettled` (index.ts:146) so one hook's rejection does not stop others, with per-rejection `log.error`. Error translation: timeouts throw via `withTimeout`; plugin load errors become `NamedError.message(err)` for user-visible `Session.publishError`. The `trigger` function (index.ts:161-174) runs hooks sequentially and mutates the shared `output` object — order-dependent by design, consistent with a pipeline. Evidence: `test/plugin/auth-override.test.ts`, `test/cli/plugin-auth-picker.test.ts`, `test/provider/xai/auth-plugin.test.ts` cover the xai internal plugin path.

## Step 4 — Performance

Plugin loading is startup-only (not a per-turn hot path), but a pathological plugin could block startup; this is bounded by `PLUGIN_TIMEOUT_MS = 15_000` applied to internal init, npm install (indirectly — `BunProc.install` is awaited but not separately timed-out here, a potential gap if npm hangs), import, plugin-init, and config-hook (index.ts:65, 109, 115, 132). The `Bus.subscribeAll` fanout (index.ts:145-152) runs on _every_ bus event for the process lifetime: each event triggers `Promise.allSettled(hooks.map(...))`, so cost is O(events × hooks) — fine for a small hook count but a hook that does expensive per-event work is the real risk (mitigated by the 15s timeout only on init, not on event handlers themselves — event handlers are fire-and-forget with no per-call timeout). No unbounded collections in the module: `hooks` is bounded by `INTERNAL_PLUGINS.length + cfg.plugin.length`. `Env.sanitize` is a per-startup pass. No caching concerns (state is created once via `Instance.state`). No performance finding; the event-handler-without-timeout is a stability note, not a perf defect.

## Step 5 — Design

The design cleanly separates three concerns: the `PluginInput` capability bag (index.ts:52-61) that defines what plugins _can_ do, the loader (index.ts:63-123) that decides what plugins _run_, and the trigger/subscribe runtime (index.ts:145-174) that routes events. The `INTERNAL_PLUGINS` array (index.ts:33) is the right pattern for built-ins that should not round-trip through npm. The `DEPRECATED_PLUGIN_PACKAGES` list (index.ts:36) is a forward-compat shim that silently skips old names — a small quality smell because "silently skip" could surprise a user who still has the old package configured; a `log.warn` would be more discoverable than the bare `continue` at index.ts:79. The `TriggerName` conditional type (index.ts:28-30) correctly narrows to hook names following the `(input, output) => Promise<void>` shape. Boundary conformance: imports stay within `@/` core (config, bus, session, bun, util, project, global, runtime) and `@ax-code/plugin`/`@ax-code/util` packages — no UI or desktop leakage. The `Instance.state(entry, dispose)` pattern (index.ts:46, 156-158) correctly pairs setup with teardown via `unsubscribe()`. Cohesion is good for a single 183-line file.

## Step 6 — Dead code / hygiene

Concrete items: the `DEPRECATED_PLUGIN_PACKAGES` skip at index.ts:79 does a bare `continue` with no log — a user whose configured plugin is silently ignored gets no signal; this is a minor discoverability defect (not a silent _error_ swallow, but a silent _config_ swallow). The npm-install branch lacks a `withTimeout` around `BunProc.install` (index.ts:85) — if npm hangs on network resolution, startup stalls past the 15s init budget because only the surrounding `plugin(input)` is timed for internal plugins, not the config-plugin install. The `for (const [_name, fn] of Object.entries<PluginInstance>(mod))` at index.ts:112 ignores the export name (`_name`) — intentional, since the `seen` Set dedupes by function identity, but means a plugin module cannot intentionally export the same function under aliases for documentation. No `TODO`/`FIXME`/`HACK` markers (inventory reports 0). No empty `catch{}` in the file. The `.catch((err) => { ... return "" })` at index.ts:86-92 converts an install failure into an empty string that then fails the `if (!plugin) continue` check — a deliberate error-to-skip translation that is logged and surfaced via `Session.publishError`, so it is observable rather than silent. No findings warranted; the deprecated-skip log gap is a quality note.

These are test-gap notes; the critical xai auth-plugin path is covered.
