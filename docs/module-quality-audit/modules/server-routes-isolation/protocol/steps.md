## Step 1 — Scope and source map

The unit under review is a single Hono route module exported as `IsolationRoutes` at `packages/ax-code/src/server/routes/isolation.ts:33`, wrapped in `lazy()` so the router is constructed once on first use. It exposes two routes on `/`: a GET (`isolation.get`, lines 35–67) and a PUT (`isolation.set`, lines 68–120). Direct dependencies I read to establish context: `./project-config` (`readProjectConfig`, `persistProjectConfigFeatureResponse`), `./query` (re-exported `JsonBoolean`), `../validation` (the `validator` wrapper around `hono-openapi`), `../../isolation` (`Isolation.DEFAULT_MODE`), and `@/util/feature-flags` (`FeatureFlag.set`, which is just `process.env[key] = String(value)`). The Zod schemas `IsolationMode` (line 15) and `IsolationState` (lines 17–22) are the only types this file owns; both are annotated with `.meta({ ref })` / used as `resolver()` for OpenAPI generation consumed by `packages/sdk/js`. No other module imports these internal schemas — they are local to the route.

## Step 2 — Threat and failure model

The asset surface is the process-global isolation policy env vars `AX_CODE_ISOLATION_MODE` / `AX_CODE_ISOLATION_NETWORK`. The GET handler (lines 53–66) and the PUT handler (lines 86–119) both write `process.env` via `FeatureFlag.set`; the PUT also persists to `ax-code.json` through `persistProjectConfigFeatureResponse`. The consequential failure modes are: (a) a persist failure surfaces as an HTTP 500 with body `{ error: "Failed to persist configuration" }` (line 116, sourced from `PROJECT_CONFIG_PERSIST_ERROR` in project-config.ts:18); (b) the network boolean is silently coerced for `read-only` (line 93); (c) because isolation flag names are NOT members of `ScopedFlagName` (`packages/ax-code/src/flag/scoped.ts:21,31` lists only `AX_CODE_AUTONOMOUS` / `AX_CODE_SUPER_LONG`), every env write is last-writer-wins across directories — the cross-project contamination case that `scoped.ts` lines 6–12 explicitly describe and fixed for autonomous/super-long but which was not extended to isolation. This is the dominant threat for this unit.

## Step 3 — Correctness of the two handlers

GET (lines 53–66): reads config fresh on every call (`readProjectConfig()` at line 59, no caching), derives `{ mode, network }` via the local `isolationConfigState` (lines 24–31), then force-writes both env vars (lines 63–64) so in-process readers (`Isolation.resolve` at `isolation/index.ts:125–127`) see the config-derived value on their next read. The precedence in `isolationConfigState` is config-then-`Isolation.DEFAULT_MODE` ("workspace-write", isolation/index.ts:59), deliberately ignoring env so an externally-edited `ax-code.json` propagates without a server restart. This is internally consistent and verified by `test/server/isolation.test.ts:42–61` ("config is the authority — env var does not override config for GET").

PUT (lines 86–119): validates `{ mode: IsolationMode, network: JsonBoolean.optional() }` (line 85), computes the effective network (line 93: read-only ⇒ false, else requested ?? (mode === "full-access")), and persists via `persistProjectConfigFeatureResponse`. The response deliberately uses the _requested_ `mode`/`network` rather than re-calling `Isolation.resolve()` because the env var still holds the OLD value until `persistProjectConfigFeatureResponse` updates it internally (`project-config.ts:57`); this stale-env-window is documented at isolation.ts:94–100 and pinned by `test/server/isolation.test.ts:239–264`. The `update` callback (lines 107–114) spreads the prior `config.isolation` object before overwriting `mode`/`network`, which preserves `backend` and `protected` — this is the regression fix called out in the inline comment and covered by `test/server/isolation.test.ts:175–212`. Correctness is sound for single-directory operation.

## Step 4 — Performance and concurrency

The route does no synchronous CPU work and no unbounded loops. Each request performs one config read (GET) or one read-modify-write under `Lock.write` + `FileLock.acquire` (`project-config.ts:140–141`); the cross-process file lock serializes concurrent PUTs on the same `ax-code.json`, which is correct. The only efficiency nit is line 87 vs line 92: `c.req.valid("json")` is invoked twice (once for `mode`, once for `network`). Hono caches the parsed body, so this is not a re-parse cost, but it is redundant and slightly obscures intent. The meaningful performance concern is at the system level, not the request level: the GET mutates a process-global env var on every call, so in a server hosting many directories each GET is an O(1) write that nonetheless invalidates the "current" isolation policy for every other directory's in-process readers — a contention/amplification issue rather than a hot-path latency issue.

## Step 5 — Design and boundary ownership

Two functions now derive isolation state from a config object: the route-local `isolationConfigState` (config + default, env-agnostic) and `Isolation.resolve` (env-first, config-fallback). The GET reconciles the divergence by overwriting env to match config. This dual-source-of-truth is intentional — env is the runtime authority for `Permission` / prompt-tools, config is the UI authority — and the inline comments (lines 25–27, 54–58, 94–100) document the reasoning thoroughly. The design smell is that the reconciliation is one-way and side-effectful: a GET (nominally a safe read) mutates runtime policy state. Combined with the fact that isolation env vars are not scoped per-directory (Step 2), the cleanest long-term fix is the one already chosen for autonomous/super-long: add `AX_CODE_ISOLATION_MODE` / `AX_CODE_ISOLATION_NETWORK` to `ScopedFlagName` and route both handlers' writes through `ScopedFlag.recordCurrent`, after which the GET's env write could be dropped or scoped. That change is larger than this unit (it touches `flag/scoped.ts`, `Isolation.resolve`, and all readers) and is flagged as a cross-module design recommendation rather than an in-unit edit.

## Step 6 — Dead code, hygiene, and API contract gaps

No dead exports, no empty catches, no TODO/FIXME markers, no unreachable branches. The `log` instance (line 13) is created and passed into `persistProjectConfigFeatureResponse` for failure logging — used. The `Config.Info` type import (line 10) is used only as a type annotation on `isolationConfigState`'s parameter — appropriate. The one contract gap is in the OpenAPI declaration: the PUT `describeRoute` (lines 70–84) declares only a 200 response, but the handler can return a 500 with body `{ error: string }` (line 116). Because the SDK is generated from these routes (`packages/sdk/openapi.json`), clients have no schema for the failure case and cannot distinguish a persist failure from a transport error. Adding a `500: { description, content: { schema: resolver(ErrorBody) } }` entry would close the gap; this is a LOW-severity API-completeness issue, not a runtime defect.

## Step 7 — Tests

Coverage for this unit is strong and lives in `packages/ax-code/test/server/isolation.test.ts` (265 lines, 9 tests). It exercises: the workspace-write default (lines 26–40), config-over-env authority for GET (42–61), read-only honored over a workspace-write env (63–79), full-access ⇒ network true (81–96), GET env reconciliation (98–117), PUT persist + env + follow-up GET round-trip (119–150), PUT full-access network (152–173), PUT preserving `backend`/`protected` (175–212), string `"false"` parsing for network (214–237), and the stale-env PUT response (239–264). The `withCleanIsolationEnv` harness (lines 8–23) saves/restores the two env vars, preventing cross-test bleed. Gaps I noted: there is no test for the persist-failure 500 path (would require forcing a write error), no test for the read-only + `network:true` silent coercion (line 93), and no multi-directory scenario exercising the cross-project env contamination described in Step 2. The first two are low-value; the third is the one worth adding if the scoped-flag migration is deferred.
