## Step 2 Threat and failure model

This is a native (`risk tags: native` per MODULE-AUDIT) filesystem + regex engine invoked from the Node host, so the failure surface is: filesystem reads/walks (no writes), regex compilation, JSON (de)serialization across the FFI boundary, OS watcher handles, and rayon thread pools. Read paths are uniformly defensive — `walk_files` at `lib.rs:147` iterates `builder.build().flatten()` so unreadable entries are skipped rather than propagated; `glob_files` at `lib.rs:244-247` swallows `std::fs::metadata` errors with `Err(_) => continue`; `search_content` at `lib.rs:490` explicitly ignores per-file search errors (`let _ = searcher.search_path(...)`) so a binary or permission-denied file aborts only that file. The one deliberate error-propagating function is `read_files_batch` (`lib.rs:834-850`), whose inline doc at `lib.rs:830-832` states it returns an error on any read failure so the JS caller can fall back — this is the opposite of its `.d.ts` docstring (see Step 3). There is no secret material, no network, and no subprocess spawn anywhere in the crate; the only OS resource held is the `notify` watcher, which `stop()` at `watcher.rs:137-144` releases by dropping the `Option<RecommendedWatcher>`. The static `IGNORE_PATTERNS` LazyLock at `lib.rs:84-87` panics if `ignore-patterns.json` is malformed, but that file is committed and covered by a drift test (comment at `lib.rs:73-76`), so the panic is a build-time invariant, not a runtime threat.

## Step 3 Correctness of public surfaces

Tracing each `.d.ts` declaration to its Rust impl surfaced one material contract drift and two minor ones. **(Material)** `index.d.ts:72-77` documents `readFilesBatch` as returning "a JSON object mapping file paths to their UTF-8 contents" with "Files that fail to read (binary, permissions, etc.) are silently skipped." Neither clause matches the implementation: `lib.rs:838-846` collects `Result<Vec<(String, String)>, String>` over a rayon `par_iter` and propagates the first failure via `.map_err(napi::Error::from_reason)?` at line 846 — so any unreadable file throws a JS error rather than being skipped — and `lib.rs:849` serializes `Vec<(String, String)>`, which serde emits as an array of `[path, content]` pairs, not an object map. The Rust doc comment at `lib.rs:830-832` correctly describes the error-and-array behavior, so the stale text is confined to the auto-generated `.d.ts` (header `index.d.ts:1`); the typings file was not regenerated when `read_files_batch` changed from best-effort-skip to fail-fast. A JS consumer coding to the `.d.ts` would neither wrap the call in try/catch nor parse the pair-array shape. **(Minor)** `chunkFile` is documented at `index.d.ts:49-50` (mirroring `embedding.rs:19-20`) as chunking "at paragraph/function boundaries when possible"; the body at `embedding.rs:28-74` is purely line-count based (`lines[start..end].join("\n")`) with no boundary detection, so the doc overstates the capability. **(Minor)** `isIgnored` at `index.d.ts:67` types `extraPatternsJson: string`, but `lib.rs:508-510` deserializes it as `Vec<String>`; a caller passing a bare glob string hits a serde error. The remaining surfaces check out: `walkFiles` returns `Array<string>` matching `Vec<String>` (`lib.rs:111`), `searchContent` reports absolute paths per the regression note at `lib.rs:474-479`, and the `FileTree` mutators (`updateFile`/`removeFile`) keep the `files` BTreeMap and `mtime_index` BTreeSet in sync by removing the old `(u64::MAX - mtime, path)` key before inserting (`lib.rs:980-1007`).

## Step 4 Performance

The crate is explicitly the performance layer (it replaces TS polling/walking), and the design bears that out. `IGNORE_FILE_MATCHERS` at `lib.rs:98-104` is a process-wide `LazyLock<Vec<GlobMatcher>>` so the hardcoded ignore patterns compile once, not per `is_ignored` call — the comment at `lib.rs:95-97` cites PERF-07/NAT-03 as the motivating cost. `scan_files` at `lib.rs:708-827` walks once, collects files, then runs all compiled regex patterns across files via `files.par_iter().flat_map(...)` at `lib.rs:786-817`, reading each file once and reusing one `RegexMatcher` per pattern. `FileTreeInner::glob_cached` at `lib.rs:957-976` iterates the `mtime_index` BTreeSet (stored as `u64::MAX - mtime` at `lib.rs:948` so ascending iteration yields newest-first) and breaks at `limit`, giving O(limit) glob queries against the cached tree with no disk I/O after `scan()`. The `before_buf` context ring uses `VecDeque` with `pop_front()` at `lib.rs:364-366` and `lib.rs:672-674` — a comment at `lib.rs:362-363` labels this BUG-284, fixing the prior O(n) `remove(0)` shift. One observation, not a finding: `scan_files` at `lib.rs:792-814` builds a fresh `SearcherBuilder`-constructed searcher per (file, pattern) pair inside the parallel loop; for large pattern sets this re-allocates searcher buffers repeatedly, but rayon amortizes it and the per-file `max_per_file` cap bounds the work.

## Step 5 Design and ownership

The crate owns a single, coherent responsibility — be the parallel, ignore-aware filesystem/regex/glob engine for the runtime — and splits cleanly into four modules: `lib.rs` (walk/glob/search/scan/tree), `watcher.rs` (OS events), `embedding.rs` (chunk/normalize/hash), `detect.rs` (port of the TS debug-engine scanners, header comment at `detect.rs:1-6`). Cross-module coupling is minimal: `watcher.rs:8` imports only `crate::IGNORE_FOLDERS`, and `lib.rs:8-9` re-exports `embedding::*` and `watcher::*` for the NAPI macro. The shared `collect_scan_files` helper at `detect.rs:1067-1118` correctly consolidates the walk+filter logic that would otherwise duplicate across the three detectors (a prior duplication risk, now collapsed). The ignore-patterns contract is dual-sourced: `crates/ax-code-fs/ignore-patterns.json` must stay byte-identical to `packages/ax-code/src/file/ignore-patterns.json`, enforced by a drift test referenced at `lib.rs:73-76` — I read the crate-side file (30 folder entries, 11 file globs) but did not independently locate the enforcing test in this pass, so I flag the dependency on that test rather than asserting it. The `EXCLUDE_DIRS` list at `detect.rs:873-881` partially overlaps `IGNORE_FOLDERS` (node_modules, dist, build, .git, .cache, .next) but adds `coverage` and drops `target`/`bin`/`obj`/`vendor` etc. — intentional per-detector scoping, not drift, since the detectors run their own walk via `collect_scan_files` rather than the shared one.

## Step 8 Finding register

No Critical, no High findings against `pkg-ax-code-fs-native`. One MEDIUM and two LOW observations:

- **MEDIUM — `readFilesBatch` contract drift (stale generated typings).** `index.d.ts:72-77` states failures are "silently skipped" and the return is "a JSON object mapping file paths to their UTF-8 contents." The implementation at `lib.rs:834-850` instead throws a `napi::Error` on the first read failure (lines 838-846) and returns a JSON array of `[path, content]` pairs (line 849 serializes `Vec<(String, String)>`). The Rust doc comment at `lib.rs:830-832` is correct, so the `.d.ts` is simply out of date. Fix: rebuild the typings (`pnpm --dir packages/ax-code-fs-native run build` regenerates `index.d.ts` from the macro doc comments per `package.json:23`) and commit the regenerated file; add an inline test asserting the error-propagation and array shape so the drift cannot recur.
- **LOW — `chunkFile` doc overstates chunking strategy.** `index.d.ts:49-50` and `embedding.rs:19-20` both claim "Chunks at paragraph/function boundaries when possible, otherwise at line count," but `embedding.rs:28-74` is purely line-count based with no paragraph or function-boundary detection. Fix: either soften the doc to "chunks by line count with optional overlap" or implement the boundary-aware splitting the doc promises.
- **LOW — `isIgnored` extra-patterns shape undocumented.** `index.d.ts:67` types `extraPatternsJson: string` without conveying that `lib.rs:508-510` deserializes it as a JSON array of glob strings (`Vec<String>`). A caller passing a single glob string receives a serde error. Fix: note the required `"[\"**\\/*.csv\"]"` shape in the doc comment.

The `findings/` directory is empty/absent, consistent with this register — no separate finding files are warranted below MEDIUM.
