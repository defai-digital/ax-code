## Step 2 Adversarial boundary review

The internet-facing entry points are `POST /provider/:providerID/oauth/authorize`, `POST /provider/:providerID/oauth/callback`, and `GET /provider/auth`. I traced attacker-controlled inputs through the route validators into `ProviderAuth.authorize` and `.callback`. The validators constrain `method` to `z.number().int().min(0)` (`server/routes/provider.ts:676` and `:712`) and `code` to an optional string. `authorize` at `auth.ts:158-165` now bounds-checks both the provider hook lookup (`hooks[input.providerID]`) and the method index (`provider.methods[input.method]`), throwing the typed `OauthMissing` error instead of dereferencing undefined — this is exactly the regression the inline comment at `auth.ts:151-157` documents (previously a raw `TypeError` took down the Effect service for every provider). No SQL, shell, eval, or template-rendering surface is touched by these inputs, so classical injection vectors are out of scope for this unit.

## Step 3 Control flow and edge cases on the public auth surface

I walked `authorize` (`auth.ts:145-184`) and `callback` (`auth.ts:186-234`) line by line. Two observations worth recording:

- At `auth.ts:168`, prompt validation runs only when `method.prompts && input.inputs` are both truthy. If a method declares required prompts but the caller omits `inputs`, validation is skipped and `method.authorize(undefined)` is invoked. The plugin is then solely responsible for rejecting the missing field. The xAI plugin at `xai/auth-plugin.ts:30-32` declares no `prompts` key, so today this path is latent — but a future plugin that declares a required text prompt and forgets to guard `undefined` would let the request through the validator.
- At `auth.ts:178`, `pending.set(input.providerID, result)` overwrites any prior in-flight entry for the same provider without checking. A user who initiates `authorize` twice for the same provider (or for two methods of the same provider) silently loses the first `pending` callback handle; the orphaned promise is never drained. No credential is leaked and no auth bypass results — the overwrite happens before any token is minted — but it is a real correctness footgun. The `finally { pending.delete(...) }` at `auth.ts:202-204` correctly guarantees single-drain cleanup per provider on the callback side regardless of outcome.

## Step 4 OAuth result branching in callback

The exclusive `if / else if / else if` ladder at `auth.ts:210-233` decides whether to persist `oauth` or `api` credentials. I verified each branch against the result shapes the plugin contract permits. The first branch (`refresh` is a non-empty string) wins, which matches the documented intent at `auth.ts:207-209` ("Prefer the oauth shape when a non-empty refresh token is present"). The second branch (`"key" in result`) persists as `api`. The third branch persists `oauth` with `refresh: result.refresh || ""`. This empty-string fallback is required because `Auth.Oauth` (`auth/index.ts:228-235`) declares `refresh: z.string()` as a non-optional field — an empty string is the schema-valid sentinel and round-trips cleanly through `encryptEntry`/`decryptEntry` at `auth/index.ts:287-293` and `:273-281`. The inline comment at `auth.ts:224-225` ("do not store \"\"") is mildly misleading because the code does store `""` when no other shape applies, but the behaviour itself is correct.

## Step 5 xAI device-code flow and timing

`xai/auth-plugin.ts` implements RFC 8628 device authorization. `CLIENT_ID` at line 5 is a public device-code client identifier, not a secret — embedding it in source matches the standard pattern for native public OAuth clients and is not a finding. The polling loop at lines 63-111 honours the device-code `expires_in`, increments `intervalMs` by `DEVICE_CODE_SLOW_DOWN_INCREMENT_MS` on `slow_down` per the RFC, and propagates `AbortSignal` through the custom `sleep` helper at lines 11-24 (which correctly removes its abort listener on resolve, avoiding a stale-listener leak). One correctness nit: at line 101 the `expires` fallback when `body.expires_in` is absent is `expiresAt`, which is the _device-code_ expiry computed at line 53, not the access-token expiry. In practice xAI returns `expires_in`, so the fallback rarely fires; when it does, the persisted token is treated as live for the device-code window (default 5 min, line 9) which may be shorter or longer than the real token lifetime. A token-derived or absent `expires` would be cleaner, but impact is bounded because the refresh token path handles renewal.

## Step 6 Capability registry ordering and matching

`model-capabilities.ts` declares `MODEL_REGISTRY` (lines 144-429) as an ordered list with "first matching registration wins" (comment at line 141). I traced the lookup in `getModelCapabilities` (lines 478-485) and the pattern matcher `matchesPattern` (lines 437-443), which tests both the raw and the normalized model id. I verified ordering for every family that has provider-specific entries preceding a fallback: Qwen 3.7–3.9 Max at lines 159-219, Qwen 3.7–3.9 Plus at lines 225-285, and GLM 5.x at lines 361-393. In each case the provider-filtered entry (`providerIds: ["alibaba-coding-plan", ...]` etc.) precedes the unfiltered fallback, so the specific capability set wins as intended. The returned object is a shallow copy (`{ ...registration.capabilities }` at lines 481 and 484), so callers cannot mutate the registry through the return value. `listRegisteredModels` at line 582 spreads only the top-level array, so mutation of a registration's nested `capabilities` object would leak into global state — minor hygiene concern, not a security boundary, and no current caller mutates it (verified via the grep hits in `agent-optimization-profile.ts` and `super-long-policy.ts`).

## Step 7 Selectability gating composition

`model-selectability.ts` is small but directly security-relevant because it decides which models surface to users and to autonomous/ensemble selection. I traced the composition: `modelSelectableForProvider` (line 43) returns `false` for undefined models, blocked memory (`modelMemoryBlockReason`, line 26, scoped to `ax-engine` only at line 31), and image-only outputs (`capabilities.output.text === false`, line 49), then delegates to `providerModelSelectable` (line 38) for the toolcall rule. `TOOLCALL_OPTIONAL_PROVIDER_IDS` (lines 7-15) is a hardcoded allowlist of seven CLI bridge providers (`claude-code`, `gemini-cli`, `codex-cli`, `grok-build-cli`, `qoder-cli`, `antigravity-cli`, `kimi-cli`); adding a provider here is a deliberate product decision and the set is small enough to audit by eye. The function is called from eight sites including `provider-impl.ts:1327`, `ensemble-shared.ts:65`, and `prompt-routing.ts:121`, so any weakening of these checks would propagate broadly — the tight, single-purpose implementation is the right shape and there is no missing case in the decision tree.

## Step 8 Findings register

No Critical or High severity findings. The three actionable items are all LOW correctness issues, none of which I am accepting as a defect against this unit's gate (they are recorded for the follow-up lane):
