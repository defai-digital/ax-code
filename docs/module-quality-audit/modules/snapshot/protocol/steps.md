## Step 1 Scope and ownership map

The `snapshot` unit is a single-file namespace (`Snapshot@packages/ax-code/src/snapshot/index.ts:14`) that maintains a project-scoped shadow git repository under `Global.Path.data/snapshot/<project.id>` (gitdir built at `index.ts:90`). It owns its own ref namespace (`refs/snapshots/<hash>` at `:59-61`) and per-hash age metadata (`<gitdir>/ax-code/snapshots/<hash>` at `:68-70`), and never writes to the user's real `.git`. Eight async public functions are exported (`init:310`, `cleanup:314`, `track:319`, `patch:368`, `restore:398`, `revert:461`, `diff:497`, `diffFull:523`) plus two zod schemas (`Patch:15`, `FileDiff:21`). State is a single `Instance.state` singleton (`index.ts:84-130`) holding `gitdir`, `worktree`, `prevHash`, a `KeyedSerialQueue`, and two cleanup timers. Cross-cutting helpers are delegated: process spawning + lock-contention retry to `src/util/git.ts`, output parsing to `src/util/git-output.ts`, per-key serialization to `KeyedSerialQueue` in `src/util/queue.ts`, project identity/lifecycle to `src/project/instance.ts`. Consumers I confirmed: `Snapshot.track`/`revert`/`restore`/`diffFull` are invoked from `src/session/revert.ts:66-68,101` and `src/session/summary.ts`, and bootstrap calls `Snapshot.init()` (`src/project/bootstrap.ts`).

## Step 2 Threat and failure model

This is a persistence-tagged unit that shells out to `git` and performs recursive filesystem deletion. Hash-bearing inputs (`patch`/`restore`/`diff`/`diffFull` parameters and `revert`'s `patches[].hash`) are validated by `valid()` (`index.ts:55-57`, regex `/^[0-9a-f]{40}$/`) with safe-degradation on mismatch (`patch:371-374`, `diff:500-506`, `diffFull:526`, `restore:401-407`). The destructive surface is `revert@:461-495`: it derives `rel = path.relative(current.worktree, file)` (`:471`) and, when both `git checkout` and `git ls-tree` indicate the file did not exist in the snapshot, reaches `remove(file)` (`:489`) which is `fs.rm(file, {recursive:true, force:true})` (`:147-149`). **There is no containment check that `file` lies inside `current.worktree` before the recursive delete.** I traced the producer of `patches[].files`: `Snapshot.patch()` itself emits only worktree-rooted paths (`path.join(current.worktree, item)` at `:393`), but those values are persisted as session message parts (schema is a bare `string[]` per `src/session/message-v2-impl.ts`) and re-loaded by `SessionRevert.revert` (`src/session/revert.ts:31-53`, `part.type === "patch"`). The HTTP revert route (`src/server/routes/session-impl.ts:1477-1510`) validates only `{messageID, partID?}` and does not itself inject paths — so the trust boundary is persisted DB state, not unauthenticated remote input. A corrupted or maliciously-written patch part with `files: ["/etc/foo", "../../sibling"]` would cause recursive deletion outside the worktree.

## Step 3 Correctness of public control flow

I traced every exported function. `track@:319-366` runs `ensureRepo` → optional `git status --porcelain` unchanged-short-circuit when `prevHash` is set (`:327-332`) → `add` → `write-tree` → `valid` → `update-ref refs/snapshots/<hash>` → `writeSnapshotMeta` → set `prevHash`. **Issue A (MEDIUM, silent durability):** when `write-tree` (`:335-343`) or `update-ref` (`:349-360`) fails, `track` logs `log.error` but returns `current.prevHash`; the caller receives a hash that looks valid but does not capture the current working tree, so a later `patch`/`diff` against it would diff against stale state. **Issue B (MEDIUM, silent error):** `add@:234-237` discards the `runGit` result entirely — its callers (`track:334`, `patch:375`, `restore:409`, `diff:507`) continue regardless. A failed `git add` (e.g. disk error writing the index) produces a valid but stale tree without rejecting the operation. `restore@:398-458` is the strongest control flow in the file: it writes a rollback tree first (`:410-419`), then `read-tree <snapshot>`, then `checkout-index`; on checkout failure it attempts `read-tree <rollbackTree>` + a second `checkout-index` (`:424-444`) before throwing. This two-phase rollback is pinned by a behavioral chmod test (`test/snapshot/snapshot.test.ts:222`) and a source-text structural test (`:1021`). `diffFull@:523-568` joins a `--name-status` pass with a `--numstat` pass under one operation lock (lock-spanning asserted at `test/snapshot/snapshot.test.ts:1146`). **Issue C (MEDIUM):** `diffFull` does not inspect either diff command's `code` before parsing stdout (`:531-566`), so a missing/pruned object or git failure yields an empty or partial summary instead of an error.

## Step 4 Concurrency, lifecycle, and performance

All mutating/read operations route through `withOperationLock` → `current.operationQueue.run("snapshot", fn)` (`index.ts:185-187`), and the queue's tail chaining drops the entry only when still current (`src/util/queue.ts:111-121`), so one failed op does not strand later work. Because the single key is the literal `"snapshot"`, every snapshot operation is strictly serial per project — necessary for git-index safety but it means one slow op blocks `track`/`restore`. Cleanup's 60 s initial delay and hourly interval are both `unref`'d (`:111`, `:113`) and both are cleared on dispose (`:119-129`); an already-queued cleanup that raced dispose still runs serialized, which is acceptable since `cleanupFor` is idempotent-ish (only deletes refs older than 7 days, `pruneMs:37`). **Performance (LOW):** `diffFull` issues 2 diff passes plus, per changed non-binary file, an `ls-tree -l` size probe (`size:189-196`) and two `show` calls (`show:198-206`), serialized across files — up to 4 git subprocesses per file. The 1 MiB `maxFileSize` cap (`:38`, enforced at `:199-200`) bounds memory and is tested (`test/snapshot/snapshot.test.ts:1403`). There is no overall timeout on `runGit`/`git` (`src/util/git.ts:27-57` retries only lock-contention); a pathological repo could stall the queue indefinitely. A bounded fan-out inside the existing lock (e.g. the `work()` helper at `src/util/queue.ts:79`) would cut wall time without breaking serialization.

## Step 5 Design cohesion and trust-boundary ownership

The namespace is cohesive around one responsibility — capturing working-tree snapshots and translating them into patch/restore/diff/diffFull operations — and delegates cleanly to `git-output`, `queue`, and `Instance`. Layering with `session/revert.ts` is sound: session code decides _which_ message range to undo (`revert.ts:24-67`), while snapshot code owns filesystem mutation. The design hole is the public `Patch` contract (`index.ts:15-18`): it exposes `files: string[]` as absolute paths with no type-level tie to the owning worktree and no constructor/refinement. Because the destructive sink (`remove(file)` at `:489`/`:147-149`) trusts these strings without re-validating containment in `current.worktree`, any producer that can write a persisted patch part (DB write, plugin, future route) can widen the deletion blast radius. The `enabled@:208-211` gate is consulted by `track` and `cleanupFor` but deliberately NOT by `restore`/`revert`/`diff`/`diffFull` — a sensible asymmetry (a user who disables snapshots after the fact must still be able to undo), though `diff`/`diffFull` calling `add(current)` mutates the snapshot index even when disabled; harmless (private gitdir) but slightly surprising.

## Step 6 Hygiene and error handling

No empty `catch`, no TODO/FIXME, no `any`/unsafe casts in the candidate source — confirmed by reading the file. Error handling is granular and intentional: `read@:140-145` swallows only ENOENT and rethrows everything else (the `EACCES`-on-exclude test at `test/snapshot/snapshot.test.ts:417` pins this). `remove@:147-149` uses `.catch(() => undefined)` converting every `fs.rm` failure — including EACCES and file↔directory replacement — to silent success. **Issue D (MEDIUM, silent error):** combined with Issue B above, a valid in-worktree revert can report success while a new file remains because deletion failure is swallowed; the regression at `test/snapshot/snapshot.test.ts:110` covers the happy-path deletion but not permission-denied or type-replacement cases. `removeSnapshotMeta@:157-159` is also best-effort but bounded (orphan meta file after its ref is gone). The `log.warn`/`log.error` callsites (`:98`, `:255`, `:271`, `:285`, `:336`, `:352`, `:402`, `:428`, `:445`, `:452`, `:479`) consistently attach structured fields (`exitCode`, `stderr`, `hash`, `gitdir`) matching repo convention.

## Step 8 Backward compatibility and migration

`snapshotTimestamp@:161-183` implements a deliberate three-tier age-resolution ladder: (1) per-hash meta file, (2) loose-ref mtime (`snapshotRefPath:63-66`), (3) `packed-refs` mtime. The comment at `:178-181` explains why the packed-refs fallback is _persisted_ back into the meta file on first read: a later `git gc` would otherwise rewrite `packed-refs` and refresh every snapshot's apparent age indefinitely, defeating the 7-day prune. This is a thoughtful migration shim for older installs and is exercised by `test/snapshot/snapshot.test.ts:436`, which writes a stale meta file directly, packs refs, and asserts the expired ref is dropped while the current ref survives. `ensureRepo@:294-308` sets `core.autocrlf=false`, `core.longpaths=true`, `core.symlinks=true`, `core.fsmonitor=false` on first creation only (guarded by `if (existed) return`), so pre-existing snapshot repos keep their original config across upgrades — no silent reconfiguration. `cleanupFor@:245-292` also carefully skips the in-flight `current.prevHash` ref (`:266`) so an active session never has its latest snapshot pruned from under it.
