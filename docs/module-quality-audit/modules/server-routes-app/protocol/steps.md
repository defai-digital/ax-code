## Step 1 Inventory and scope confirmation

The unit under review is a single TypeScript module that registers eight top-level Hono routes on a lazily-instantiated router. `AppRoutes` is exported at `packages/ax-code/src/server/routes/app.ts:34` as `lazy(() => new Hono().post(...).get(...) ...)`. The lazy wrapper (`packages/ax-code/src/util/lazy.ts:7`) memoises the Hono instance, so `Server.Default()` calling `AppRoutes()` at `packages/ax-code/src/server/server.ts:324` mounts exactly one router tree per process. The eight operations exposed are `POST /instance/dispose`, `POST /instance/restart`, `GET /path`, `GET /vcs`, `GET /command`, `GET /capability`, `POST /log`, and `GET /agent`. No other file in the worktree declares an `AppRoutes` symbol (grep returned only the definition site and the single mount site), confirming the unit is self-contained.

## Step 2 Boundary and threat surface

This module sits behind the unified Hono app, which enforces `assertAuthenticatedNetworkBind` at bind time (`packages/ax-code/src/server/server.ts:355`) plus the global rate-limit and request-logging middleware wired in via `createRateLimitMiddleware` / `createRequestLoggingMiddleware` imported at `server.ts:57`. The risk-bearing surface in this unit is concentrated in the two POST handlers. `POST /log` (`app.ts:190-250`) accepts untrusted `message` (max 10000 chars) and free-form `extra` metadata from any authenticated client and persists it through `Log.create({ service })` (`app.ts:226`) — a network-reachable log-injection sink. The `service` regex `^[a-zA-Z0-9._-]+$` with `.max(64)` (`app.ts:213-214`) and the control-character stripping in `clean()` (`app.ts:16-18`) plus depth/key-bounded `cleanExtra()` (`app.ts:23-32`, `EXTRA_MAX_DEPTH=5`, `EXTRA_MAX_KEYS=50`) are the mitigations; they are appropriate. `POST /instance/dispose` (`app.ts:36-57`) and `POST /instance/restart` (`app.ts:58-82`) are destructive, instance-wide operations reachable from any authorised caller — they rely entirely on upstream auth to gate execution, with no per-route confirmation.

## Step 3 Correctness of control flow

Read against the dependencies. `Instance.dispose()` (`packages/ax-code/src/project/instance.ts:309-341`) and `Instance.reload()` (`instance.ts:274-308`) both publish lifecycle events and re-throw on failure, so the handlers at `app.ts:54` and `app.ts:76` propagate errors to the Hono error envelope in `packages/ax-code/src/server/error.ts:242-254`. That envelope path covers `HTTPException`, `NamedError`, and plain `Error`, so a 500 with `logRef` is produced for unexpected failures. The `/log` handler destructures `c.req.valid("json")` at `app.ts:225` and dispatches across the four allowed `level` enum values (`app.ts:233-246`); the `switch` has no default arm but the zod enum (`app.ts:216`) makes the four cases exhaustive at runtime, so no fall-through exists in practice. The `extra` optional field is only spread into metadata when present (`app.ts:230`), and `cleanExtra` is applied there — the path is correct. `Vcs.branch()` returns the live current branch (`packages/ax-code/src/project/vcs.ts:78-80`) and the response shape `{ branch }` at `app.ts:141-143` matches the declared `Vcs.Info` schema (`vcs.ts:21-28`: `z.object({ branch: z.string() }).meta({ ref: "VcsInfo" })`), so the OpenAPI contract and runtime payload agree.

## Step 4 Performance and resource behaviour

All handlers are `async` and `await` their backing calls, so the Hono event loop is never blocked. `Command.list()` (`app.ts:164`), `Capability.list()` (`app.ts:186`), and `Agent.list()` (`app.ts:269`) are awaited sequentially per request; none are coalesced here, but each is a cheap in-process catalog read and the route is called rarely (UI bootstrap), so no batching or caching is warranted at this layer. `cleanExtra()` walks `extra` to a fixed depth and slices arrays/objects at 50 entries (`app.ts:24-29`), bounding CPU and log-volume for any single `/log` post — this is the right place to enforce the cap. `AppRoutes` itself is `lazy`-wrapped, so the route tree and its zod schemas are built once per process, not per request. No N+1, no unbounded growth, no leaking timers or listeners are introduced by this module.

## Step 5 Design and module boundaries

The module is intentionally a thin registration shell: it owns routing, OpenAPI metadata, and input sanitisation only, delegating persistence (`Instance`, `Vcs`, `Log`), catalog data (`Command`, `Capability`, `Agent`), validation (`validator` from `packages/ax-code/src/server/validation.ts:4-14`), and error envelopes (`error.ts`) to their respective owners. That is the correct separation for a routes file. One structural observation: the instance-scoped handlers (`/instance/dispose`, `/instance/restart`, `/path`, `/vcs`) operate on the ambient default `Instance` with no `?directory=` query parameter, unlike the `/context` route tested in `packages/ax-code/test/server/app-context-routes.test.ts:8-10` which takes `?directory=`. In single-project loopback use this is fine; in the multi-project Desktop scenario implied by `invalidateProviderStateAll` (`server.ts:93-98`) these routes implicitly target whichever project the default `Instance` resolves to. This is a pre-existing design choice rather than a defect introduced here, but it is worth noting because the module is the place a future directory-scoping refactor would touch.

## Step 6 Hygiene, dead code, duplication

No TODO/FIXME markers, no empty `catch` blocks, no commented-out code in the file. `clean` and `cleanExtra` are local helpers used only within the `/log` handler; they are not exported and not duplicated elsewhere in `src/server/routes/`. The `EXTRA_MAX_DEPTH` / `EXTRA_MAX_KEYS` constants (`app.ts:20-21`) are well-named and live next to their only consumer. A minor hygiene nit: `cleanExtra` returns `"[truncated]"` for depth overflow (`app.ts:24`) but silently `slice(0, EXTRA_MAX_KEYS)` drops array/object entries beyond 50 without any marker (`app.ts:26`, `app.ts:28`), so clients reading logs cannot tell whether truncation occurred at the breadth axis. This is LOW severity and does not require changes for sign-off.
