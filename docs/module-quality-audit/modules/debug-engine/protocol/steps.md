## Step 3 Graph analysis and correlation correctness

`analyzeBugImpl` clamps caller depth, parses and filters frames, resolves every reported symbol through `CodeIntelligence`, and builds a hypothesis only around a resolved frame (`packages/ax-code/src/debug-engine/analyze-bug.ts:275-390`). The cite-or-drop validator removes nonexistent frame indices and rejects a claim with no surviving citation (`analyze-bug.ts:401-412`). `analyzeImpactImpl` also bounds traversal and forces truncated results to high risk (`packages/ax-code/src/debug-engine/analyze-impact.ts:225-239`, `:250-307`). A material limitation is explicit at `analyze-impact.ts:176-180`: the BFS walks callers only because references are source locations, despite the module header describing call/reference impact at lines 8-19. Imports, non-call references, and other dependency edges can therefore be absent while the report still returns a low risk label; this is a Medium under-approximation risk.

Diagnostic correlation has a separate Medium signal-quality issue. `findCrossFileRootCause` receives the diagnostic message at `packages/ax-code/src/debug-engine/diagnostic-correlation.ts:329-337`, but candidate scoring at lines 377-420 never uses that message or type relationship. Any direct cross-file function/method caller can receive `confidence: "high"`, and non-low candidates are rendered to users at lines 435-452. The test deliberately pins this topology-only inference (`packages/ax-code/test/debug-engine/diagnostic-correlation.test.ts:229-270`), so the result should remain labelled as a possible lead or gain semantic evidence before being treated as a high-confidence root cause.

## Step 4 Scanner semantics and native parity

The scanners are intentionally heuristic. Hardcode scanning tracks multiline block-comment state before running number, URL, path, and entropy detectors (`packages/ax-code/src/debug-engine/detect-hardcodes.ts:249-336`); security scanning limits each detector and supports suppression comments (`packages/ax-code/src/debug-engine/detect-security.ts:271-300`). However, the race and lifecycle scope finders only begin a function when brace depth is zero (`packages/ax-code/src/debug-engine/detect-races.ts:62-87`; `packages/ax-code/src/debug-engine/detect-lifecycle.ts:92-132`). Methods inside a class begin at depth one, so async class-method races and class-method resource leaks are silently skipped in the JavaScript paths. This is accepted as a Medium coverage defect; the existing scanner tests use top-level functions, for example `packages/ax-code/test/debug-engine/phase2-3.test.ts:750-773` and `:917-933`.

Native mode is opt-in (`packages/ax-code/src/debug-engine/native-scan.ts:10-12`, `:159-191`), but it is not behaviorally identical. The TypeScript security path exempts trusted script targets (`packages/ax-code/src/debug-engine/detect-security.ts:33-43`), whereas the Rust path scans every collected target without that exemption (`crates/ax-code-fs/src/detect.rs:887-923`). Rust file collection stops at `max_files` (`detect.rs:1086-1117`) and then reports truncation whenever the retained count is equal to the cap (`detect.rs:894-903`), so an exactly-at-cap workspace is falsely marked truncated and a larger candidate count is never measured. These native/JS parity differences are Medium/Low respectively and need opt-in-mode regressions.

## Step 5 Safe-refactor mutation and concurrency

The plan pipeline resolves graph targets, records affected files/references, snapshots the graph cursor, and persists a pending DRE-owned row (`packages/ax-code/src/debug-engine/plan-refactor.ts:186-270`). Apply rejects missing, non-pending, stale, dirty, and non-git cases before validation (`packages/ax-code/src/debug-engine/apply-safe-refactor.ts:145-173`), then cleans the shadow in a `finally` block (`apply-safe-refactor.ts:344-346`). The principal finding is High correctness/data-integrity risk in the final apply: every invocation writes the caller patch to the same real-worktree filename `.dre-apply.patch`, invokes `git apply` on it, and unconditionally removes it (`apply-safe-refactor.ts:299-313`). Meanwhile the same-project shadow gate permits three concurrent handles (`packages/ax-code/src/debug-engine/shadow-worktree.ts:32-59`). Two approved applies can therefore overwrite or remove the shared patch file between write and process read, causing one plan to fail or apply another plan's diff; a clean tracked file already named `.dre-apply.patch` would also be overwritten and deleted. Use a unique temporary file outside the worktree (or a stdin-capable git helper), and serialize the real-worktree decision/apply/status section per project. The test suite covers one happy apply and one bad patch (`packages/ax-code/test/debug-engine/phase2-3.test.ts:1613-1722`) but not concurrency or filename collision.

## Step 6 Performance, caches, and persistence

Graph walks are bounded: bug caller depth is at most eight (`packages/ax-code/src/debug-engine/analyze-bug.ts:31-32`), impact visits at most 10,000 nodes (`packages/ax-code/src/debug-engine/analyze-impact.ts:34-37`), diagnostic correlation caps callers, depth, and output (`packages/ax-code/src/debug-engine/diagnostic-correlation.ts:56-65`), and scanner reads use batches of eight (`packages/ax-code/src/debug-engine/scanner-utils.ts:12`, `:142-166`). Duplicate near-match grouping is still quadratic: nested singleton comparisons live at `packages/ax-code/src/debug-engine/detect-duplicates.ts:243-274`, while the public tool permits 10,000 candidates. The worst case is roughly 50 million Jaccard comparisons on the event loop; this is a Medium performance advisory, and a token/inverted index or a lower hard limit would provide a safer bound.

Correlation state is instance-owned, debounced, TTL-bound, and capped at 200 entries (`packages/ax-code/src/debug-engine/diagnostic-correlation.ts:40-54`, `:174-197`, `:502-514`). Refactor rows and embedding rows are project-scoped in every query (`packages/ax-code/src/debug-engine/query.ts:27-110`). Pattern memory evicts 10 percent at its 1,000-row threshold (`packages/ax-code/src/debug-engine/pattern-memory.ts:341-376`), though concurrent check-then-insert calls can temporarily exceed that soft cap. LSP prewarm reserves timestamps before awaiting and removes failed reservations (`packages/ax-code/src/debug-engine/prewarm-lsp.ts:50-74`), which is directly covered by concurrent and retry tests at `packages/ax-code/test/debug-engine/prewarm-lsp.test.ts:28-58`.
