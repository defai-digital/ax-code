# 7.15.0 Undo / Restore 历史窗口恢复修复

日期：2026-09-09。基于本地 `local/v7.15.0-fixes-performance-20260909`，保留之前的 Redo、并发撤销、RPC EOF 和上游已合入的性能/控制台修复。主分支不变，暂不提交或推送。

## 问题与原因

长会话存在撤销标记，但 TUI 只加载最近 100 条消息。当撤销点在窗口外，之前加入的保护会隐藏无法确定可见性的消息并拒绝猜测 Undo / Redo 目标，却没有实现补齐历史。结果是提示一直存在，用户无法继续撤销或恢复。

后端已有 `session.messages` 的 `before` 游标分页以及 `X-Next-Cursor` 响应头，前端未使用。即使临时补齐历史，实时 `message.updated` 的 100 条裁剪也可能再次移除撤销点。

## 修复方法

- TUI 检测到缺失撤销点后自动加载历史，每页最多 100 条，沿后端游标加载到撤销点以及前一用户轮次；保留原有普通会话的初始加载上限。
- Undo 位于已加载历史最前端时，也会先补页再选择前一轮；Redo / Restore 等待必要历史加载完成后选择正确轮次。
- 合并历史时保留实时消息、消息增量和已加载的 parts，避免旧响应覆盖正在流式更新的数据。
- 同一目标共用加载请求；会话或撤销点变化、页面销毁时取消请求；返回结果再次核对目标，防止串会话写入。
- 单页请求超时为 10 秒。加载失败保留错误和重试入口：点击 Retry 或执行 `/undo-history`。空进展或重复游标明确报错，避免无限循环。
- 撤销状态存在时，实时消息事件保留补回的历史窗口；清除撤销后恢复普通裁剪。离开会话仍按原逻辑释放历史。
- 新增 `/restore-all`，经确认后调用已有后端 `unrevert`，无需前端先加载撤销点即可请求完整恢复。普通 `/redo` 和 Restore 保持逐轮恢复语义。
- 历史提示显示实际加载条数。
- 将状态重置和自动加载放在同一 effect 中，避免初始化时另一个 effect 取消刚启动的恢复请求。
- 确认弹窗先消费 Enter 再执行确认和关闭，避免同一次按键影响底层输入框。
- 输入框在弹窗打开时不抢占提交按键；延迟粘贴提交也检查弹窗状态，确保确认操作不会误触发模型提示提交。

## 范围与代价

撤销点越早，需要读取并保留的历史越多，相应增加网络请求与内存。采用固定大小分页，避免一次返回整个长会话；翻页过程中只在完成时合并，避免反复展开整个历史。

本修复针对“消息存在于存储但未加载”的操作阻塞，不会捏造或删除消息。若撤销点或快照实际损坏，界面明确报错；Restore all 仍依赖后端有效的撤销数据，失败时保留状态，不承诺修复损坏的数据库。之前暂缓处理的 RPC / SSE 大响应限制不在本次修改范围。

测试未操作用户真实会话或项目文件。
