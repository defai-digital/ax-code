## #456：清理时保护仍被会话引用的快照

原行为：超过 7 天的快照引用可能被删除，GC 随后回收对象；会话仍保留，但相关撤销失败。

修改：

- 从注册数据库枚举本项目仍存在的会话，保留 `session.revert.snapshot`。
- 通过 `SessionShard.storeForProject()` 读取相应 registry/shard，保留 `step-start.snapshot`、`step-finish.snapshot` 和 `patch.hash`。归档但未删除的会话同样受保护。
- 按 128 个会话分批查询，只提取有关类型的哈希，避免加载文本、工具输出等无关大字段。
- 清理跳过这些哈希。引用已被旧版本删除但对象仍存在时，先重建 Git 引用。
- 无法读取引用列表、无法查询 Git refs 或无法重新保护对象时，跳过本轮清理。无会话引用的过期快照仍可回收。

验证：分别在未分片、已分片两种存储模式下，创建六个快照并将元数据、松散对象时间设为 8 天前，模拟时间流逝。四类会话引用的快照与当前快照均保留；无引用的过期快照被回收；已删引用得到恢复。执行实际 `Snapshot.revert()` 后，文件恢复为预期内容。另行注入引用读取失败，确认不删除 refs、不执行 GC。

边界：已被 Git 真正回收的对象无法凭哈希重建。此时本修复跳过清理并记录错误，不声称能够找回已丢失内容。保留会话的快照可能增加磁盘占用，这是保留撤销能力的必要结果。

## #457：核心请求部分失败时标记 partial

原行为：6 个核心任务失败 5 个，只要剩余一个成功，就标记 `complete`。

修改：任一核心任务失败即保持或切换为 `partial`，但仍结束启动等待，让界面可以交互。全部核心任务成功才标记 `complete`；后续成功重试可恢复完整状态。重新连接前已经是 `complete` 的情况也可降级为 `partial`。

验证：分别从 `loading`、`partial`、`complete` 三种初始状态执行“五失败、一成功”，确认状态为 `partial`、启动完成回调仍调用、5 条错误被记录；再执行全成功重试，确认恢复 `complete`。已有全失败、全成功及各启动阶段测试也通过。

边界：此次修复状态表达，没有新增自动重试机制，也没有改变造成请求失败的网络或后端因素。

## #458：同一快照仓库的目录实例共享事务队列

原行为：同一 Git 项目的不同目录实例共享快照 index，却各自串行化。`restore()` 的 `read-tree` 和 `checkout-index` 之间，另一实例可以执行 `track()` 改写 index，导致恢复返回成功但文件未恢复。

修改：快照模块共用 `KeyedSerialQueue`，按快照仓库路径串行执行完整操作。数据根路径先解析真实路径，Windows 队列键统一大小写。不同快照仓库使用不同键；队列会在操作完成后释放对应条目。

验证：在同一临时 Git 仓库的 `a/`、`b/` 创建两个目录实例，分别测试 `restore/track` 和 `revert/track` 交错。暂停第一项真实 Git 操作后，第二实例的 `track()` 必须等待；释放后文件为原始内容，后续快照哈希与原始树一致。另注入 Git 失败，确认不会阻塞另一目录之后的快照操作。

边界：这是同一进程内不同目录实例的事务串行化。没有新增跨进程事务锁，不宣称两个独立 CLI 进程之间的多命令事务已被互斥保护。原始 `restore()` 复现属于底层 API；本次增加了当前会话撤销所用 `revert()` 路径的并发回归，但未做真实模型会话的端到端操作。
