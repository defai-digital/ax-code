Launch multiple specialized agents in parallel for independent research or exploration digs.

Use this when several digs have distinct deliverables and non-overlapping discovery scopes (for example: auth, billing, and infra). Name the owned paths or subsystem in each brief and share existing evidence. Use one investigator for a single call path; do not split one cache or performance question into agents that all inspect the same implementation. Explicit independent review may revisit evidence to answer a distinct verification question. Prefer explore / read-only agents.

Do NOT use this tool as a substitute for multi-provider **council** or **arena**. Those tools fan out to multiple LLM providers; task_parallel only runs local agents. If the user asked for council/arena, call those tools first with a short context brief — do not open multi-explore digs first.

Do NOT use concurrent writers. If two or more agents can edit files or run bash mutations, this tool rejects the call. Run writers one at a time with the task tool, or use a single build agent.

Available agent types:
{agents}

Two call shapes:

1. **tasks** — one full prompt per member, when each brief is genuinely different.
2. **items + prompt_template + subagent_type** — one brief fanned over a list. Every
   `{{item}}` occurrence in the template is replaced by one item, so a list of N
   files, modules or cases becomes N members without writing N prompts. Every
   item must produce a distinct prompt, and the whole swarm uses one agent type
   and one optional output_schema. Substitution is single pass: an item that
   contains the placeholder text is inserted verbatim, never expanded again.
   Prefer the task tool when you have a single dig.

Limits:
- 1–8 members per call
- At most `concurrency` members run at once (default 4); the rest queue behind them
- Each member is a separate subagent session with its own context
- Nested task / task_parallel fan-out from children is denied
- Same depth and timeout rules as the single task tool

When the digs finish, summarize the combined evidence for the user. Each result includes a task_id you can resume later with the task tool.

Set output_schema on an individual task (a JSON Schema object) when that result must be machine-checkable rather than prose. Each child then returns that shape; captured values appear per result in both the metadata and a <task_structured_output> block. External $ref is rejected.
