# Tech Spec: Tool Execution Integrity and Request Provenance

**Status:** Implemented
**Date:** 2026-08-21
**Related:** PRD-2026-08-21-tool-execution-integrity, ADR-060

## 1. Scope

This specification implements the selected improvements from the DeepSeek Harness review in the existing AX Code
architecture. It covers registry/MCP state ownership, canonical tool invocation, scoped registration, and a
raw-prompt-free, privacy-minimized pre-adapter request manifest.

## 2. P0 — instance-scoped runtime state

### 2.1 Tool Registry

File: `packages/ax-code/src/tool/registry.ts`

- Move initialized-tool cache and any in-flight initialization promise into the value returned by `Instance.state`.
- Resolve `state()` before checking a cache.
- Retain a bounded single-key cache per instance; cache keys continue to cover model/config variability.
- Invalidate only the current instance after registration changes.

Regression: create two live `Instance`s with different project tools but the same model/config key, load A then B,
and prove their tool sets and captured directories remain distinct.

### 2.2 MCP

File: `packages/ax-code/src/mcp/impl.ts`

Add the following to `McpState`:

- discovered tool cache;
- in-flight discovery promise;
- cache generation;
- per-instance bus unsubscriber;
- per-instance keyed connection queue.

Every add/connect/disconnect/trust/client-close mutation invalidates only that instance. Instance disposal marks the
state disposed, removes its subscription, invalidates discovery, and closes queue admission. It then removes and
closes the already-established client snapshot before awaiting startup and admitted queue work; after that work
settles, it closes any late client in a final pass. This ordering reduces the process-residual window when an MCP
connect is slower than the state-disposal budget without touching another instance. Async callbacks capture their
owning `McpState`; they must not resolve a fresh state after disposal, and stale discovery failures may mutate state
only while their client identity remains current.

Regression: hold two instances open, connect distinct mock servers, discover both, dispose one, and prove the other
still returns its own tools.

### 2.3 Transformed schema cache

File: `packages/ax-code/src/session/prompt-tools.ts`

Keep registry/MCP transformed-schema caches and in-flight work in `Instance.state`. A cache identity includes the
SHA-256 digest of the actual JSON Schema and the full transformation identity: model ID, provider ID, API ID, SDK npm
package, and API URL. This prevents same-name schema changes and model-specific transforms from reusing stale output.

## 3. P1 — canonical invocation

### 3.1 Shared lifecycle helper

File: `packages/ax-code/src/session/prompt-tools.ts`

Extract a helper that runs, in order:

1. `tool.execute.before` plugin hook;
2. PreToolUse lifecycle hook and blocking decision;
3. the supplied execution closure;
4. `tool.execute.after` plugin hook;
5. PostToolUse lifecycle hook.

Existing hook error tolerance and explicit blocking semantics remain unchanged.

### 3.2 Enabled registry dispatcher

The direct-tool resolver constructs an internal dispatcher only from registry tools that survive disabled-tool and
agent visibility filtering. It exposes tool IDs and an execute operation; it does not expose MCP tools.

- Direct wrappers invoke the shared registry invocation function with `isolationPolicy = "escalate"`.
- Only a direct Batch wrapper receives the enabled dispatcher through tool context; nested calls invoke the same
  registry function with `isolationPolicy = "fail-closed"`.
- Nested Batch invocation is excluded to avoid recursion.
- Registry schema parsing remains at the tool-definition boundary.
- The dispatcher returns fully materialized `FilePart` attachments. Batch persists those records unchanged so their
  existing IDs are not regenerated by the outer surface.

### 3.3 MCP lifecycle parity

Wrap the existing MCP `ctx.ask()` plus client call in the shared lifecycle helper. Preserve MCP result conversion and
the existing plugin payload contract. Do not add local-process isolation retry.

## 4. P2 — registration and provenance

### 4.1 Scoped registration

File: `packages/ax-code/src/tool/registry.ts`

Maintain per-ID registration layers `{ token, tool }[]`. The newest layer wins. A returned idempotent disposer removes
only its token, invalidates the current instance cache, and reveals the next layer. Instance disposal remains the
outer lifetime boundary.

### 4.2 Request manifest

Files:

- `packages/ax-code/src/session/request-provenance.ts` (new)
- `packages/ax-code/src/session/llm-impl.ts`
- `packages/ax-code/src/session/processor-impl.ts`
- `packages/ax-code/src/replay/event.ts`

After system transformations, tool resolution, and parameter assembly, canonicalize a manifest at AX Code's AI-SDK
pre-adapter boundary and calculate SHA-256 fingerprints. This boundary excludes later adapter transformations,
headers, and exact provider-wire bytes. Persist additive fields on `llm.request`:

- `provenanceVersion`;
- provider and model IDs;
- message/system/tool counts;
- ordered active tool names;
- hashes for system input, messages, tool definitions, options, and the complete manifest;
- non-sensitive selected options such as tool choice and output-token limit when present.

The options fingerprint covers both those selected common options and the complete sanitized provider-specific
options object. `llm-impl.ts` computes that provider-options object once, passes the same object to provenance and
`streamText`, and persists only its contribution to the hash—not its raw values.

Canonicalization recursively sorts object keys, retains array order, maps unsupported values to stable markers, and
rejects cycles. Tool definitions include model-visible description and JSON Schema, never execute functions.
Unsalted hashes are pseudonymous rather than anonymous: they leak equality and can be dictionary-guessed for
low-entropy input, so normal replay retention/access controls apply. If a tool schema cannot resolve within 250 ms,
emit only `provenanceErrorCode = "manifest_unavailable"` for that request and continue provider dispatch; never emit a
complete-looking partial manifest.

## 5. Compatibility

- Existing callers may ignore the disposer returned by `register()`.
- Replay fields are additive and require no SQLite migration.
- User-facing tool names and results do not change.
- Batch remains parallel and MCP remains excluded.
- Existing lifecycle event names and plugin hook names remain stable.

## 6. Verification

Targeted tests:

- Tool Registry two-instance isolation and registration-layer disposal.
- MCP two-instance discovery/disposal isolation.
- Direct and Batch enabled-tool visibility.
- Plugin + Pre/PostToolUse parity for Batch and MCP.
- Fail-closed Batch isolation.
- Stable request fingerprints and sensitivity to material changes.
- One assembled, keyless request test covering final system/tools/options evidence.

AX_TEST_FILES=<targeted-files> pnpm --dir packages/ax-code exec vitest run

## 7. Rollout

- P0 may ship independently and has no user-visible API change.
- P1 ships after hook/visibility regressions pass.
- P2 replay fields are additive; consumers must tolerate absence in older sessions.
- Any rollback removes one phase without reverting unrelated user changes.
